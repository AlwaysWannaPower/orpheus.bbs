# 13. Что дальше: идеи развития проекта

Плеер работает и им можно пользоваться. Этот файл — про то, куда двигаться
дальше: какие задачи логично взять следующими, в каком порядке и что каждая
из них даст именно с точки зрения учёбы.

Идеи отсортированы по принципу **«польза / затраченное усилие»**: сверху —
то, что даёт много при малых усилиях.

---

## 0. Прежде чем что-то добавлять: закрепи текущее

Три вещи, которые надо сделать до любой новой фичи.

### 0.1. Инициализировать git-репозиторий как следует

```bash
git add -A
git commit -m "Рабочий плеер: скан, библиотека, стриминг, плейлисты, история"
```

Важно убедиться, что в коммит **не попали**:
* `music/` — личная музыка (гигабайты бинарников в истории git — это боль);
* `data/` — база данных;
* `.env` — твои локальные настройки.

Всё это уже прописано в `.gitignore`. Проверить просто:

```bash
git status --short          # что попадёт в коммит
git ls-files | grep -c mp3  # должно быть 0
```

### 0.2. Зафиксировать версии

Файл `bun.lock` **обязан** быть в репозитории. Без него через полгода
`bun install` поставит другие версии библиотек, и проект может перестать
собираться «на ровном месте».

### 0.3. Проверить, что сборка проходит на чистом клоне

Самый честный тест: склонируй репозиторий в другую папку, положи туда пару
mp3 и попробуй собрать с нуля. Если получилось — проект действительно
переносимый, а не «работает только у меня».

## 1. Быстрые улучшения (вечер-два каждое)

### 1.1. Автоматическое сканирование при старте

Сейчас после запуска нужно нажать кнопку. Можно сделать, чтобы сервер сам
проверял библиотеку при старте, а кнопка осталась для ручного обновления.

**Где:** `src/lib/db/client.ts` или отдельный `instrumentation.ts`
(это специальный файл Next.js, который выполняется один раз при старте
сервера).

**Чему научишься:** жизненный цикл серверного процесса, разница между
«работает по запросу» и «работает при инициализации».

**Осторожно:** скан на 5 000 файлов при каждом старте замедлит запуск.
Правильнее — запускать его в фоне, не блокируя сервер.

---

### 1.2. Прогресс сканирования через Server-Sent Events

Сейчас во время скана кнопка просто показывает `▓▒░ СКАНИРОВАНИЕ…`.
Пользователь не знает, идёт процесс или завис.

**Что сделать:** заменить один `POST /api/scan` на поток событий.

```ts
// Сервер отправляет события по мере обработки файлов
export async function GET() {
  const stream = new ReadableStream({
    async start(controller) {
      const encoder = new TextEncoder();
      await scanMusicLibrary({
        onProgress: (done, total) => {
          controller.enqueue(encoder.encode(`data: ${JSON.stringify({ done, total })}\n\n`));
        },
      });
      controller.close();
    },
  });

  return new Response(stream, {
    headers: { "Content-Type": "text/event-stream" },
  });
}
```

**Чему научишься:** SSE (Server-Sent Events), потоки на сервере, работа
с `EventSource` в браузере. Это тот же материал, что и в главе
[05](05-http-range-streaming.md), но с другой стороны.

**Почему SSE, а не WebSocket:** данные идут только в одну сторону
(сервер → клиент). WebSocket умеет двустороннюю связь, но здесь она
не нужна. Выбирать инструмент по задаче — хорошая привычка.

### 1.3. Правка метаданных вручную

Бывает, что теги проставлены криво: исполнитель записан как «ATL, Ка тет,
Horus» в одном поле. Хочется поправить.

**Что сделать:**

1. добавить колонку `is_manual_edit` в `tracks` (0/1);
2. в сканере **не перезаписывать** поля, если стоит флаг;
3. сделать форму редактирования в интерфейсе.

**Чему научишься:** миграции (изменение схемы живой базы!), правило
«пользовательские данные не трогает автоматика» (то же, что уже сделано
для избранного).

**Это отличное упражнение на миграции.** Порядок действий:

```bash
# 1. правишь schema.ts
# 2. генерируешь миграцию
bunx drizzle-kit generate
# 3. смотришь получившийся SQL — он разумный?
cat drizzle/0001_*.sql
# 4. перезапускаешь сервер — миграция применится автоматически
bun run dev
```

Плейлист можно выгрузить в файл и перенести на другой компьютер.

**Чему научишься:** работа с файлами на сервере, `Blob` и скачивание

### 1.5. Отображение «сейчас играет» в заголовке вкладки

Когда вкладка свёрнута, хочется видеть в заголовке название трека.

```ts
useEffect(() => {
  if (!currentTrack) return;
  document.title = `${isPlaying ? "▶" : "❚❚"} ${currentTrack.title} — ${currentTrack.artist}`;
  return () => { document.title = "ORPHEUS.BBS"; };

```

**Чему научишься:** прямое взаимодействие с DOM из React, зачем нужна
функция очистки в `useEffect`.

### 1.6. Полнотекстовый поиск через FTS5

Сейчас поиск — это `LIKE '%текст%'` по колонке `search_text`. Для тысяч
треков этого достаточно, но у `LIKE` есть ограничения: нельзя искать
по опечаткам, нельзя ранжировать по релевантности.

В SQLite есть модуль **FTS5** — полнотекстовый поиск с индексом по словам.

```sql
CREATE VIRTUAL TABLE tracks_fts USING fts5(title, artist, album, content='tracks', content_rowid='id');
```

**Чему научишься:** виртуальные таблицы SQLite, триггеры для синхронизации
индекса, разница между «поиском по подстроке» и «поиском по словам».

**Связь с основным курсом:** это прямой аналог полнотекстовых индексов
в ClickHouse (например, `tokenbf_v1` / `ngrambf_v1` skip-индексы).
Полезно сравнить подходы.

## 2. Средние задачи (выходные)

### 2.1. Тесты

В проекте нет ни одного теста. Это нормально для учебного проекта, но
**это первое, чего будет не хватать**, когда код начнёт расти.

Что стоит покрыть в первую очередь — **чистые функции**, потому что они
тестируются проще всего:

* `src/lib/format.ts` — `formatDuration`, `formatRelativeTime`, `pluralize`
  (обрати внимание на склонения: «1 трек», «2 трека», «5 треков» — идеальный
  кандидат на таблицу тест-кейсов);
* `src/lib/db/mappers.ts` — `toTrackDTO`;
* `src/lib/scanner/metadata.ts` — `titleFromFilename`, `guessFromFolders`;
* `parseRangeHeader` (сейчас она внутри route-файла — придётся вынести
  в `src/lib/http-range.ts`, и это само по себе улучшение: чистая логика
  не должна жить в обработчике HTTP).

Bun умеет запускать тесты из коробки, без установки чего-либо:

```ts
// src/lib/format.test.ts
import { describe, expect, test } from "bun:test";
import { formatDuration, pluralize } from "./format";

describe("formatDuration", () => {
  test("секунды и минуты", () => {
    expect(formatDuration(0)).toBe("0:00");
    expect(formatDuration(45)).toBe("0:45");
    expect(formatDuration(213.9)).toBe("3:33");   // округление ВНИЗ
  });

  test("часы", () => {
    expect(formatDuration(3725)).toBe("1:02:05");
  });

  test("мусорные значения", () => {
    expect(formatDuration(NaN)).toBe("0:00");
    expect(formatDuration(-5)).toBe("0:00");
  });
});
```

```bash
bun test
```

**Чему научишься:** `describe`/`test`/`expect`, тестирование граничных
случаев (ноль, отрицательное, NaN), что такое «чистая функция» и почему
её легко тестировать.

### 2.2. Понятные уведомления вместо `alert`

Сейчас результат действий показывается в маленьких блоках внутри интерфейса.
Можно сделать аккуратную систему уведомлений (toast).

**Чему научишься:** `createPortal` в React, работа с `position: fixed`

### 2.3. Кэширование тяжёлых запросов

Список альбомов и статистика библиотеки считаются при каждом заходе
на страницу. Данные меняются редко — их можно кэшировать.

В Next.js 16 для этого есть директива `"use cache"` и механизм Cache
Components. Но **сначала измерь**: если запрос выполняется за 2 мс,
кэшировать нечего. Профилируй, потом оптимизируй.

**Чему научишься:** кэширование в Next.js, инвалидация кэша (самая сложная
тема в информатике — шутка, в которой много правды), разница между
«данные меняются» и «данные неизменны».

---

### 2.4. Обложки альбомов: скачивание и ручная замена

Иногда у альбома нет встроенной обложки. Можно:

* сделать страницу альбома, где обложку можно загрузить руками;
* автоматически подтягивать обложки из внешних источников (MusicBrainz,
  Cover Art Archive) — но это сетевая зависимость и вопросы лицензий.

**Чему научишься:** загрузка файлов на сервер (`FormData`,
`request.formData()`), проверка типа и размера загружаемого файла
(**никогда не доверяй тому, что загрузил пользователь**), работа
с внешними API и их ограничениями (rate limiting).

### 2.5. Страница альбома и страница исполнителя

Сейчас есть только общий список, а запросы `listAlbums()` и `listArtists()`
в `src/lib/db/track-queries.ts` **уже написаны** — но не используются
в интерфейсе!

Сделать:
* `/artists` — сетка исполнителей;
* `/artists/[name]` — альбомы исполнителя;
* `/albums/[id]` — треки альбома с обложкой во всю ширину.

**Чему научишься:** вложенные динамические маршруты, `generateMetadata`
для заголовка страницы, передача параметров через URL.

**Бонус:** это самый быстрый способ получить «много интерфейса» из кода,
который уже есть.

## 3. Крупные задачи (то, что стоит делать осознанно)

### 3.1. YouTube-загрузчик (из ТЗ — «потом и отдельно»)

В техническом задании сказано правильно: **не смешивать с плеером**.
Загрузчик должен быть просто ещё одним источником файлов в `./music`,
и плеер о нём ничего не знает.

Почему так:

* плеер не знает, откуда взялся файл, и это хорошо — меньше связности;
* если загрузчик сломается (а такие штуки ломаются часто), плеер продолжит
  работать;
* можно запускать загрузчик отдельно, например по расписанию.

**Про реализацию.** Технически это `yt-dlp` — внешняя программа, которую
надо вызывать из кода:

```ts
import { spawn } from "node:child_process";

const child = spawn("yt-dlp", [
  "--extract-audio",
  "--audio-format", "mp3",
  "--audio-quality", "0",
  "--embed-thumbnail",
  "--output", `${MUSIC_DIR}/%(artist)s - %(title)s.%(ext)s`,
  url,
]);
```

Дальше нужно:
1. стримить вывод процесса в интерфейс (чтобы видеть прогресс);
2. ловить ошибки (неверная ссылка, недоступное видео, нет интернета);
3. после успешной загрузки автоматически запустить сканирование.

**Чему научишься:** `child_process.spawn`, потоки процессов, обработка
долгих операций, построение очереди задач.

> ⚠️ **Юридическая часть, которую нельзя пропускать.** Скачивание контента
> с YouTube регулируется Условиями использования сервиса и авторским правом.
> Использовать это стоит только для контента, который тебе разрешено
> скачивать: собственные видео, материалы с открытой лицензией, контент
> правообладателя, который дал разрешение. Технически сделать можно многое —
> а вот стоит ли, вопрос отдельный. В ТЗ это отмечено отдельно, и не зря.

### 3.2. Встраивание плеера в сайт-резюме

Разобрано в главе [12](12-dizayn-i-temy.md), раздел 11.
Три уровня сложности: скопировать стили, вынести общий пакет, встроить
компонент напрямую. Начинать стоит с первого.

Самая сильная идея там — **показывать на сайте-резюме реальную статистику
из плеера**. Не «нарисованные» достижения, а настоящие данные:

* топ-5 треков по прослушиваниям;
* сколько часов музыки прослушано;
* распределение по жанрам.

Запросы для этого уже написаны. Рекрутер, который видит «человек сделал
продукт и пользуется им каждый день», получает совсем другое впечатление,
чем от списка технологий.

### 3.3. Аналитика: SQLite → ClickHouse → dbt → BI

**Вот это — самая ценная идея для тебя лично**, потому что она соединяет
этот проект с твоим основным курсом.

Идея: `play_history` — это настоящая таблица фактов, которую ты сам
производишь. Не учебный датасет про продажи кофе, а собственные данные.

```
SQLite (OLTP)              ClickHouse (OLAP)
┌─────────────────┐        ┌──────────────────────┐
│ play_history    │        │ listens              │
│ tracks          │───────►│ tracks_dim           │
│ playlists       │ выгруз │                      │
└─────────────────┘        └──────────┬───────────┘
                                      │
                                   dbt модели
                                      │
                          ┌───────────▼───────────┐
                          │  stg_listens          │
                          │  fct_listens          │  ← витрины
                          │  dim_tracks           │
                          │  mart_top_artists     │
                          └───────────┬───────────┘
                                      │
                                  BI-дашборд
```

**Что это даёт:**

1. **Настоящий end-to-end конвейер.** От собственного приложения до
   дашборда. Это уже уровень «портфолио-проект», а не «учебное задание».
2. **Понимание OLTP vs OLAP** на живом примере: почему нельзя просто
   «переключить SQLite на ClickHouse» и всё заработает.
3. **Данные, которые растут сами.** Каждый день прослушивания добавляют
   строки. Через полгода у тебя будет датасет с историей — а с ним уже
   интересно работать.

**С чего начать, по шагам:**

1. Написать скрипт выгрузки: `SELECT * FROM play_history` → сохранить
   в JSON/CSV/Parquet.
2. Поднять ClickHouse в Docker (теперь ты знаешь, как).
3. Создать таблицу с движком `MergeTree`, `ORDER BY played_at`.
4. Залить данные.
5. Написать dbt-проект: `stg_` → `fct_` → `mart_`.
6. Собрать дашборд в Metabase/Superset/Grafana.

**Упражнение на размышление:** почему в ClickHouse таблицу фактов делают
с `ORDER BY (played_at)` или `ORDER BY (track_id, played_at)`, а не так,
как в SQLite? Что изменится в производительности запросов «топ треков
за месяц» и «сколько слушали в среду вечером»?

### 3.4. PWA: установка на телефон

Можно сделать так, чтобы сайт устанавливался на телефон как приложение:
иконка на домашнем экране, работа без адресной строки, оффлайн-режим.

**Что нужно:**

1. `manifest.json` — описание приложения (имя, иконки, цвет темы);
2. service worker — кэширование статики;
3. HTTPS (или localhost) — обязательное требование браузеров.

**Чему научишься:** service workers, стратегии кэширования, `Cache API`,
работа с оффлайном.

**Сложность:** реальная. Service worker — это отдельный поток со своей
жизнью, и отладка там специфическая. Зато тема интересная и полезная.

---

### 3.5. Многопользовательский режим (осторожно!)

Кажется простым: добавить таблицу `users` и колонку `user_id`. На деле
это **самая опасная задача из списка**.

Что придётся сделать:

* аутентификация: хеширование паролей (никогда не храни пароли в открытом
  виде!), сессии, cookies с флагами `HttpOnly` и `Secure`;
* авторизация: проверка, что пользователь имеет право на этот трек
  (иначе один пользователь скачает библиотеку другого);
* CSRF-защита;
* миграция существующих данных.

**Рекомендация:** если руки чешутся — не делай это «для галочки». Плохо
сделанная авторизация хуже, чем её отсутствие: создаётся ложное чувство
защищённости. В ТЗ прямо сказано «сложный auth не добавляем», и это
правильное решение для учебного проекта.

Если очень хочется — используй готовые решения (Better Auth, Lucia,
Auth.js). Но помни: ты учишься, и добавлять «чёрный ящик» в учебный проект
значит учиться меньше.

## 4. Что стоит изучить отдельно (не в этом проекте)

Темы, которые логично освоить на других, маленьких проектах:

| Тема | Почему отдельно |
| --- | --- |
| **Тестирование React-компонентов** | нужен отдельный стек (Vitest + Testing Library), лучше на маленьком проекте |
| **Формы со сложной валидацией** | Zod/react-hook-form — легче понять на форме без плеера |
| **Оптимистичные обновления и кэш-библиотеки** | TanStack Query — в этом проекте не нужен (Server Components справляются), но знать полезно |
| **CSS-анимации и переходы** | лучше на сайте-резюме, там больше свободы |
| **Веб-сокеты и реалтайм** | нужен сценарий «несколько клиентов одновременно», а у нас один |

**Общее правило:** не тащи технологию в проект, где она не решает реальную
проблему. Каждая лишняя библиотека — это то, что надо обновлять, отлаживать
и понимать. Проект тем и хорош, что в нём мало зависимостей.

## 5. Порядок, который я бы рекомендовал

```
1. Закоммитить текущее состояние и проверить чистый клон
2. Страницы исполнителей и альбомов      ← много интерфейса из готового кода
3. Тесты на чистые функции               ← навык, который нужен везде
4. Прогресс сканирования через SSE       ← красиво и поучительно
5. Правка метаданных вручную             ← упражнение на миграции
6. Сайт-резюме + встраивание плеера      ← то, ради чего всё затевалось
7. SQLite → ClickHouse → dbt → BI        ← соединение с основным курсом
8. PWA / YouTube-загрузчик               ← когда будет время и желание
```

Пункты 2, 3 и 6 дают максимум пользы на единицу усилий. Пункт 7 — самый
ценный стратегически.

## 6. Мысли напоследок

Этот проект получился ровно таким, каким должен быть учебный проект:

* **маленький** — весь код читается за вечер;
* **работающий** — им можно пользоваться каждый день;
* **прикладной** — в нём есть и HTTP, и SQL, и React, и Docker;
* **свой** — не клон туториала, а вещь под собственную задачу.

Самое ценное в нём — даже не код, а **привычка доводить до работающего
состояния**. Большинство учебных проектов умирают на стадии «вроде
запускается». Здесь доведено до состояния «я этим пользуюсь».

Дальше можно двигаться в любую сторону: углубляться в фронтенд (и сделать
красивый сайт-резюме), или в данные (и построить аналитику поверх
собственных прослушиваний), или во что-то третье. Хорошая новость в том,
что база теперь есть везде.

И последнее: **это твой проект**. Если какое-то решение в нём кажется
неправильным — поменяй. Лучший способ учиться — переделать что-то своими
руками и посмотреть, что получится. Весь код прокомментирован именно
для этого.
