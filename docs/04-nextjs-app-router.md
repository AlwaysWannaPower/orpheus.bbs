# 04. Next.js и App Router

Это самая концептуально сложная глава. Если предыдущие технологии
(TypeScript, React) можно понять «по аналогии», то Next.js требует смены
мышления: **часть твоего кода выполняется на сервере, часть — в браузере**,
и впервые за всю историю фронтенда это стало нормой, а не костылём.

Читай эту главу медленно и держи рядом код проекта.

---

## 1. Зачем нужен Next.js, если уже есть React

React — это **библиотека для интерфейсов**. Он умеет: «вот данные → вот
разметка». Всё.

Но у настоящего приложения есть задачи, к React не относящиеся вообще:

* как сделать так, чтобы URL `/playlists/3` открывал нужную страницу;
* как отдать браузеру HTML, а не пустую страницу с JavaScript;
* где взять данные из базы (в браузере к базе подключиться нельзя!);
* как сделать API для браузера;
* как собрать проект в production-версию.

Раньше это решалось сборкой «React + куча библиотек». Next.js дал один
конструктор, в котором всё это есть из коробки. Причём с одной важной идеей:
**серверный код и клиентский код пишутся в одном проекте**, а разделяются
не «репозиториями», а одной строчкой `"use client"`.

## 2. App Router: маршрут = папка

Основная идея App Router (папка `app/` или `src/app/`) — **структура папок
и есть структура URL**. Специальные имена файлов определяют, что делает
эта папка.

```
src/app/
├── layout.tsx                  ← общая рамка для ВСЕХ страниц        →  (любой URL)
├── page.tsx                    ← главная страница                    →  /
├── (loading.tsx)               ← экран загрузки — в проекте СОЗНАТЕЛЬНО не используется, см. §8.1
├── error.tsx                   ← что показывать при ошибке
├── not-found.tsx               ← что показывать на 404
│
├── playlists/
│   ├── page.tsx                ← страница списка                     →  /playlists
│   └── [id]/
│       └── page.tsx            ← страница одного плейлиста           →  /playlists/3
│
├── history/
│   └── page.tsx                ← история                             →  /history
│
└── api/
    ├── scan/route.ts           ← POST /api/scan
    ├── tracks/
    │   ├── route.ts            ← GET  /api/tracks
    │   └── [id]/
    │       ├── route.ts        ← PATCH /api/tracks/1
    │       ├── stream/route.ts ← GET  /api/tracks/1/stream
    │       └── cover/route.ts  ← GET  /api/tracks/1/cover
    ├── playlists/…
    ├── history/route.ts
    └── playback-state/route.ts
```

Правила, которые надо запомнить:

| Файл | Что означает |
| --- | --- |
| `page.tsx` | это URL, который увидит пользователь |
| `layout.tsx` | общая рамка; **не пересоздаётся** при переходах между дочерними страницами |
| `route.ts` | обработчик HTTP. Это API, а не страница |
| `loading.tsx` | автоматический экран загрузки (обёртка в `<Suspense>`). В проекте не используется — почему, см. §8.1 |
| `error.tsx` | граница ошибок: если внутри упало — пользователь увидит это |
| `not-found.tsx` | страница 404 |

**Важные ограничения:**

* `page.tsx` и `route.ts` **не могут** лежать в одной папке: «здесь страница»
  и «здесь API» — взаимоисключающие вещи. Именно поэтому API живёт в
  отдельных папках внутри `api/`.
* Папки, имя которых начинается с `_` (или взято в круглые скобки `()`),
  **не становятся маршрутами**. Это служебные папки. Автор этого проекта
  наткнулся на эту особенность на практике: файл `src/app/api/__probe/route.ts`
  упорно отдавал 404, пока не выяснилось, что двойное подчёркивание делает
  папку приватной. Полезно помнить.

### Динамические сегменты `[id]`

Папка в квадратных скобках означает «сюда подставляется любое значение».
Запрос `/playlists/3` попадёт в `playlists/[id]/page.tsx`, и значение `3`
придёт в параметр `id`.

```tsx
// src/app/playlists/[id]/page.tsx
export default async function PlaylistPage({ params }: PageProps<"/playlists/[id]">) {
  const { id } = await params;      // id — строка "3"
  const playlistId = Number(id);     // а нам нужен number
  // …
}
```

> **Здесь спотыкаются все.** В Next.js 15 `params` и `searchParams` стали
> **Promise**. Их обязательно `await`-ить. Старые туториалы пишут `params.id`
> напрямую — в этой версии так уже не работает.

Есть и «универсальные» сегменты: `[...slug]` (ловит всё, включая слэши)
и `[[...slug]]` (то же, но необязательный).

## 3. Server Components и Client Components — главная идея

### Что происходит «под капотом»

Когда браузер запрашивает страницу:

```
браузер: GET /
    ↓
Next.js выполняет СЕРВЕРНЫЕ компоненты (твой код на сервере)
    ↓
получается HTML → отправляется браузеру сразу
    ↓
браузер показывает HTML, затем подгружает JavaScript
    ↓
React «оживляет» КЛИЕНТСКИЕ компоненты (делает их интерактивными)
```

Обрати внимание: **HTML приходит уже готовым**. Серверные компоненты
не нужно «дожидаться» — их результат уже внутри HTML. Поэтому страница
видна почти сразу, даже если JavaScript ещё грузится.

### Как определить, какой это компонент

**По умолчанию — серверный.** В `src/app/page.tsx` нет никаких директив,
значит это серверный компонент: он может читать базу напрямую.

**Клиентским он становится**, если в первой строке файла написано:

```tsx
"use client";
```

### Таблица различий

| | Серверный компонент | Клиентский компонент |
| --- | --- | --- |
| Где выполняется | только на сервере | в браузере (и на сервере при первой отрисовке) |
| `async` / `await` | ✅ да | ❌ нет |
| Доступ к базе данных | ✅ да | ❌ нет |
| Доступ к файлам (`fs`) | ✅ да | ❌ нет |
| Переменные окружения с секретами | ✅ да | ❌ только `NEXT_PUBLIC_*` |
| `useState`, `useEffect`, `useRef` | ❌ нет | ✅ да |
| `onClick` и другие обработчики | ❌ нет | ✅ да |
| `window`, `document`, `localStorage` | ❌ нет | ✅ да |
| Попадает ли код в браузер | ❌ нет | ✅ да |

Последняя строка — самая приятная. Код серверного компонента **не уезжает
пользователю вообще**. Значит, в нём можно держать что угодно, не думая
о размере бандла.

### Живые примеры из проекта

**Серверные** (нет `"use client"`, могут читать базу):

* `src/app/page.tsx` — библиотека; вызывает `listTracks()` и
  `getPlaybackState()` напрямую;
* `src/app/playlists/[id]/page.tsx` — читает плейлист и его треки;
* `src/components/layout/AppHeader.tsx` — `async`-компонент, считает
  статистику библиотеки;
* `src/components/layout/Sidebar.tsx` — список плейлистов из базы.

**Клиентские** (есть `"use client"`, нужны хуки и обработчики):

* `src/components/player/player-context.tsx` — нужны `useState`, `useEffect`,
  доступ к `<audio>`, `localStorage`;
* `src/components/library/TrackList.tsx` — нужны `onClick` и `onKeyDown`;
* `src/components/library/SearchBar.tsx` — `useState`, роутер;
* `src/components/library/ScanButton.tsx` — `fetch`, состояние загрузки.

### ГРАНИЦА МЕЖДУ МИРАМИ

Клиентский компонент может **включать в себя** серверный, если передаст его
как `children`. А наоборот — серверный включает клиентский — можно свободно.

Но данные через границу должны быть **сериализуемыми**. Можно передать:

* строки, числа, boolean, `null`, `undefined`;
* массивы и обычные объекты из них;
* `Date` (Next сериализует его сам);
* `Promise` (тоже поддерживается).

Нельзя передать: функцию, класс, экземпляр объекта базы, файловый дескриптор.

Именно поэтому в проекте есть `src/lib/types.ts` с типом `TrackDTO` — это
«транспортная» версия строки базы. Из неё **сознательно убраны** поля `path`
(абсолютный путь к файлу на сервере) и преобразованы `Date` → число.
Подробнее — в комментариях `src/lib/db/mappers.ts`.

## 4. Где брать данные: сервер, а не API

В классическом SPA данные берут так:

```
браузер → GET /api/tracks → сервер → база → JSON → браузер → рендер
```

В Next.js с серверными компонентами можно короче:

```
сервер (Server Component) → база → HTML → браузер
```

**Второй вариант быстрее и проще:** нет сетевого запроса, нет сериализации,
нет состояния загрузки, нет `useEffect`.

В проекте это выглядит так:

```tsx
// src/app/page.tsx — серверный компонент
export default async function LibraryPage({ searchParams }: PageProps<"/">) {
  const params = await searchParams;

  // Прямой вызов функции, читающей SQLite. Никакого fetch!
  const tracks = await listTracks({ search: params.search, sort: "added_desc" });

  return <TrackList tracks={tracks} />;
}
```

### Когда всё-таки нужен API

Когда запрос идёт **из браузера**. В проекте это:

* мутации (изменение данных): избранное, плейлисты, история;
* сканирование библиотеки;
* поток аудио (`/api/tracks/[id]/stream`) — его запрашивает сам `<audio>`;
* обложки.

Проще говоря:

> **Читаем — на сервере напрямую. Меняем — через API.**

Это не догма, но правило работает почти всегда.

## 5. Route Handlers (API)

Файл `route.ts` экспортирует функции с именами HTTP-методов.

```ts
// src/app/api/scan/route.ts
export async function POST(): Promise<Response> {
  const result = await scanMusicLibrary();
  return Response.json(result);
}
```

Всё. Никаких роутеров, контроллеров и декораторов — имя функции и есть метод.

Поддерживаются `GET`, `POST`, `PUT`, `PATCH`, `DELETE`, `HEAD`, `OPTIONS`.
Если запросить несуществующий метод, Next вернёт `405 Method Not Allowed`
автоматически.

### Request и Response — стандартные веб-API

Внутри Route Handler ты работаешь с теми же объектами `Request` и `Response`,
что и в браузере. Это стандарты платформы, а не изобретение Next.js. Поэтому
знание переносится: то же самое в Cloudflare Workers, Deno, Service Worker.

```ts
// Чтение параметров запроса
const url = new URL(request.url);
const search = url.searchParams.get("search");

// Чтение тела
const body = await request.json();

// Заголовки
const range = request.headers.get("range");

// Ответ
return Response.json({ ok: true });
return new Response(null, { status: 204 });
return new Response(stream, { status: 206, headers: { … } });
```

### Валидируй всё, что приходит снаружи

Правило: **URL и тело запроса — это пользовательский ввод**, даже если у тебя
есть свой интерфейс. Запрос можно отправить `curl`'ом, и туда прилетит что
угодно.

В проекте это видно в каждом обработчике. Пример из
`src/app/api/playlists/[id]/route.ts`:

```ts
function parseId(rawId: string): number | Response {
  const id = Number(rawId);
  if (!Number.isInteger(id) || id <= 0) {
    return jsonError("Некорректный идентификатор плейлиста", 400);
  }
  return id;
}
```

Обрати внимание на возвращаемый тип `number | Response` — это union
«или число, или готовый ответ с ошибкой». TypeScript заставит проверить,
что именно вернулось, прежде чем использовать:

```ts
const parsed = parseId((await context.params).id);
if (parsed instanceof Response) return parsed;   // это ошибка, отдаём её
// дальше parsed — точно number
```

## 6. layout.tsx: рамка, которая не пересоздаётся

Это самое важное место всего проекта с точки зрения архитектуры.

```tsx
// src/app/layout.tsx
export default function RootLayout({ children }: LayoutProps<"/">) {
  return (
    <html lang="ru">
      <body>
        <PlayerProvider>        {/* ← клиентский провайдер плеера */}
          <AppHeader />
          <div className="flex">
            <Sidebar />
            <main>{children}</main>   {/* ← сюда подставляется страница */}
          </div>
          <PlayerBar />         {/* ← панель управления плеером */}
        </PlayerProvider>
      </body>
    </html>
  );
}
```

Что это даёт:

1. **`<audio>` создаётся один раз.** При переходе с `/` на `/history` React
   НЕ размонтирует `PlayerProvider`, значит элемент живёт, и музыка
   продолжает играть.
2. **Шапка и боковая панель не перерисовываются.** Они уже есть в DOM.
3. **Общий стиль и шрифт** применяются ко всему приложению автоматически.

> **Типичная ошибка:** положить провайдер плеера в `page.tsx`. Тогда при
> первом же переходе на другую страницу `<audio>` уничтожится и музыка
> оборвётся. Если однажды столкнёшься с таким поведением — ищи, где живёт
> провайдер.

Layout-ы **вкладываются**: корневой `layout.tsx`, внутри может быть
`playlists/layout.tsx`, внутри — ещё. `children` — это «то, что ниже».

## 7. Навигация

### `<Link>` вместо `<a>`

```tsx
import Link from "next/link";

<Link href="/playlists">ПЛЕЙЛИСТЫ</Link>
```

Почему не `<a href>`:

* `<a>` заставляет браузер загрузить страницу целиком — заново скачать HTML,
  CSS, JS, пересоздать React-дерево. **Музыка остановится.**
* `<Link>` делает «мягкий» переход: догружает только изменившуюся часть,
  сохраняет состояние клиентских компонентов.
* `<Link>` заранее подгружает страницу, когда пользователь наводит курсор
  (prefetch) — переход кажется мгновенным.

### Программная навигация

```tsx
"use client";
import { useRouter } from "next/navigation";

const router = useRouter();
router.replace("/?search=атл");   // заменить текущую запись истории
router.push("/history");          // добавить новую запись
router.refresh();                 // перезапросить данные с сервера
```

Разница между `push` и `replace` — в поведении кнопки «назад»:

* `push` — «назад» вернёт туда, где были;
* `replace` — записи не остаётся, «назад» перепрыгнет через это состояние.

В проекте `replace` используется для поиска и сортировки
(`src/components/library/SearchBar.tsx`). Иначе кнопка «назад» отматывала бы
по одной букве — это очень раздражает.

### `router.refresh()` — ключевой приём

После изменения данных на клиенте (поставили «избранное», создали плейлист)
нужно, чтобы серверные компоненты показали новое состояние.

```tsx
fetch(`/api/tracks/${trackId}`, { method: "PATCH", … })
  .then(() => router.refresh());
```

`refresh()` **заново выполняет серверные компоненты**, не теряя состояние
клиентских. Музыка продолжает играть, поле поиска не очищается — обновляется
только то, что пришло с сервера.

Сравни с `window.location.reload()`: полная перезагрузка, сброс всего
состояния, остановка музыки. Никогда так не делай в этом проекте.

## 8. Рендеринг: статический и динамический

Next.js старается отдать как можно больше «замороженного» HTML. Такой HTML
можно закэшировать и отдавать мгновенно.

Но у нас база данных, которая меняется. Значит, страницы должны собираться
**при каждом запросе**. Это и называется динамическим рендерингом.

В проекте это указано явно:

```ts
// src/app/page.tsx
export const dynamic = "force-dynamic";
```

Такие объявления называются **route segment config** — константы на уровне
модуля, которые читает Next.js.

Что ещё делает страницу динамической автоматически:

* обращение к `searchParams` или `params`;
* вызов `headers()` или `cookies()`;
* `fetch` с `cache: "no-store"`.

### Про кэширование GET-обработчиков

В этом Next.js `GET`-обработчики **не кэшируются по умолчанию** (в старых
версиях было наоборот — это одна из «ломающих перемен», о которых
предупреждает `AGENTS.md`). В API проекта мы всё равно явно ставим
`export const dynamic = "force-dynamic"` — чтобы никто (включая будущего
себя) случайно не включил кэш и не получил баг «браузер отдаёт старые данные».

А вот файлы кэшировать полезно: у аудио стоит `Cache-Control: public,
max-age=86400`, у обложек — `immutable, max-age=31536000`, потому что имя
файла обложки это SHA-1 от содержимого и файл с таким именем не меняется
никогда.

## 9. Метаданные и typed routes

### Метаданные

```tsx
// src/app/layout.tsx
export const metadata: Metadata = {
  title: "ORPHEUS.BBS — персональный музыкальный плеер",
  description: "Локальная музыкальная библиотека…",
};

// ВАЖНО: viewport — ОТДЕЛЬНЫЙ экспорт, а не поле в metadata.
// Это тоже изменение новой версии Next.js.
export const viewport: Viewport = {
  width: "device-width",
  initialScale: 1,
  themeColor: "#040704",
};
```

Метаданные вкладываются: `metadata` в конкретной странице дополняет
корневые и перекрывает совпадающие поля (см. `src/app/history/page.tsx`).

### Типизированные маршруты

В Next.js 16 типы маршрутов генерируются автоматически. После запуска
`next dev` или `next build` становятся доступны глобальные типы:

```tsx
PageProps<"/">                    // пропсы страницы (params, searchParams)
PageProps<"/playlists/[id]">      // с конкретным динамическим сегментом
LayoutProps<"/">                  // пропсы layout
RouteContext<"/users/[id]">       // контекст Route Handler
```

Их не надо импортировать — они глобальные. Если редактор подчёркивает
`PageProps` красным, значит типы ещё не сгенерированы: запусти dev-сервер.

Что это даёт: если перепутаешь путь (`PageProps<"/playlist/[id]">` вместо
`"/playlists/[id]"`), TypeScript сразу скажет, что такого маршрута нет.

### Suspense и «граница ожидания»

```tsx
<Suspense fallback={<div>загрузка…</div>}>
  <SearchBar />
</Suspense>
```

`<Suspense>` говорит React: «пока этот кусок не готов — показывай fallback».
Это работает и на сервере: HTML вылетает браузеру сразу, а медленные части
догружаются позже. Приём называется **streaming SSR**.

Компоненту `SearchBar` Suspense обязателен, потому что он использует
`useSearchParams` — Next.js требует обернуть такие компоненты.

### 8.1. Почему в проекте НЕТ `loading.tsx` (реальный найденный баг)

Это самая поучительная история проекта про Next.js, и она стоит того, чтобы
её разобрать.

**Что было сделано сначала.** Был создан файл `src/app/loading.tsx` —
терминальный экран «ЗАГРУЗКА ДАННЫХ…». Красиво, по-своему логично: данные
из базы, пусть пользователь видит, что происходит.

**Что пошло не так.** Проверка показала:

```bash
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/playlists/999
# 200   ← а должно быть 404!
```

Несуществующий плейлист отдавался с кодом **200 OK**. Страница при этом
показывала правильную надпись «РЕСУРС НЕ НАЙДЕН», но **статус-код был
неверным**.

**Почему так произошло.** Разберём по шагам:

1. `loading.tsx` в папке — это не просто «файл с разметкой». Next.js
   автоматически оборачивает страницу в `<Suspense>` и берёт этот файл
   как `fallback`.
2. `<Suspense>` включает **streaming**: сервер начинает отправлять HTML
   браузеру, не дожидаясь, пока все данные загрузятся. Сначала уходит
   оболочка (корневой `layout.tsx` с шапкой и боковой панелью), затем
   подгружаются более медленные части.
3. А теперь главное: **статус-код HTTP отправляется в первых байтах ответа**.
   Пока сервер ждал данных, он уже отправил `200 OK` вместе с оболочкой.
4. Когда страница наконец вызвала `notFound()` и захотела ответить 404 —
   ответ уже «начал течь». Поменять статус задним числом невозможно:
   он уже у получателя.

Next.js не может обойти физику протокола. Он честно подменяет содержимое
страницы на `not-found.tsx`, но код ответа остаётся 200.

**Проверка гипотезы.** Файл был временно убран, проект пересобран:

```bash
# без src/app/loading.tsx
curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/playlists/999
# 404   ← теперь правильно
```

Гипотеза подтвердилась полностью.

**Какое решение принято и почему.** Корневой `loading.tsx` **удалён**.
Вместо него добавлен `src/app/playlists/[id]/not-found.tsx` — локальная
страница 404 с понятным текстом именно про плейлист.

Обоснование выбора:

| | С `loading.tsx` | Без него |
| --- | --- | --- |
| Экран загрузки | есть | нет |
| HTTP-статус 404 | **неверный (200)** | правильный |
| Виден ли экран загрузки на практике | практически никогда: запрос к локальной SQLite занимает ~1 мс | — |

Второй пункт решает всё. Данные лежат в **локальном** файле, запрос к ним
занимает миллисекунды. Экран загрузки физически не успевает появиться —
пользователь видит его разве что при первом заходе на холодном кеше.

А вот неправильный код ответа — это реальная проблема:

* поисковые роботы индексируют несуществующую страницу как существующую;
* `curl`, Postman и любые внешние программы не понимают, что ресурса нет;
* если однажды появится API-клиент или мобильное приложение, оно получит 200
  и решит, что всё в порядке.

**Мораль, которую стоит запомнить:**

> Удобство интерфейса иногда конфликтует с корректностью протокола.
> Когда речь о **контракте с внешним миром** (HTTP-коды, форматы данных,
> схемы) — выбирай корректность. Интерфейс можно улучшить позже,
> а сломанный контракт обнаруживается уже у потребителя.

И ещё одно: **всегда проверяй статус-коды `curl`'ом**, а не только глазами
в браузере. Браузер показывает страницу и не сообщает, что за код пришёл.
Целый класс ошибок виден только через `curl -w '%{http_code}'`.

### 8.2. Ловушка `useSearchParams` в эффекте (реальный бесконечный цикл)

Ещё один найденный на практике баг — на этот раз не про статус-коды, а про
производительность. В консоли сервера появилось вот это, раз в секунду:

```
GET /?search=%D1%8F%D1%89%D0%B8%D0%BA 200 in 18ms
GET /?search=%D1%8F%D1%89%D0%B8%D0%BA 200 in 19ms
GET /?search=%D1%8F%D1%89%D0%B8%D0%BA 200 in 24ms
...и так до перезагрузки вкладки
```

Страница запрашивалась у сервера **бесконечно**, причём с одним и тем же URL.

**Причина.** В `src/components/library/SearchBar.tsx` эффект обновлял URL
и при этом зависел от `searchParams`:

```tsx
// ❌ ИСТОЧНИК ЦИКЛА
const searchParams = useSearchParams();

useEffect(() => {
  router.replace(urlFrom(searchParams, value));
}, [value, searchParams]);        // ← вот эта зависимость
```

Что происходило по шагам:

1. Пользователь ввёл текст → дебаунс → `router.replace(новый URL)`
2. URL изменился → хук `useSearchParams()` вернул **новый объект**
3. Новый объект — изменившаяся зависимость → эффект запустился снова
4. Эффект снова поставил таймер и снова вызвал `router.replace`
5. Возврат к шагу 2 — вечно

Коварство в том, что URL на каждом круге был **один и тот же**. Мы просили
сервер отрисовать ту же самую страницу — но просили бесконечно. Снаружи
интерфейс выглядел нормально, а сервер работал вхолостую.

**Почему зависимость срабатывала, хотя «ничего не менялось».** В JavaScript
объекты сравниваются **по ссылке**, а не по содержимому:

```js
{} === {}                                    // false — разные объекты
new URLSearchParams("a=1") === new URLSearchParams("a=1")   // тоже false
"ящик" === "ящик"                            // true — строки по значению
```

`useSearchParams()` возвращает новый объект при каждом изменении URL, поэтому
React честно считал зависимость изменившейся.

**Как исправлено** (три независимых предохранителя):

1. **Главный:** чистая функция `buildSearchUrl` (`src/lib/search-url.ts`)
   возвращает `null`, если менять нечего. Компонент просто выходит:

   ```tsx
   const nextUrl = buildSearchUrl(searchParamsRef.current, pathname, value);
   if (nextUrl === null) return;          // ← разрывает цикл
   ```

2. **В зависимостях — только скалярные значения.** Вместо объекта
   `searchParams` используется строка `searchParams.get("search") ?? ""`.
   Строки сравниваются по значению, ложных срабатываний нет. Сам объект
   доступен через `ref`, который обновляется после каждого рендера
   и не участвует в зависимостях.

3. **Защита от внешних изменений** через `lastWrittenRef` — чтобы отличить
   «пользователь печатает» от «нажали ссылку `сбросить`».

**Проверено тестом.** В `src/lib/search-url.test.ts` есть тест на
**идемпотентность**: применяем функцию к адресу, получаем новый адрес,
применяем ещё раз — должно вернуться `null`. Именно отсутствие этого
свойства и вызывало цикл.

```bash
bun test
# 13 pass, 0 fail
```

> **Правило, которое стоит запомнить:**
> если эффект изменяет значение, от которого сам же зависит, — это почти
> всегда бесконечный цикл. Лечится либо удалением зависимости, либо
> проверкой «если менять нечего — ничего не делай». Второй вариант надёжнее.
>
> И второе правило: **сравнивай по значению, а не по ссылке**, когда речь
> о примитивах. `"ящик" === "ящик"` всегда `true`, а `{} === {}` — всегда
> `false`.

## 11. Частые ошибки (и как их узнать)

| Симптом | Причина | Что делать |
| --- | --- | --- |
| `Module not found: Can't resolve 'fs'` | серверный модуль импортирован в клиентский компонент | убрать `"use client"` выше по дереву или перенести логику в `lib` и вызывать через API |
| `useState only works in a Client Component` | используешь хук в серверном компоненте | добавить `"use client"` первой строкой |
| `params should be awaited` | забыл `await` перед `params`/`searchParams` | `const { id } = await params` |
| `Event handlers cannot be passed to Client Component props` | передал функцию из серверного компонента в клиентский | передавай данные, а не функции |
| `useSearchParams() should be wrapped in a suspense boundary` | нет `<Suspense>` вокруг | обернуть |
| `Hydration failed` | HTML с сервера не совпал с тем, что отрисовал клиент | типичная причина — обращение к `localStorage`/`Date.now()` при первом рендере; читай их в `useEffect` |
| `You're importing a component that needs "next/headers"` | серверный API в клиентском компоненте | вынести в серверный |
| Страница отдаёт 404, хотя файл есть | папка начинается с `_` | переименовать |

Про гидратацию стоит сказать отдельно. **Гидратация** — это момент, когда
React «оживляет» уже отрисованный сервером HTML. Если HTML с сервера и первый
рендер в браузере не совпадают, React ругается и перерисовывает всё заново.

Классический источник проблемы — чтение `localStorage` прямо при
инициализации состояния:

```tsx
// ❌ ПЛОХО: на сервере localStorage нет → значение по умолчанию,
//          в браузере другое → несовпадение разметки
const [volume, setVolume] = useState(Number(localStorage.getItem("volume")));

// ✅ ХОРОШО: сервер и браузер рисуют одно и то же, а настройка
//            подтягивается после первого рендера
const [volume, setVolume] = useState(1);
useEffect(() => {
  const saved = Number(readLocalStorage("pmp.volume"));
  if (Number.isFinite(saved)) setVolume(saved);
}, []);
```

Именно поэтому в `src/components/player/player-context.tsx` чтение
сохранённых настроек вынесено в отдельный `useEffect`.

## 12. Шпаргалка

| Нужно | Как |
| --- | --- |
| Новая страница | папка + `page.tsx` |
| Новый API | папка в `src/app/api/` + `route.ts` |
| Общая рамка | `layout.tsx` |
| Экран загрузки | `loading.tsx` (см. §8.1 — у нас его нет осознанно) |
| Обработка ошибок | `error.tsx` |
| Динамический URL | папка `[id]`, читать через `await params` |
| Параметры-фильтры | `searchParams` (тоже Promise) |
| Читать базу | прямо в серверном компоненте или в `lib/db` |
| Изменить данные | Route Handler + `router.refresh()` |
| Переход внутри сайта | `<Link href>` |
| Переход из кода | `useRouter()` |
| Сделать компонент интерактивным | `"use client"` первой строкой |
| Не кэшировать страницу | `export const dynamic = "force-dynamic"` |
| Метаданные | `export const metadata` / `export const viewport` |
| Типы маршрутов | `PageProps<"/путь">`, `LayoutProps<"/путь">` |
