## 0. Главное одним абзацем

Это **учебный** персональный музыкальный плеер. Хозяин проекта учится:
TypeScript, JavaScript, React, Next.js, Bun. Его основной профессиональный курс —
SQL / ClickHouse / dbt / BI, а это проект «для отдушины». Поэтому **код важнее
фич**: понятный, прокомментированный, объяснённый код ценнее, чем ещё одна
функция. Всё, что сгенерировано, должно быть понятно человеку, который читает
этот код впервые.

## 2. Рантайм Bun — самое важное правило

Приложение обращается к базе через модуль **`bun:sqlite`**, которого в Node.js
не существует. Поэтому Next.js обязан запускаться **рантаймом Bun**:

```bash
bun --bun run dev      # ✅ правильно
bun run dev            # ❌ это скрипт из package.json, он уже содержит --bun
node node_modules/.bin/next dev   # ❌ упадёт на первом обращении к базе
```

Скрипты в `package.json` уже содержат `bun --bun` — используй `bun run <script>`.

Проверка, что всё в порядке: `typeof Bun !== "undefined"` внутри Route Handler.
Если видишь ошибку `Cannot find module 'bun:sqlite'` — сервер запущен на Node.

Типы для Bun-модулей даёт пакет `@types/bun` (уже в devDependencies).

## 3. Комментарии — главная ценность проекта

**Пиши комментарии на русском языке. Подробно. «Разжёванно».**

Ожидаемый уровень объяснения — как для человека, который впервые видит этот
концепт, но при этом не считай читателя глупым: он взрослый специалист в данных.

Для каждой нетривиальной вещи объясняй по схеме:

1. **ЧТО** это такое (простыми словами).
2. **ЗАЧЕМ** это нужно здесь (какую проблему решает).
3. **КАК** работает (механика).
4. **ПРИМЕР** (код или псевдокод).

Дополнительно:

* Рядом с SQL-запросом на Drizzle пиши в комментарии **эквивалентный SQL**
  (`-- SQL: SELECT * FROM tracks WHERE ...`). Хозяин проекта учит SQL и должен
  видеть, во что превращается код.
* Если есть подводный камень, типичная ошибка или альтернативный подход —
  напиши об этом прямо в комментарии.
* Комментарии вида `// увеличиваем i` над `i++` — мусор. Комментируй СМЫСЛ,
  а не очевидную механику.
* Файл начинай с шапки: что это, зачем, какие ключевые идеи.
* Для особо важных файлов (`src/components/player/player-context.tsx`,
  `src/app/api/tracks/[id]/stream/route.ts`, `src/lib/db/client.ts`) —
  комментариев должно быть не меньше, чем кода.

## 4. Структура и раскладка

```
src/app/          маршруты (App Router): page.tsx, layout.tsx, route.ts
src/app/api/      Route Handlers — HTTP-API приложения
src/components/   React-компоненты, сгруппированные по смыслу
src/lib/          бизнес-логика: db, scanner, конфиг, утилиты
src/hooks/        (при необходимости) собственные React-хуки
docs/             учебные материалы (см. раздел 8)
drizzle/          SQL-миграции, сгенерированные drizzle-kit
data/             база и обложки (в git НЕ коммитится)
music/            музыка пользователя (в git НЕ коммитится)
```

Правила:

* **Логика — в `src/lib`, а не в компонентах.** Компонент отвечает за показ и
  взаимодействие; запросы к базе и работа с файлами живут в `lib`.
* **`page.tsx` и `route.ts` не могут лежать в одной папке** — это ошибка Next.js.
* Файлы в `src/lib` — `kebab-case` (`track-queries.ts`),
  компоненты — `PascalCase` (`TrackList.tsx`).
* Импорты только через алиас: `import { db } from "@/lib/db/client"`.
  Никаких `../../../`.
* Один компонент — один файл. Исключение: тесно связанные мелкие компоненты
  (например `TrackRow` внутри `TrackList.tsx`) — тогда объясни это в комментарии.

## 5. Server Components и Client Components

* **По умолчанию — серверный компонент.** Он может читать базу напрямую.
* Директива `"use client"` — только когда реально нужны хуки (`useState`,
  `useEffect`) или обработчики событий (`onClick`).
* **Данные для первой отрисовки берём на сервере** (Server Component → `lib/db`),
  а не через `fetch` к собственному API. Свой API вызываем только из браузера.
* После мутации на клиенте — `router.refresh()`, а не `window.location.reload()`.
  Перезагрузка убьёт воспроизведение музыки.
* Список треков **не должен** подписываться на постоянно меняющееся состояние.
  В проекте для этого три отдельных контекста (`usePlayerActions`,
  `usePlayerTrack`, `usePlayerTimeline`) — не сливай их в один.
* `params` и `searchParams` в Next.js 15+ — это **Promise**, их нужно `await`.

## 6. Работа с базой данных

* Схема живёт **только** в `src/lib/db/schema.ts`. Меняешь схему — генерируешь
  миграцию:
  ```bash
  bunx drizzle-kit generate
  ```
  Полученный SQL-файл в `drizzle/` **коммитится в git**.
* Руками таблицы в базе не правим. Никаких `ALTER TABLE` из консоли —
  иначе следующий `migrate()` разъедется со схемой.
* Миграции применяются автоматически при старте (`src/lib/db/client.ts`).
* Все запросы — **только** через `src/lib/db/*.ts`. Ни один компонент и ни один
  Route Handler не пишет SQL сам.
* Значения в SQL передаются **параметрами** (`eq(...)`, `inArray(...)`),
  а не склейкой строк. Склейка = SQL-инъекция.
* Не забывай про проблему N+1: вместо запроса в цикле — один запрос с `IN (...)`.
* `data/` — это данные, а не код. Их можно удалить и пересоздать сканированием.
* Музыкальные файлы — источник правды. База — производный индекс.

## 7. Оформление (дизайн-система)

Проект называется **ORPHEUS.BBS**. Стилистика — гибрид древнегреческой
античности и хакерской культуры девяностых (отсылка к фильму «Хакеры», 1995).
Позже на этой же основе будет сайт-резюме, поэтому стиль должен быть
переносимым.

### 7.1. Три темы, переключаемые в интерфейсе

| id | Название | Идея |
| --- | --- | --- |
| `aegean` | Эгейское море | мрамор, золото, ночная синева (по умолчанию) |
| `oracle` | Дельфийский оракул | янтарный монохром |
| `gibson` | Гибсон | фосфорно-зелёный CRT |

Тема хранится в **cookie** `orpheus_theme`, читается на сервере
в `src/app/layout.tsx` и попадает в атрибут `<html data-theme="…">`.
Переключатель — `src/components/settings/ThemeSwitcher.tsx`.

**Никогда не используй `localStorage` для темы**: сервер о нём не знает,
и при загрузке будет вспышка чужого оформления (FOUC) плюс риск ошибки
гидратации.

### 7.2. Роли вместо цветов — главное правило

Компоненты **не знают конкретных цветов**, только роли. Токены объявлены
в `@theme` в `src/app/globals.css`, значения задают файлы в `src/themes/`:

| Токен | Роль |
| --- | --- |
| `canvas` / `surface` / `surface-2` | фон страницы / панелей / вложенный |
| `ink` / `ink-muted` / `ink-faint` | текст: основной / второстепенный / служебный |
| `line` / `line-strong` | **только рамки**, никогда текст |
| `accent` | главное действие (кнопки, активные элементы) |
| `accent-2` / `accent-3` | предупреждение / ссылки |
| `alert` | ошибки |
| `on-accent` | текст поверх акцентного фона |

* **Хардкод цветов в компонентах запрещён** (`text-[#e8b53f]` — нельзя).
* Цвета группы `line` — только для `border-*`. Для текста — три уровня `ink`.
  Именно на этом сломалось первое оформление: подсказка по клавишам была
  окрашена цветом рамки и давала контраст 1.3:1.
* Любой текст обязан проходить WCAG AA: **≥ 4.5:1** к фону. Проверяй расчётом,
  а не «на глаз».

### 7.3. Шрифт

**Fira Mono** через `next/font/google`, subsets `latin`, `cyrillic`, `greek`.
Начертания: 400 (текст), 500 (акценты), 700 (заголовки).

Почему не IBM Plex Mono: у него **нет греческого сабсета** в наборе Google
Fonts, и греческие буквы названия отрисовались бы запасным шрифтом.
Перед сменой шрифта проверяй в типах `next/font`, какие subset-ы доступны.

### 7.4. Классы

`term-panel`, `term-title`, `term-btn`, `term-btn-danger`, `term-btn-active`,
`term-input`, `track-row`, `term-range`, `cursor-blink`, `glow`, `ascii-rule`,
`motif-meander`, `motif-frieze`, `fade-up`.

Прежде чем писать новые стили — проверь, нет ли уже подходящего класса.
`motif-meander` — греческий орнамент через `mask-image` с `currentColor`,
поэтому красится любым классом `text-*`. Используй его как декоративный
разделитель, всегда с `aria-hidden="true"`.

### 7.5. Доступность — не опциональна

* `prefers-reduced-motion` отключает мерцание и анимации — обязательно.
* У иконочных кнопок — `aria-label`; у переключателей — `aria-pressed`
  или `aria-checked`; у ошибок — `role="alert"`.
* Интерактивные не-кнопки получают `role="button"` + `tabIndex` + Enter/пробел.
* Различие состояний дублируй **формой**, а не только цветом (дальтонизм).
* Видимый фокус с клавиатуры (`:focus-visible`) обязателен везде.

### 7.6. Имя проекта

Имя, слоганы и служебные тексты живут в `src/config/branding.ts` —
**в одном месте**. Никогда не пиши `"ORPHEUS.BBS"` строкой в компоненте:
используй `BRANDING.name`. Переименование проекта должно быть правкой
одной строки.

## 9. Проверка результата (обязательно перед ответом «готово»)

1. `bun run typecheck` — типы должны сходиться без ошибок.
2. `bun run lint` — без новых предупреждений.
3. `bun run build` — production-сборка проходит.
4. Запустить dev-сервер и реально дёрнуть изменённое:
   ```bash
   curl -s http://127.0.0.1:3000/api/tracks
   curl -s -I -H "Range: bytes=0-1023" http://127.0.0.1:3000/api/tracks/1/stream
   ```
   Ожидаемо: `206 Partial Content` и заголовок `Content-Range`.
5. Если менял UI — открыть страницу и убедиться, что она отдаёт 200 и рендерит
   данные, а не пустую оболочку.

Никогда не сообщай «сделано», не проверив хотя бы пункты 1 и 4.

## 10. Особенности окружения
