# 14. Деплой: как вывести плеер наружу

> Продолжение главы [10-docker.md](10-docker.md): там разобрано **что такое образ,
> контейнер, том и `docker compose up -d`**. Здесь — следующее: **как сделать так, чтобы
> плеером можно было пользоваться не только за тем же компьютером.**

**Деплой** — перенос рабочего приложения туда, где им будут пользоваться, плюс всё вокруг:
доступ, домен, HTTPS, бэкапы, обновления. Упаковка у нас уже сделана (`Dockerfile` +
`docker-compose.yml`), поэтому решаем три вопроса: **куда** ставить, **как** закрыть доступ
и **как** это обслуживать.

> **Честно о проверенном.** Всё про файлы проекта (сервис `orpheus-bbs`, порт 3000, пути
> `/music` и `/data`, переменные `STREAM_TOKEN` / `MUSIC_DIR` / `DB_PATH` / `COVERS_DIR`,
> файлы `music.db`, `music.db-wal`, `music.db-shm`, миграции при старте) взято из реального
> кода. Поведение `NEXT_PUBLIC_STREAM_TOKEN` **проверено отдельной сборкой** (сюрприз, см.
> 6.1). Цифры по памяти (раздел 9) — **ориентиры**, а не замеры на твоей машине. Команды
> Ubuntu/Docker стандартные, но на VPS я их не прогонял — у меня его нет.

## 1. Три сценария деплоя

| | **А. Свой ноутбук** | **Б. Домашний сервер в Wi-Fi** | **В. VPS в интернете** |
| --- | --- | --- | --- |
| **Что нужно** | Docker на этой же машине | + вторая машина, работающая постоянно (старый ноутбук, мини-ПК, Raspberry Pi) | + VPS с публичным IP, домен, понимание прокси и TLS |
| **Кто слушает** | только ты | ты, телефон, планшет, ТВ — всё в твоей сети | ты из любой точки мира |
| **Музыка рядом с базой** | да | да, на диске сервера | **нет**, её надо заливать (4.7) |
| **HTTPS / домен** | не нужны | не нужны, хватает IP | **обязателен** |
| **Стоимость** | 0 | 0 (электричество) | ~3–6 € / мес |
| **Сложность** | ★ | ★★ | ★★★★ |
| **Кто видит проект** | никто | **соседи по Wi-Fi** (если не закрыть) | **весь интернет** (если не закрыть) |
| **Что ломается** | ничего | IP машины поменялся после перезагрузки | кончился диск, вышел трафик, сломался сертификат |

**Для личного плеера правильный ответ почти всегда — Б:** бесплатно, музыка рядом, по
локальной сети быстрее, чем через интернет, TLS не нужен. Сценарий В оправдан одним:
**«слушаю музыку вне дома и готов это обслуживать»**.

## 2. Сценарий А: локальный запуск

Подробности — в [10-docker.md](10-docker.md), здесь минимальный повтор:

```bash
# Из корня проекта (там же, где Dockerfile и docker-compose.yml)
docker compose up -d          # собрать образ и запустить в фоне
docker compose logs -f        # ждём строку: [player] SQLite открыта: /data/music.db
```

Дальше `http://localhost:3000` и один раз кнопка **«СКАНИРОВАТЬ»** — приложение не сканирует
папку само при старте.

Важно понять сразу: Next.js слушает `0.0.0.0` (все интерфейсы), а в compose стоит
`"3000:3000"`. Значит, **плеер уже виден всей домашней сети**, просто ты об этом не думал.
Отсюда растёт сценарий Б.

## 3. Сценарий Б: домашний сервер в локальной сети

### 3.1. IP машины и почему адрес «уезжает»

Локальная сеть (LAN) — твой роутер и всё, что к нему подключено. Внутренние адреса
(`192.168.x.x`, `10.x.x.x`) **из интернета не видны**, а роутер выдаёт их по DHCP, то есть
«в аренду».

```bash
ip -4 addr show | grep inet    # Linux: все IPv4-адреса и маски
hostname -I                    # Linux: только адреса, коротко
ipconfig getifaddr en0         # macOS, интерфейс Wi-Fi
```

Обычно это что-то вида `192.168.1.42/24`: с телефона открываешь `http://192.168.1.42:3000`.

> **Подводный камень: адрес меняется.** После перезагрузки DHCP может выдать другой адрес,
> закладка в телефоне сломается, и покажется, что «всё сломалось». **Лечение:** в настройках
> роутера привязать MAC сервера к постоянному IP (Static lease / DHCP reservation) — это
> надёжнее статического IP на самой машине. Альтернатива — mDNS-имя
> `http://orpheus.local:3000` (macOS и Linux-десктопы «из коробки», на Android нестабильно).

### 3.2. Плеер доступен соседям — что делать

Порт проброшен наружу, поэтому **любой в твоём Wi-Fi (гость, сосед) может открыть библиотеку
и скачать музыку**. Токен интерфейс, плейлисты и историю не закрывает.

**Способ 1, строгий:** не публиковать порт наружу — `ports: ["127.0.0.1:3000:3000"]`.
Снаружи не достучится никто, но и с телефона не послушать — для домашнего сервера не годится.

**Способ 2, наш:** токен на аудиопоток. В `docker-compose.yml`:

```yaml
    environment:
      # ... остальное как было ...
      STREAM_TOKEN: "длинная-случайная-строка"
      NEXT_PUBLIC_STREAM_TOKEN: "длинная-случайная-строка"   # значение ДОЛЖНО совпадать
```

```bash
openssl rand -hex 32      # 32 случайных байта: такой токен не угадать
docker compose up -d      # применить
```

| Переменная | Кто видит | Зачем |
| --- | --- | --- |
| `STREAM_TOKEN` | только сервер | сверяет пришедшее значение (`checkAccessToken` в `src/app/api/tracks/[id]/stream/route.ts`) |
| `NEXT_PUBLIC_STREAM_TOKEN` | сервер **и браузер** | чтобы `<audio src>` подставил токен (`src/lib/stream-url.ts`) |

**Чего токен не делает:** не закрывает интерфейс, плейлисты, историю, обложки и
`POST /api/scan` (там проверки токена нет вообще). Токен в URL попадает в историю браузера и
логи сервера. Это не безопасность, а «закрыть музыку от случайного гостя».

### 3.3. Почему здесь HTTPS не нужен

HTTPS решает две задачи: **шифрование** и **подтверждение**, что ты говоришь именно с тем
сервером. Дома шифровать не от кого (трафик не выходит за Wi-Fi), подтверждать нечего (это
твоя машина), а сертификат Let's Encrypt на `192.168.x.x` **выписать невозможно** — нужен
домен с публичным IP.

**Уточнение.** `localhost` и `127.0.0.1` браузер считает «безопасным контекстом», а
`192.168.1.42` — нет. По внутреннему IP **не заработают** Service Worker (установка как PWA
с офлайном), микрофон, часть Clipboard API. **На музыку это не влияет:** `<audio>`,
Range-запросы и Media Session работают по обычному HTTP.

### 3.4. Что ещё предусмотреть дома

```bash
sudo systemctl enable --now docker   # Docker должен стартовать при загрузке ОС
sudo reboot                          # проверка: переживает ли сервер перезагрузку
docker ps                            # ждём orpheus-bbs ... Up (healthy)
```

`restart: unless-stopped` в compose уже поднимает контейнер сам. Если 3000 занят — меняй
левое число (`"8080:3000"`), **правое не трогай**: внутри контейнера всегда 3000
(`ENV PORT=3000` в `Dockerfile`).

## 4. Сценарий В: VPS в интернете

VPS — арендованный кусок железа в датацентре с публичным IP: голая Ubuntu и root по SSH.
Плюс — доступ откуда угодно и независимость от домашнего интернета; минус — **музыки там
нет**, надо платить и администрировать.

### 4.1. Что покупать

| Параметр | Минимум для запуска | Комфортно | Почему так |
| --- | --- | --- | --- |
| CPU | 1 vCPU | 2 vCPU | Приложение простаивает: читает файл и отдаёт байты. CPU грузится только на сканировании (`music-metadata` разбирает теги) |
| RAM | **1 ГБ** | **2 ГБ** | Работать хватает 1 ГБ, но **сборка образа** (`bun install` + `next build`) — самый прожорливый момент: на 1 ГБ без swap её убьёт OOM-killer |
| Диск | 10 ГБ | 25–40 ГБ | ОС ~3 ГБ, образы ~1–2 ГБ, `data/` — десятки МБ; остальное под музыку |
| Трафик | 1 ТБ/мес | — | Считается **исходящий** — то, что уходит слушателю |

**Прикидка по трафику:** mp3 320 кбит/с ≈ 40 КБ/с ≈ **2,4 МБ/мин ≈ 144 МБ/час**, FLAC ≈
400 МБ/час. 1 ТБ — это ~7000 часов mp3, столько не слушают. **Упрётся раньше заливка
библиотеки:** 20 ГБ музыки — это 20 ГБ вверх с домашнего интернета и час-два ожидания.

**Swap на слабом VPS** — спасает сборку от падения:

```bash
sudo fallocate -l 2G /swapfile    # создать файл подкачки
sudo chmod 600 /swapfile          # читает только root
sudo mkswap /swapfile             # разметить как swap
sudo swapon /swapfile             # включить сейчас
echo '/swapfile none swap sw 0 0' | sudo tee -a /etc/fstab   # и после перезагрузки
free -h                           # проверка: строка Swap не 0B
```

### 4.2. Первичная настройка и firewall

```bash
ssh root@203.0.113.10                       # пример адреса, у тебя свой
sudo apt update && sudo apt upgrade -y      # обновить систему сразу после покупки
sudo apt install -y ca-certificates curl git rsync ufw sqlite3
adduser august && usermod -aG sudo august   # дальше работать от обычного пользователя
ssh-copy-id august@203.0.113.10             # (на своём компьютере) вход по ключу без пароля
```

```bash
sudo ufw allow OpenSSH     # 22 — иначе потеряешь доступ к серверу!
sudo ufw allow 80/tcp      # HTTP: нужен Caddy для проверки домена и редиректа
sudo ufw allow 443/tcp     # HTTPS
sudo ufw enable
sudo ufw status verbose    # проверить правила
```

**Порта 3000 в этом списке быть не должно** — наружу смотрит только Caddy.

### 4.3. Установка Docker и docker compose

В репозиториях Ubuntu лежит устаревший `docker.io`, поэтому подключаем официальный
репозиторий Docker:

```bash
# 1. Убрать возможные старые версии, чтобы не конфликтовали
sudo apt remove -y docker.io docker-doc docker-compose podman-docker containerd runc 2>/dev/null || true

# 2. GPG-ключ репозитория Docker
sudo install -m 0755 -d /etc/apt/keyrings
sudo curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
sudo chmod a+r /etc/apt/keyrings/docker.asc

# 3. Подключить репозиторий (версия Ubuntu подставляется автоматически)
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo "$VERSION_CODENAME") stable" | sudo tee /etc/apt/sources.list.d/docker.list > /dev/null

# 4. Установить Docker, containerd и плагин compose
sudo apt update
sudo apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin

# 5. Чтобы не писать sudo перед каждой командой (нужно перелогиниться!)
sudo usermod -aG docker $USER

# 6. Проверка
docker --version && docker compose version && docker run --rm hello-world
```

`docker compose` (с пробелом) — это плагин Compose v2 из пакета `docker-compose-plugin`.
Старый `docker-compose` через дефис — отдельный Python-скрипт, нам не нужен.

### 4.4. Код на сервере и что с музыкой

**Сначала про git.** Сейчас в репозитории один коммит (`Initial commit from Create Next
App`), а код проекта не закоммичен — `git status` показывает кучу новых файлов. **Перед
деплоем надо закоммитить и запушить** (как — в [13-chto-dalshe.md, раздел 0.1](13-chto-dalshe.md)),
иначе на сервер нечего клонировать.

```bash
sudo mkdir -p /srv && sudo chown "$USER":"$USER" /srv
cd /srv
git clone https://github.com/твой-логин/orpheus-bbs.git
cd orpheus-bbs
```

**Почему в репозитории нет `music/` и `data/`** — обе папки в `.gitignore` (`/music/*` кроме
`music/.gitkeep`, и `/data/`): музыка весит гигабайты и у каждого своя, а `data/` — данные,
меняющиеся каждый день. Значит, после `git clone` на сервере **не будет ни одной песни**.

```bash
# ВЫПОЛНЯЕТСЯ НА ДОМАШНЕМ КОМПЬЮТЕРЕ. -a архивно (права, время), -v показывать,
# -z сжимать, --progress прогресс. СЛЕШ В КОНЦЕ: ~/Music/ — «содержимое папки».
rsync -avz --progress ~/Music/ august@203.0.113.10:/srv/orpheus-bbs/music/

# Проще, один раз (glob раскроет оболочка; в музыке есть файлы с пробелами в
# именах — вроде «ATL x Зараза x Ка тет ...mp3» — пути бери в кавычки)
scp -r ~/Music/* august@203.0.113.10:/srv/orpheus-bbs/music/
```

**`data/` переносить не нужно** (база и обложки пересоздаются сканированием), кроме случая,
когда хочешь сохранить плейлисты и историю:

```bash
docker compose stop                      # дома: остановить, чтобы WAL дописался в базу
rsync -avz ./data/ august@203.0.113.10:/srv/orpheus-bbs/data/   # копируем папку целиком
docker compose start
```

Почему нельзя копировать один `music.db` «на живую» — раздел 7.2.

### 4.5. Главный вопрос: откуда на VPS возьмётся музыка

**У VPS нет твоей музыки** — сервер стоит в датацентре с пустым диском. Варианты:

| Вариант | Что это значит | Кому |
| --- | --- | --- |
| Залить всю библиотеку | 20 ГБ = 20 ГБ трафика вверх и столько же места; домашний интернет (ADSL/4G) не выдержит | если библиотека 5–10 ГБ и интернет быстрый |
| Залить только избранное | 200–300 треков, 2–3 ГБ: дёшево и по месту, и по трафику | **оптимально:** дома вся библиотека, на VPS — любимое |
| Слушать только залитое | плеер показывает ровно то, что положил | если VPS нужен «для поездок» |
| **Не брать VPS** | дома всё работает, музыка рядом, 0 €/мес | **честный ответ для большинства** |

Ответь себе: **где я реально слушаю музыку?** и **готов ли я это обслуживать** (обновления,
бэкапы, диск, сертификат)? Если «слушаю дома» — VPS не нужен.

## 5. Домен и HTTPS: обратный прокси и Caddy

### 5.1. Зачем прокси

**Обратный прокси** — маленький веб-сервер перед приложением, принимающий весь внешний
трафик. Две задачи: **терминация TLS** (сертификат, шифрование, редирект на HTTPS —
приложению про сертификаты знать не нужно, внутри остаётся HTTP на 3000) и **один вход на
много сервисов** (наружу 80/443, прокси по имени домена решает, куда отправить; добавить
сайт-резюме = дописать десять строк конфига).

### 5.2. Домен: что сделать до Caddy

1. Купить домен.
2. В DNS создать **A-запись**: `music` (или `@`) → IP твоего VPS.
3. Проверить, что DNS разошёлся:

```bash
dig +short music.example.com    # должен напечатать IP VPS; пусто — DNS ещё не обновился
```

Caddy получит сертификат только для домена, который резолвится в этот сервер, а Let's Encrypt
при выдаче постучится **снаружи** — порты 80/443 должны быть открыты.

### 5.3. Полный `Caddyfile` для этого проекта

Файл `/srv/orpheus-bbs/Caddyfile`:

```text
# ГЛОБАЛЬНЫЙ БЛОК (необязательный): скобки без адреса — настройки всего сервера.
# email — аккаунт Let's Encrypt: туда придут письма о проблемах с сертификатом.
{
	email you@example.com
}

# АДРЕС САЙТА. Домен можно вписать руками или взять из окружения: Caddy
# подставляет {$ИМЯ} (задаём в docker-compose.yml) — «{$ORPHEUS_DOMAIN} {».
#
# ГЛАВНОЕ ПРО ЭТУ СТРОКУ: схему http:// писать НЕ надо — без неё Caddy сам
# включит HTTPS, сам сходит в Let's Encrypt, получит и будет продлевать
# сертификат, сам настроит редирект с http:// на https://.
# Условие: DNS-запись готова, порты 80 и 443 открыты снаружи.
music.example.com {
	# Сжатие: HTML/JSON/JS сжимаются отлично, аудио уже сжато кодеком —
	# Caddy его не трогает, лишний CPU не тратится.
	encode zstd gzip

	# Пароль на ВЕСЬ сайт: интерфейс, API и аудио. Браузер спросит логин и будет
	# слать его с каждым запросом, в том числе когда <audio> тянет кусок файла.
	# Открытый пароль Caddy НЕ примет — только хеш:
	#   docker compose exec caddy caddy hash-password --plaintext 'мой-пароль'
	# (директива называется basic_auth с версии Caddy 2.8, раньше — basicauth)
	basic_auth {
		august $2a$14$ЗАМЕНИ_ЭТО_НА_СВОЙ_ХЕШ
	}

	# Куда перенаправлять. orpheus-bbs — имя сервиса из docker-compose.yml: в
	# общей сети Docker у сервиса есть DNS-имя, равное имени сервиса.
	# 3000 — порт, который слушает Next.js внутри контейнера.
	reverse_proxy orpheus-bbs:3000
}
```

| Строка | Что делает |
| --- | --- |
| `{ email ... }` | Глобальный блок; email регистрируется в Let's Encrypt для уведомлений |
| `music.example.com {` | **Адрес сайта.** Без схемы `http://` — значит «включи автоматический HTTPS»; именно эта строка заставляет получить сертификат |
| `encode zstd gzip` | Сжатие текстовых ответов; MP3/FLAC/JPEG пропускаются (уже сжаты) |
| `basic_auth { }` | Пароль на всё: закрывает то, что `STREAM_TOKEN` не закрывает |
| `august $2a$14$...` | Логин и **хеш** (не пароль!); `$2a$` = bcrypt, тип по умолчанию |
| `reverse_proxy orpheus-bbs:3000` | Переслать запрос в контейнер; заголовки `Range` и `Content-Range` сохраняются, поэтому частичная отдача аудио работает и через прокси |

Проверить, что Range прошёл через прокси, обязательно (см. чек-лист):

```bash
curl -o /dev/null -s -w "статус: %{http_code}\n" \
  -H "Range: bytes=0-1023" https://music.example.com/api/tracks/1/stream   # ждём 206
```

### 5.4. Обновлённый `docker-compose.yml`: добавляем Caddy

**Изменение первое** — у `orpheus-bbs` порт 3000 больше не публикуется наружу:

```yaml
  orpheus-bbs:
    # ... build, container_name, volumes, environment, restart, logging как были ...

    # БЫЛО (сценарии А/Б): порт торчал в интернет
    # ports:
    #   - "3000:3000"

    # СТАЛО: порт виден только внутри сети Docker. expose — «документация для
    # соседних контейнеров»: 3000 доступен сервису caddy, но снаружи его нет.
    # Проверка: docker ps НЕ показывает 0.0.0.0:3000->3000/tcp.
    expose:
      - "3000"

    networks:
      - orpheus-net
```

**Изменение второе** — новый сервис и общая сеть:

```yaml
  # ОБРАТНЫЙ ПРОКСИ
  caddy:
    image: caddy:2-alpine
    container_name: orpheus-caddy
    restart: unless-stopped

    # Наружу только стандартные веб-порты: 80 — проверка домена Let's Encrypt и
    # редирект на HTTPS, 443 — сам HTTPS, 443/udp — HTTP/3 (тот же HTTPS по UDP).
    ports:
      - "80:80"
      - "443:443"
      - "443:443/udp"

    volumes:
      - ./Caddyfile:/etc/caddy/Caddyfile:ro   # наш конфиг, :ro — только чтение
      # Сертификаты и состояние Caddy. Тома ИМЕНОВАННЫЕ: потеряешь — придётся
      # получать сертификаты заново, а Let's Encrypt ограничивает число выдач.
      - caddy_data:/data
      - caddy_config:/config

    environment:
      # Подставляется в Caddyfile как {$ORPHEUS_DOMAIN}; если переменной нет
      # в .env — берётся значение после :-.
      ORPHEUS_DOMAIN: ${ORPHEUS_DOMAIN:-music.example.com}

    networks:
      - orpheus-net
    depends_on:
      - orpheus-bbs

# Compose и так создаёт одну сеть на весь файл, и сервисы видят друг друга по
# именам, но объявить сеть явно полезно: видно, кто с кем связан.
networks:
  orpheus-net:
    driver: bridge

# Именованные тома Caddy: переживают удаление контейнера и `docker compose down`.
volumes:
  caddy_data:
  caddy_config:
```

```bash
echo 'ORPHEUS_DOMAIN=music.example.com' >> .env   # домен в одном месте
docker compose up -d          # пересборка НЕ нужна: изменился только compose
docker compose logs -f caddy  # ждём "certificate obtained successfully"
docker ps                     # у orpheus-bbs в PORTS пусто; у caddy — 80 и 443
```

> **Что изменилось для проверок.** До Caddy локальные тесты делались как
> `curl http://127.0.0.1:3000/...` прямо с сервера. После перехода на `expose` порт на хосте
> больше не слушается, поэтому проверять теперь нужно либо через домен
> (`https://music.example.com/...`), либо изнутри контейнера:
> `docker compose exec orpheus-bbs wget -q -O - http://127.0.0.1:3000/api/tracks`.

### 5.5. Альтернативы: nginx + certbot, Traefik

* **nginx + certbot** — самый популярный, гора готовых конфигов, встретишь на работе. Минусы:
  сертификаты продлевает отдельный таймер; конфиг на 40 строк с `proxy_set_header`; грабли со
  стримингом.
* **Traefik** — конфиг метками прямо в compose, сам находит контейнеры. Минусы: своя система
  понятий (entrypoints, providers, middlewares), для одного сервиса — из пушки по воробьям.
* **Caddy** (наш выбор) — сертификаты получаются и продлеваются **сами**, конфиг ~10 строк,
  Range и веб-сокеты работают без плясок. Минус один: примеров в интернете меньше, чем у nginx.

Поэтому в этой главе нет ни `certbot renew`, ни крона для сертификатов.

## 6. Безопасность при выходе в интернет

Если плеер смотрит в интернет, а ты ничего не сделал, **музыка и вся библиотека доступны
любому, кто знает адрес**. Адреса сканируют боты круглосуточно, домены из DNS попадают в
публичные списки за часы.

### 6.1. Что защищает, а что нет

| Механизм | Что закрывает | Что НЕ закрывает |
| --- | --- | --- |
| `STREAM_TOKEN` | только аудиопоток `/api/tracks/:id/stream` | интерфейс, плейлисты, историю, обложки, `POST /api/scan` |
| **Basic Auth в Caddy** | **весь сайт целиком** | ничего, кроме доступа |
| Ограничение по IP | всё, но только для «своих» адресов | из поездки не зайти; домашний IP меняется |
| fail2ban | перебор по SSH | сам веб не защищает |

**Про `STREAM_TOKEN` важно знать три вещи.** (1) **Токен в URL попадает в логи**: при
включённых access-логах строка `GET /api/tracks/12/stream?token=abc...` окажется в файле
целиком (и в истории браузера). (2) **Он не заменяет авторизацию** — в
`src/app/api/tracks/[id]/stream/route.ts` прямо написано: настоящая авторизация это логин,
пароль, сессии, роли, а ТЗ просит не усложнять. (3) **Нормальной авторизации в приложении
нет вообще**: ни пользователей, ни входа, ни ролей — кто открыл сайт, тот и «хозяин», он
видит историю, плейлисты и может запустить скан.

**Сюрприз с `NEXT_PUBLIC_STREAM_TOKEN` в Docker.** Next.js подставляет значения с префиксом
`NEXT_PUBLIC_` **в момент сборки** (документация лежит локально:
`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`). Я проверил это
отдельной сборкой: с заданной переменной значение **вклеилось** в клиентский JS строкой, без
неё в бандле осталось обращение к `process.env.NEXT_PUBLIC_...`, которое в браузере даёт
`undefined` — то есть пустую строку.

А в Docker сборка идёт на `docker compose build` (стадия `builder` в `Dockerfile`), тогда как
`environment:` из compose применяется только при **запуске**. Значит, если просто
раскомментировать `NEXT_PUBLIC_STREAM_TOKEN` и сделать `docker compose up -d`, браузер токена,
скорее всего, **не получит** и аудио начнёт отдавать 401. В `docs/10-docker.md` этот момент
описан оптимистичнее; полную проверку в Docker я не делал, поэтому проверь сам:

```bash
# Если команда что-то нашла — значение НЕ вклеилось, до браузера токен не дошёл
docker compose exec orpheus-bbs sh -c "grep -rl 'NEXT_PUBLIC_STREAM_TOKEN' .next/static | head"
# Живая проверка: открой сайт, F12 → Network → запрос /stream → есть ли ?token=...
```

Если токен всё-таки нужен, его передают **на этап сборки**:

```dockerfile
FROM oven/bun:1-alpine AS builder
# ARG — переменная, передаваемая только во время сборки (build.args в compose).
# ENV делает её обычной переменной окружения, которую увидит next build.
ARG NEXT_PUBLIC_STREAM_TOKEN=""
ENV NEXT_PUBLIC_STREAM_TOKEN=$NEXT_PUBLIC_STREAM_TOKEN
```

```yaml
    build:
      context: .
      dockerfile: Dockerfile
      args:
        NEXT_PUBLIC_STREAM_TOKEN: ${NEXT_PUBLIC_STREAM_TOKEN:-}   # значение из .env
```

Минус: **токен становится частью образа** — кто получит образ, увидит его внутри. Поэтому для
интернета я советую **другое**: оставить `STREAM_TOKEN` выключенным и защищать всё через Basic
Auth в Caddy — тогда токен не нужен вовсе, браузер один раз спросит логин и дальше будет
присылать его и для аудио.

### 6.2. Обязательные меры

**1. Basic Auth на весь сайт** — показан в 5.3. Пароль длинный и уникальный:

```bash
docker compose exec caddy caddy hash-password --plaintext 'длинный-пароль-из-менеджера'
# вставь строку ($2a$14$...) в Caddyfile вместо заглушки, затем:
docker compose restart caddy
```

**2. Порт 3000 не публиковать** — в compose `expose`, а не `ports`. Проверка: `docker ps` не
показывает `0.0.0.0:3000->3000/tcp`, а `curl http://IP-сервера:3000` не отвечает.

**3. Firewall** — открыты только 22, 80, 443 (см. 4.2).

**4. Ограничение по IP** — дополнительный слой, если слушаешь из дома:

```text
# в Caddyfile, внутри блока сайта, ПЕРЕД reverse_proxy
# @notmine — именованный матчер: «всё, что НЕ с моего адреса»
@notmine not remote_ip 203.0.113.55
respond @notmine "Доступ только с разрешённых адресов" 403
```

Домашний IP у большинства провайдеров динамический: как единственная защита — плохо, как
дополнение к Basic Auth — хорошо.

**5. fail2ban** — защита от перебора; по умолчанию сторожит SSH, а не веб:

```bash
sudo apt install -y fail2ban && sudo systemctl enable --now fail2ban
sudo fail2ban-client status sshd    # сколько раз банили по SSH
```

Чтобы он банил за перебор Basic Auth, нужны access-логи Caddy и свой фильтр под них —
**этого я в проекте не настраивал и не проверял**. С длинным паролем перебор Basic Auth
практически нереален и без fail2ban.

**6. Про SSH** (это важнее веб-защиты — SSH взламывают чаще всего):

```bash
# Запретить вход по паролю, оставить только ключи.
# СНАЧАЛА убедись, что вход по ключу работает, иначе потеряешь доступ!
sudo sed -i 's/^#\?PasswordAuthentication.*/PasswordAuthentication no/' /etc/ssh/sshd_config
sudo systemctl restart ssh
```

**7. Обновлять образы** раз в месяц — в них приходят исправления уязвимостей:

```bash
docker compose pull caddy      # свежий образ Caddy из реестра
docker compose build           # пересобрать наш образ (свежий oven/bun + зависимости)
docker compose up -d
docker image prune -f          # убрать висячие слои, чтобы не рос диск
```

## 7. Бэкапы

Самая скучная и самая важная часть деплоя: **диск умирает без предупреждения, а плейлисты и
история существуют только в одном файле.**

### 7.1. Что бэкапить, а что нет

```
/srv/orpheus-bbs/
├── data/
│   ├── music.db        ← БЭКАПИТЬ. tracks, playlists, playlist_tracks,
│   │                     play_history, playback_state (см. src/lib/db/schema.ts)
│   ├── music.db-wal    ← БЭКАПИТЬ ВМЕСТЕ С БАЗОЙ: свежие изменения, ещё не
│   │                     перенесённые в music.db
│   ├── music.db-shm    ← разделяемая память WAL (пересоздаётся, но копировать проще)
│   └── covers/         ← по желанию: восстановимы сканированием, но это долго
└── music/              ← НЕ НАДО: это источник правды, он и так на диске
```

| Что | Бэкапить? | Почему |
| --- | --- | --- |
| `data/music.db` (+ `-wal`, `-shm`) | **Обязательно** | Плейлисты, историю, позиции «продолжить слушать» из mp3 восстановить **невозможно** |
| `data/covers/` | По желанию | Восстанавливаются сканированием, но это минуты и повторное чтение тегов |
| `music/` | Нет | Это первоисточник; его бэкап = копия всей библиотеки (нужен лишь если записи уникальны) |
| `Caddyfile`, `docker-compose.yml`, `.env` | Да, они крошечные | Конфигурация: без неё после переустановки придётся всё вспоминать |

База сейчас крошечная: в этом репозитории `data/music.db` — 64 КБ при трёх треках. Даже
библиотека на тысячи песен даёт десятки мегабайт, так что **причины не делать бэкап нет**.

### 7.2. Почему нельзя просто скопировать файл базы

В `src/lib/db/client.ts` при открытии базы выполняется `PRAGMA journal_mode = WAL`.
**WAL (Write-Ahead Logging)** означает: изменения пишутся сначала в `music.db-wal`, и лишь при
контрольной точке попадают в `music.db`. Пока приложение работает, часть свежих данных лежит
**только в WAL**, а сам `music.db` может быть пойман в середине записи. Наивный
`cp data/music.db backup.db` даёт либо устаревшую копию (последние плейлисты остались в WAL),
либо несогласованный файл. `docs/10-docker.md` советует останавливать контейнер — это
работает, но мешает автоматизации. Правильные способы:

**1) `sqlite3 .backup` (лучший):** встроенный online backup специально сделан для копирования
**работающей** базы и корректно учитывает WAL.

```bash
sudo apt install -y sqlite3    # в контейнере его нет: там Alpine и только Bun
sqlite3 /srv/orpheus-bbs/data/music.db ".backup '/srv/orpheus-bbs/backups/music-$(date +%F).db'"
sqlite3 /srv/orpheus-bbs/backups/music-$(date +%F).db "PRAGMA integrity_check;"   # ждём "ok"
```

**2) `VACUUM INTO`** — обычный SQL, тоже безопасен на живой базе и попутно пересобирает файл
без «дыр» (копия часто меньше). Нюанс: откажется писать в существующий файл — имя должно быть
новым.

```bash
sqlite3 /srv/orpheus-bbs/data/music.db "VACUUM INTO '/srv/orpheus-bbs/backups/music.db';"
```

**3) Остановить и скопировать** — проще понять, но приложение недоступно:

```bash
cd /srv/orpheus-bbs
docker compose stop                        # при остановке SQLite дописывает WAL в основу
cp -a data "backups/data-$(date +%F_%H%M)" # теперь обычное копирование безопасно
docker compose start
```

> Версии SQLite у `sqlite3` на хосте и `bun:sqlite` в контейнере — разные сборки. На Ubuntu
> 24.04 стоит 3.45, этого достаточно. Если утилита скажет `file is not a database` на живой
> базе, версии разошлись: обнови `sqlite3` или используй способ 3.

### 7.3. Скрипт бэкапа с ротацией (cron)

`/srv/orpheus-bbs/scripts/backup.sh`:

```bash
#!/usr/bin/env bash
# =============================================================================
# backup.sh — БЭКАП БАЗЫ И ОБЛОЖЕК ORPHEUS.BBS (запускается по cron).
# 1) согласованная копия базы (sqlite3 .backup — безопасно на живой базе)
# 2) проверка копии на целостность (PRAGMA integrity_check)
# 3) архив обложек   4) удаление копий старше KEEP_DAYS дней
# =============================================================================

# Строгий режим: -e выйти при любой ошибке, -u ругаться на незаданную переменную,
# -o pipefail считать ошибкой падение любой команды в конвейере. Без этого скрипт
# может «успешно» завершиться, ничего не сделав.
set -euo pipefail

PROJECT_DIR="/srv/orpheus-bbs"
DB_FILE="$PROJECT_DIR/data/music.db"
COVERS_DIR="$PROJECT_DIR/data/covers"
BACKUP_DIR="$PROJECT_DIR/backups"
KEEP_DAYS=14        # сколько дней хранить копии

# Дата и время в имени файла: копии не перезаписывают друг друга, а имена
# сортируются как текст — удобно чистить.
STAMP="$(date +%F_%H-%M)"
mkdir -p "$BACKUP_DIR"

# ── 1. БАЗА: .backup — online backup, безопасен при работающем приложении ────
sqlite3 "$DB_FILE" ".backup '$BACKUP_DIR/music-$STAMP.db'"

# ── 2. ПРОВЕРКА: бэкап, который никто не проверял, — это надежда, а не бэкап ─
CHECK="$(sqlite3 "$BACKUP_DIR/music-$STAMP.db" 'PRAGMA integrity_check;')"
if [ "$CHECK" != "ok" ]; then
  echo "ОШИБКА: копия базы повреждена ($CHECK)" >&2
  exit 1
fi

# ── 3. ОБЛОЖКИ: -c создать архив, -z сжать, -f имя файла ─────────────────────
if [ -d "$COVERS_DIR" ]; then
  tar -czf "$BACKUP_DIR/covers-$STAMP.tar.gz" -C "$PROJECT_DIR/data" covers
fi

# ── 4. РОТАЦИЯ: -mtime +N — «старше N суток» ─────────────────────────────────
find "$BACKUP_DIR" -maxdepth 1 -name 'music-*.db'      -mtime +"$KEEP_DAYS" -delete
find "$BACKUP_DIR" -maxdepth 1 -name 'covers-*.tar.gz' -mtime +"$KEEP_DAYS" -delete

echo "$(date '+%F %T') бэкап готов: music-$STAMP.db ($(du -h "$BACKUP_DIR/music-$STAMP.db" | cut -f1))"
```

```bash
chmod +x /srv/orpheus-bbs/scripts/backup.sh
/srv/orpheus-bbs/scripts/backup.sh    # прогнать руками ПЕРЕД тем, как доверить cron
ls -lh /srv/orpheus-bbs/backups/
crontab -e                            # и добавить строку расписания:
```

```bash
# ┌ минута (0-59)   ┌ час (0-23)   ┌ день месяца   ┌ месяц   ┌ день недели (0-7)
# 15 4 * * *  /srv/orpheus-bbs/scripts/backup.sh >> /var/log/orpheus-backup.log 2>&1
```

Читается так: **каждый день в 04:15 запустить скрипт, вывод и ошибки дописать в лог**
(`>>` — дописать, не затереть; `2>&1` — ошибки туда же). Сам лог тоже растёт: раз в месяц
подрезай его (`sudo truncate -s 0 /var/log/orpheus-backup.log`) или настрой logrotate.

### 7.4. Бэкап на том же диске — не бэкап

Смерть диска VPS убьёт и базу, и бэкапы. Минимум — унести копию за пределы сервера:

```bash
# На ДОМАШНЕМ компьютере, раз в неделю (можно в cron — он всегда под рукой):
rsync -avz august@203.0.113.10:/srv/orpheus-bbs/backups/ ~/orpheus-backups/
```

### 7.5. Восстановление из бэкапа

```bash
cd /srv/orpheus-bbs

docker compose stop                                        # 1. база должна быть закрыта
mv data/music.db "data/music.db.broken-$(date +%F_%H%M)"   # 2. страховка на всякий случай

# 3. КРИТИЧНО: удалить журналы старой базы. music.db-wal содержит изменения ДРУГОЙ
#    базы; оставив его рядом с копией, ты подсунешь SQLite чужие страницы.
rm -f data/music.db-wal data/music.db-shm

cp backups/music-2025-01-31_04-15.db data/music.db             # 4. копию на место
tar -xzf backups/covers-2025-01-31_04-15.tar.gz -C data/       # 5. вернуть обложки

docker compose start && docker compose logs -f                 # 6. ждём "[player] SQLite открыта"
curl -s http://127.0.0.1:3000/api/playlists | head -c 300      # 7. плейлисты вернулись?
curl -s http://127.0.0.1:3000/api/history   | head -c 300      #    история вернулась?
# (если Caddy уже настроен и порт 3000 закрыт на хосте — те же запросы через
#  https://music.example.com либо изнутри контейнера, см. врезку в 5.4)
```

**Правило, отличающее настоящий бэкап от воображаемого: восстановление надо проверить.**
Прогони эти шаги заранее, а не в момент аварии. Это пункт чек-листа.

## 8. Обновление версии приложения

### 8.1. Порядок действий

```bash
cd /srv/orpheus-bbs
scripts/backup.sh       # 1. бэкап перед обновлением. Всегда, даже если «ничего не меняется»
git pull                # 2. забрать новый код
docker compose build    # 3. пересобрать: bun install + next build, самая тяжёлая операция
docker compose up -d    # 4. применить: Compose пересоздаст контейнер
docker compose ps       # 5. проверить: ждём (healthy)
docker compose logs --tail=50
```

### 8.2. Почему данные не теряются

Данные лежат **не в контейнере, а в томах** — в compose это bind mount'ы:

```yaml
    volumes:
      - ./music:/music:ro      # музыка: папка на хосте
      - ./data:/data           # база и обложки: папка на хосте
```

`docker compose up -d` удаляет старый контейнер и создаёт новый, но папки `./music` и `./data`
на диске не трогает: тома переживают и пересборку образа, и `down`. Проверить самому:

```bash
ls -l data/music.db      # запомнить размер и дату
docker compose down && docker compose up -d
ls -l data/music.db      # тот же файл, та же дата изменения
```

### 8.3. Если появилась миграция БД

Отдельных действий не нужно: **миграции применяются автоматически при старте**. В
`src/lib/db/client.ts` при первом обращении к базе выполняется
`migrate(db, { migrationsFolder: path.resolve(process.cwd(), "drizzle") })`. Drizzle читает
папку `drizzle/` (скопирована в образ в `Dockerfile`) и применяет файлы, которых ещё нет в
служебной таблице `__drizzle_migrations`. Цепочка «поменял `schema.ts` →
`bunx drizzle-kit generate` → закоммитил SQL → задеплоил» заканчивается тем, что миграция
применится сама.

```bash
docker compose logs --tail=100 | grep -i -E "migrat|sqlite"
# или заглянуть в служебную таблицу прямо в контейнере:
docker compose exec orpheus-bbs bun -e "
  const { Database } = require('bun:sqlite');
  const db = new Database('/data/music.db');
  console.log(db.query('SELECT * FROM __drizzle_migrations').all());
"
```

> **Миграции применяются «только вперёд».** Файлов отката в проекте нет: если новая версия
> добавила колонку или таблицу, откат кода её не удалит. Обычно это безвредно (старый код
> просто не знает о новой колонке), но если миграция что-то переименовала или удалила, откат
> без бэкапа может сломать приложение.

### 9.1. `docker stats` — главная команда

```bash
docker stats                     # живая таблица, обновляется раз в секунду (выход — Ctrl+C)
docker stats --no-stream         # ОДИН снимок и выход — удобно для логов и скриптов
docker stats --no-stream orpheus-bbs caddy
```

```text
CONTAINER ID   NAME            CPU %    MEM USAGE / LIMIT     MEM %    NET I/O          BLOCK I/O        PIDS
a3f9c1b2d4e5   orpheus-bbs     0.35%    187.4MiB / 1.861GiB   9.83%    12.4MB / 890MB   45.2MB / 3.1MB   24
b7c2e1f0a9d8   orpheus-caddy   0.02%    21.7MiB / 1.861GiB    1.14%    890MB / 12.4MB   8.1MB / 512kB    11
```

| Колонка | Что означает | На что смотреть |
| --- | --- | --- |
| `CPU %` | Загрузка **в процентах от одного ядра** (может быть больше 100%) | В простое доли процента, на сканировании 100%+ |
| `MEM USAGE / LIMIT` | Занятая память и лимит | Здесь видно, сработал ли `mem_limit` из 9.7 |
| `MEM %` | `USAGE / LIMIT` | Не должно подходить к 100%: при упоре в лимит контейнер убьют (OOM) |
| `NET I/O` | Принято / отдано **за всё время жизни** контейнера | После часа mp3 отдача вырастет примерно на 150 МБ — норма |
| `BLOCK I/O` | Прочитано / записано на диск | Правое число растёт на сканировании (пишется база и обложки) |
| `PIDS` | Процессов внутри контейнера | Единицы-десятки; рост до сотен — плохой признак |

### 9.2. Кто ест память на всём сервере

```bash
ps aux --sort=-%mem | head -10     # топ-10 по памяти, -%mem = сортировка по убыванию
```

```text
USER   PID  %CPU %MEM     VSZ    RSS COMMAND
root   812  0.7  8.9  2145320 178432 bun server.js     ← наш Next.js на Bun
```

| Колонка | Что это | Как относиться |
| --- | --- | --- |
| `VSZ` | Virtual Set Size: **вся** виртуальная память, которую процесс зарезервировал, включая неиспользованное и отображённые файлы | Может быть в разы больше реальной. **Смотреть бессмысленно** — этим числом любят пугать |
| `RSS` | Resident Set Size: сколько физической памяти реально занято **сейчас** (в килобайтах) | **Вот на это смотреть.** Это же число `docker stats` показывает как MEM USAGE |
| `%MEM` | RSS в процентах от памяти сервера | Быстрая оценка: 8.9% от 2 ГБ ≈ 180 МБ |
| `%CPU` | Средняя загрузка CPU за время жизни процесса | Для мгновенной картины лучше `docker stats` или `htop` |

Одной фразой: **VSZ — «сколько процесс попросил виртуального адресного пространства», RSS —
«сколько он реально занял в оперативной памяти»**.

```bash
ps -o pid,rss,vsz,%cpu,comm -p 812          # один процесс подробно (812 — PID из ps выше)
ps -o rss= -p 812 | awk '{ printf "%.1f МБ\n", $1/1024 }'   # RSS в мегабайтах

# PID главного процесса контейнера на хосте — дальше работают обычные ps/htop
docker inspect -f '{{.State.Pid}}' orpheus-bbs
```

### 9.3. Если хочется копнуть в ядро: `/sys/fs/cgroup`

Память контейнера считает механизм **cgroups** — это первоисточник чисел из `docker stats`.

```bash
CID="$(docker ps -q -f name=orpheus-bbs)"
D="/sys/fs/cgroup/system.slice/docker-$CID.scope"   # путь cgroup v2 (новые Ubuntu)
cat "$D/memory.current"    # текущее потребление в байтах = MEM USAGE
cat "$D/memory.peak"       # ПИК за всю жизнь контейнера — очень полезно!
cat "$D/memory.max"        # лимит ("max" = лимита нет)
head -20 "$D/memory.stat"  # разбивка: anon (куча), file (кэш файлов), slab и т.д.
```

Если путь отличается (старые системы с cgroup v1 держат его в
`/sys/fs/cgroup/memory/docker/`), найди директорию по ID контейнера через `ls -d`. Особенно
ценна строка **`memory.peak`**: она отвечает на вопрос «сколько памяти нужно на VPS?», не
требуя сидеть перед `docker stats` в нужный момент — запусти сканирование, дождись окончания,
прочитай пик.

```bash
docker inspect -f '{{.State.Health.Status}}' orpheus-bbs   # healthy / unhealthy / starting
docker inspect orpheus-bbs | grep -i -E 'memory|cpu|pids'  # лимиты и настройки ресурсов
```

### 9.4. Системные инструменты: `htop`, `free`, `vmstat`

```bash
sudo apt install -y htop      # если ещё не стоит
htop                          # F6 сортировка, F5 дерево процессов, F10 выход

free -h
# Ключевая колонка — available: сколько памяти РЕАЛЬНО можно отдать процессам.
# Колонка free обманывает: Linux специально держит свободную память под кэш файлов
# (buff/cache) и отдаёт её при необходимости.

vmstat 1
#  r   b  swpd  free  buff  cache   si   so   bi   bo   in   cs  us sy id wa
#  r     — сколько процессов готовы выполняться (больше числа ядер = перегрузка)
#  si/so — swap in/out: если регулярно НЕ нули, памяти не хватает (это медленно!)
#  us/sy — время CPU в пользовательских/системных вызовах
#  id    — простой (чем ближе к 100, тем свободнее сервер)
#  wa    — ожидание ввода-вывода: высокая wa на сканировании = узкое место диск,
#          и это нормально при чтении тысяч файлов
```

### 9.5. Ориентиры для этого стека

Это **ориентиры порядка величины**, а не замеры на твоём сервере. Сними свои:
`docker stats --no-stream` в трёх состояниях — простой, сканирование, прослушивание.

| Состояние | Ожидаемая картина | Почему так |
| --- | --- | --- |
| Запустился, никто ничего не делает | 80–250 МБ RSS, CPU ~0% | Next.js держит в памяти серверный код, модули и соединение с SQLite; Bun на «пустом» сервере заметно экономнее Node.js |
| Слушаешь музыку | +20–80 МБ, CPU доли процента | Аудио идёт **потоком**: `createReadStream` в `stream/route.ts` читает файл кусками, а не целиком. 60-мегабайтный FLAC не превращается в 60 МБ памяти |
| Идёт сканирование | CPU до 100% на ядро, RSS растёт ступенями на 100–400 МБ, BLOCK I/O активен | `music-metadata` **разбирает файлы**: читает теги, а вложенную обложку вытаскивает целиком (это мегабайты). В `src/lib/scanner/index.ts` разбор идёт через `mapWithConcurrency` с лимитом **6 файлов одновременно** — отсюда пик памяти и CPU |
| Повторный скан без изменений | Почти не растёт | Сканер инкрементальный: сравнивает размер и mtime, неизменившиеся файлы **не читает вообще** |
| `data/` и SQLite | Единицы мегабайт | SQLite — не сервер, а **библиотека внутри процесса**: своего процесса и порта нет, кэш страниц невелик, а журнал WAL живёт на диске (`music.db-wal`), не в памяти |

**Вывод по VPS:** плееру спокойно на 1–2 ГБ, и 1 ГБ хватает даже при сканировании — впритык
становится только **сборка образа**, поэтому в 4.1 и предложен swap.

### 9.6. «Память растёт и не возвращается» — это нормально

**Самое важное предупреждение раздела.** У Bun (как у Node.js и большинства управляемых
рантаймов) память освобождается **не сразу**: рантайм берёт её у системы блоками и не отдаёт
при первом освобождении объектов, а сборщик мусора (GC) запускается по своему решению, а не
после каждой удалённой переменной. Поэтому график выглядит как **лестница**: плавный рост,
ступенька вверх, долгое плато, иногда ступенька вниз.

| Признак | Норма | Утечка |
| --- | --- | --- |
| Память **в простое** | Растёт и выходит на **плато** | Растёт монотонно и без остановки |
| После перезапуска контейнера | Возвращается к стартовой и снова выходит на плато | За сутки снова уползает вверх тем же темпом |
| После сканирования | Осталась на чуть более высоком плато | Продолжает расти между сканированиями |
| `memory.peak` | Стабильный | Каждые сутки новый и выше |
| За час vs за сутки | За час «выросла» на 100 МБ и остановилась | За сутки выросла в разы |

**Проверять надо тренд, а не минуту:**

```bash
# Снимок раз в час (добавь в cron), потом посмотреть через сутки:
echo "$(date '+%F %T') $(docker stats --no-stream --format '{{.MemUsage}}' orpheus-bbs)" \
  >> ~/orpheus-memory.log
cat ~/orpheus-memory.log
```

Если через сутки простоя память стоит на одном уровне (пусть и выросла за первые часы) — **это
не утечка**. Если растёт линейно всю ночь — искать причину, а перезапуск по расписанию
использовать только как временный костыль. (Разбор утечек глубже — `bun --inspect`, heap
snapshots — тема отдельной главы.)

### 9.7. Как ограничить ресурсы контейнера

На слабом VPS смысл лимитов простой: **чтобы приложение не утащило весь сервер** (на
сканировании Next.js может занять всю память, и тогда OOM-killer убьёт что-нибудь ещё,
например твой SSH-сеанс).

```yaml
  orpheus-bbs:
    # ... остальное как было ...

    # ЛИМИТЫ, ПОНЯТНЫЕ COMPOSE (работают без swarm-режима):
    mem_limit: 768m      # верхняя граница памяти; при упоре в неё процесс убьют
    cpus: 1.0            # максимум одно ядро ("0.5" — половина ядра)
    pids_limit: 256      # максимум процессов/потоков — защита от «форка-бомбы»

    # АЛЬТЕРНАТИВА В СТИЛЕ SWARM (современный Compose тоже понимает):
    # deploy:
    #   resources:
    #     limits:
    #       memory: 768m
    #       cpus: "1.0"
```

**Проверка:** в `docker stats` в колонке `MEM USAGE / LIMIT` справа должно стоять твоё значение
(например `768MiB`), а не вся память сервера. Если там вся память — эта версия Compose ключи не
подхватила, попробуй вариант `deploy.resources.limits`.

**Как подобрать цифры:** запусти сканирование и посмотри `memory.peak` (9.3), затем поставь
лимит с запасом примерно в 1,5 раза. Для 1 ГБ VPS разумно 512–768 МБ, остальное — системе,
Docker и Caddy. **Слишком маленький лимит хуже отсутствия лимита:** приложение будет падать на
сканировании.

```bash
docker ps -a          # STATUS: Exited (137) — контейнер убит по памяти
dmesg | tail -20      # в логе ядра будет строка про oom-kill
```

**А** уже работает и ничего не стоит. **Б** — правильный выбор для личного плеера (слушать с
телефона, HTTPS не нужен). **В** бери только если правда слушаешь музыку вне дома: на VPS надо
заливать музыку, а без Basic Auth в Caddy и проверенного восстановлением бэкапа деплой не
закончен. Дальше — [13-chto-dalshe.md](13-chto-dalshe.md).

**Деплой — это не «залить и забыть», а режим обслуживания:** раз в месяц обновить образы, раз в
неделю глянуть `docker stats` и `df -h`, раз в полгода проверить бэкап.
