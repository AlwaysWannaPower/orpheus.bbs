# 08. Аудио в браузере: тег `<audio>` и HTMLAudioElement

Всё, что делает наш плеер, — это разговор с одним DOM-элементом `<audio>`. Разбираем по живому коду:

| Файл | Что там |
| --- | --- |
| `src/components/player/player-context.tsx` | **сердце плеера**: сам `<audio>`, все события, очередь, громкость |
| `src/components/player/PlayerBar.tsx` | кнопки, горячие клавиши, полоса перемотки, доступность |
| `src/lib/stream-url.ts` | как собирается адрес потока (то, что попадает в `src`) |
| `src/app/api/tracks/[id]/stream/route.ts` | серверная часть: Range-запросы, ответы 200/206/416 |

```
Клик по строке трека
      │
playQueue(tracks, index)          ← обычная функция React, меняет состояние
      │
useEffect([currentTrackId])       ← срабатывает на смену трека
      ├── audio.src = buildStreamUrl(id)   ← подставили адрес
      ├── audio.load()                      ← «начинай загрузку»
      └── audio.play()                      ← «начинай звучать» (Promise!)
               │
        GET /api/tracks/5/stream → 200 или 206 (Range)
               │
        События: loadedmetadata → canplay → play → playing
               │
        Обработчики меняют состояние React → панель перерисовывается
```

**Ключевая мысль:** React **не управляет звуком**. Звуком управляет DOM-элемент; React лишь хранит
копию его состояния (`isPlaying`, `currentTime`, `duration`) и рисует интерфейс.

## 1. Тег `<audio>` и его атрибуты

```tsx
// ПОЧЕМУ ОТРИСОВАН, А НЕ СОЗДАН ЧЕРЕЗ new Audio():
// элемент в разметке виден в DevTools, им удобно управлять через ref,
// и он ведёт себя предсказуемо при серверном рендеринге.
<audio ref={audioRef} preload="metadata" />
```

### `src` — адрес файла

Мы **не пишем** `src` в разметке, а подставляем программно:

```tsx
// Смена .src запускает загрузку. Браузер сам отправит Range-запрос,
// когда пользователь начнёт перематывать.
audio.src = buildStreamUrl(currentTrackId);
audio.load();
```

Почему не `<audio src={...} />`? Потому что это **императивная операция, привязанная к событию**:
сначала сбросить состояние, потом поставить адрес, потом перемотать, потом запустить. С пропсом
React сделал бы «поставил src и ушёл думать», а нам нужны ещё три шага после. Адрес собирается
в одном месте — `src/lib/stream-url.ts`:

```ts
export function buildStreamUrl(trackId: number): string {
  const base = `/api/tracks/${trackId}/stream`;
  // encodeURIComponent нужен, если в токене окажутся символы вроде & или #,
  // которые в URL имеют специальный смысл.
  return STREAM_TOKEN ? `${base}?token=${encodeURIComponent(STREAM_TOKEN)}` : base;
}
```

> **Правило:** URL медиа собирай в отдельной функции. Понадобится CDN или префикс — править одну строку.

### `preload` — сколько качать заранее

| Значение | Что делает браузер | Когда использовать |
| --- | --- | --- |
| `none` | Ничего не качает, пока не нажмут play | Экономия трафика (агрессивная) |
| `metadata` | Качает **начало** файла: длительность, формат | **Наш случай.** Дефолт для списков |
| `auto` | Качает столько, сколько сочтёт нужным (часто весь файл) | Один короткий файл, который точно будут слушать |

**Почему это важно у нас.** В библиотеке может быть 2000 песен. С `auto` браузер попытался бы тянуть
их все — гигабайты трафика. С `metadata` запрашиваются первые килобайты.

Это **подсказка, а не приказ**: браузер учитывает ещё и свою настройку экономии трафика. Реальное
поведение проверяй в DevTools → Network. И `preload` работает только пока нет `src`.

### `controls` — почему мы его НЕ используем

```tsx
// Так НЕ делаем:
<audio ref={audioRef} src={url} controls />
```

- **Внешний вид неподконтролен** — внутри shadow DOM, стилизовать нельзя. Терминальный зелёный дизайн сломался бы.
- **Нельзя добавить своё** — кнопок «перемешать», «повтор», счётчика «3/25» там не будет.
- **Чужая логика.** Кнопка «назад» в нативной панели просто перематывает в начало, а у нас своё правило:
  играет дольше 3 секунд — в начало, иначе — предыдущий трек.

**Итог:** рисуем свой интерфейс (`PlayerBar.tsx`), `<audio>` оставляем невидимым «двигателем».

### `crossOrigin` — запросы на чужой домен

`crossOrigin="anonymous"` нужен, когда файл лежит **на другом домене** и без CORS его не отдадут,
или когда ты хочешь читать пиксели через Canvas / использовать Web Audio API (иначе холст «испортится»).
У нас он **не нужен**: файлы отдаёт свой же сервер по относительному пути `/api/...`. Понадобится,
если однажды переедешь на отдельный CDN (плюс `Access-Control-Allow-Origin` на нём).

## 2. Программный интерфейс

```tsx
// useRef даёт «коробку», которая сохраняет значение между рендерами,
// но НЕ вызывает перерисовку при изменении. Для DOM-узлов это идеально.
const audioRef = useRef<HTMLAudioElement | null>(null);
```

**Методы.** `play()` — начинает/возобновляет, возвращает **`Promise<void>`** (см. раздел 4);
`pause()` — ставит на паузу; `load()` — сбрасывает элемент и заново читает `src`;
`canPlayType("audio/flac")` — «умеешь такое играть?» → `""` / `"maybe"` / `"probably"`.

`load()` вызывается дважды в важных местах `player-context.tsx`: когда очередь опустела
(`audio.removeAttribute("src"); audio.load()` — без этого старый файл остался бы «внутри») и когда
поставлен новый `src`. Установка `src` уже запускает загрузку, но **явный `load()` гарантирует сброс буфера**.

**Свойства времени:**

| Свойство | Тип | Замечание |
| --- | --- | --- |
| `currentTime` | `number` сек. | **Чтение/запись.** Присваивание = перемотка |
| `duration` | `number` сек. | Только чтение. До метаданных — `NaN` |
| `played` | `TimeRanges` | Что уже **прослушано** |
| `buffered` | `TimeRanges` | Что уже **скачано** |

Разница `played` и `buffered` — классическая путаница. Если пользователь перемотал в середину,
`buffered` покажет два отдельных куска (0–30 сек и 300–340), и между ними — дырка.

```tsx
const seek = useCallback((seconds: number) => {
  const audio = audioRef.current;
  if (!audio) return;

  // Зажимаем значение в диапазон [0, duration]. audio.duration || 0 —
  // защита от NaN, пока метаданные не загружены.
  const clamped = Math.min(Math.max(seconds, 0), audio.duration || 0);
  audio.currentTime = clamped;
  setCurrentTime(clamped);   // ← оптимистично обновляем UI, не ждём события seeked
}, []);
```

**Свойства состояния:**

| Свойство | Тип | Смысл |
| --- | --- | --- |
| `paused` | `boolean` | `true`, если на паузе (в самом начале — тоже) |
| `ended` | `boolean` | Трек доиграл |
| `error` | `MediaError \| null` | Объект ошибки, см. раздел 6 |
| `readyState` | `number` | Насколько готовы **данные** |
| `networkState` | `number` | Что происходит **с сетью** |
| `seeking` | `boolean` | Идёт перемотка |
| `volume` | `number` 0..1 | См. раздел 8 |
| `muted` | `boolean` | Беззвучный режим |

```tsx
const toggle = useCallback(() => {
  const audio = audioRef.current;
  if (!audio || !audio.src) return;   // трек не выбран — ничего не делаем

  if (audio.paused) {
    audio.play().catch(() => setError("Не удалось начать воспроизведение"));
  } else {
    audio.pause();
    // При паузе сразу сохраняем позицию — вдруг пользователь уйдёт.
    savePlaybackStateToServer(audio.currentTime);
  }
}, [savePlaybackStateToServer]);
```

**Почему `audio.paused`, а не наш `isPlaying`?** Источник правды — сам элемент. Наш флаг может
отставать на рендер: `play()` ещё не выполнился, а мы уже решили, что играем.

**`readyState`** (насколько готовы данные): `0 HAVE_NOTHING` → `1 HAVE_METADATA` (сработал
`loadedmetadata`) → `2 HAVE_CURRENT_DATA` → `3 HAVE_FUTURE_DATA` (`canplay`) → `4 HAVE_ENOUGH_DATA`.

**`networkState`**: `0 EMPTY` → `1 IDLE` (данные есть, загрузка на паузе) → `2 LOADING` →
`3 NO_SOURCE`. Отладочный инструмент: если трек «висит», `NO_SOURCE` обычно значит, что сервер
вернул не тот `Content-Type`.

## 3. События: полный разбор

```tsx
// Имена событий пишутся в нижнем регистре: "loadedmetadata", "canplay" —
// это НАТИВНЫЕ DOM-события, а не React-пропсы вроде onLoadedMetadata.
audio.addEventListener("loadedmetadata", handleLoadedMetadata);
audio.addEventListener("play", handlePlay);
audio.addEventListener("playing", handlePlaying);
audio.addEventListener("pause", handlePause);
audio.addEventListener("waiting", handleWaiting);
audio.addEventListener("canplay", handleCanPlay);
audio.addEventListener("error", handleError);
audio.addEventListener("ended", handleEnded);
```

React-проп `onLoadedMetadata` и `addEventListener("loadedmetadata", ...)` — разные вещи: у пропса есть
коварная особенность «догонять» события, случившиеся до монтирования, что даёт неочевидные двойные
срабатывания. Мы сознательно используем **нативный `addEventListener`**.

**Полный список событий элемента:**

| Событие | Когда срабатывает |
| --- | --- |
| `loadstart` | Началась загрузка |
| `durationchange` | Изменилась `duration` |
| `loadedmetadata` | Стали известны метаданные (длительность, размеры) |
| `loadeddata` | Загружены данные первой порции |
| `progress` | Периодически, пока качаются данные |
| `canplay` | Можно начинать играть |
| `canplaythrough` | Можно играть до конца, скорее всего, без остановок |
| `play` | Вызвали `play()` — **ещё не обязательно звучит** |
| `playing` | Воспроизведение **фактически началось** |
| `pause` | Поставили на паузу |
| `waiting` | Пауза из-за нехватки данных (буферизация) |
| `stalled` | Браузер пытается качать, но данные не приходят |
| `timeupdate` | Позиция изменилась (≈4 раза в секунду) |
| `seeking` / `seeked` | Началась / завершилась перемотка |
| `ratechange` | Изменилась скорость воспроизведения |
| `volumechange` | Изменилась громкость или `muted` |
| `ended` | Трек доиграл до конца |
| `error` | Ошибка (см. раздел 6) |
| `emptied` | Элемент сброшен |

### `loadedmetadata` — «теперь я знаю длительность»

```tsx
const handleLoadedMetadata = () => {
  // duration может быть Infinity у потоковых источников — защищаемся.
  setDuration(Number.isFinite(audio.duration) ? audio.duration : 0);
  setIsLoading(false);
};
```

**Зачем `Number.isFinite`?** У «живых» потоков (интернет-радио) `duration` равна `Infinity`.
У нас всегда файлы, но защита стоит копейки и спасает от `NaN` в вёрстке.

Это же событие — момент, когда **надёжно работает перемотка**, поэтому отложенный seek
(«продолжить слушать») подписывается именно на него:

```tsx
// ОТЛОЖЕННАЯ ПЕРЕМОТКА. Подписываемся на loadedmetadata ОДИН раз и сразу
// отписываемся внутри обработчика — «одноразовый слушатель».
if (pendingSeekRef.current !== null) {
  const seekTarget = pendingSeekRef.current;
  pendingSeekRef.current = null;

  const applyPendingSeek = () => {
    // Защита, если сохранённая позиция больше длительности
    // (например, трек заменили на короткий).
    audio.currentTime = Math.min(seekTarget, audio.duration || seekTarget);
    audio.removeEventListener("loadedmetadata", applyPendingSeek);
  };

  audio.addEventListener("loadedmetadata", applyPendingSeek);
}
```

**Почему нельзя сразу `audio.currentTime = 42` после `audio.src = ...`?** Длительность ещё неизвестна,
браузер не знает, куда перематывать в байтах, и присваивание часто «не прилипает» — сбрасывается в 0.
**Правило: перематывай после `loadedmetadata`.**

### `play`, `pause`, `waiting`, `canplay`

```tsx
const handlePlay = () => { setIsPlaying(true); setError(null); };
const handlePause = () => setIsPlaying(false);

// ---- Буферизация -------------------------------------------------------
const handleWaiting = () => setIsLoading(true);
const handleCanPlay = () => setIsLoading(false);
```

`pause` прилетает **и** от пользователя, **и** когда паузу вызвал код, **и** когда воспроизведение
прервала система. Без него наш `isPlaying` разъедется с реальностью. В интерфейсе `isLoading` даёт
надпись: `{isLoading ? "[ БУФЕРИЗАЦИЯ ]" : isPlaying ? "[ ВОСПРОИЗВЕДЕНИЕ ]" : "[ ПАУЗА ]"}`.

### 🔑 Разница между `play` и `playing`

Это **самый частый вопрос** по аудио в вебе.

| | `play` | `playing` |
| --- | --- | --- |
| Смысл | «Начали **пытаться** играть» | «Звук действительно пошёл» |
| Когда | Сразу после `play()` или клика | Когда данные докачались и воспроизведение стартовало |
| Сработает при блокировке автозапуска? | **Да**, `play` может прийти и следом `pause` | **Нет** |
| Сработает при мгновенной буферизации? | Да, мгновенно | Только когда буфер набрался |
| Сколько раз за трек | Обычно 1 | 1, но может быть больше (после каждой буферизации) |

```
play() вызван
   ├─► "play"        ← «попытка зафиксирована», isPlaying = true, кнопка переключилась
   ├─► "waiting"     ← «данных нет, ждём», isLoading = true
   │   ... прошло 2 секунды ...
   ├─► "playing"     ← «поехали!», isLoading = false, пишем историю
   └─► "timeupdate" × N
```

Отсюда разделение ролей: **`play`** — мгновенная реакция интерфейса (кнопка должна переключиться
**сразу**), **`playing`** — «настоящий старт», момент для побочных эффектов.

```tsx
// Трек реально начал звучать. Именно здесь уместно писать историю:
// play — «начали пытаться», playing — «звук пошёл».
const handlePlaying = () => {
  setIsLoading(false);
  setIsPlaying(true);

  const track = queueRef.current[orderRef.current[orderPositionRef.current] ?? -1];
  if (track && historyTrackIdRef.current !== track.id) {
    historyTrackIdRef.current = track.id;   // ← защита от повторной записи

    void fetch("/api/history", {
      method: "POST",
      headers: { "content-type": "application/json" },
      body: JSON.stringify({ trackId: track.id }),
    }).catch(() => undefined);
  }
};
```

**Почему история пишется на `playing`, а не на `play`?** Потому что `play` срабатывает и для треков,
которые так и не зазвучали: пользователь передумал, сеть упала, браузер заблокировал автозапуск.
История — это факт «слушал», а не «пытался». Защита по `historyTrackIdRef` нужна потому, что `playing`
может сработать несколько раз за трек (после каждой буферизации), а записать хотим один раз.

### `ended` — трек доиграл

```tsx
const handleEnded = () => {
  // Логика повтора: "one" — тот же трек заново; "all" — к следующему,
  // а на последнем к первому; "off" — на последнем останавливаемся.
  const currentOrder = orderRef.current;
  const position = orderPositionRef.current;

  if (repeatRef.current === "one") {
    audio.currentTime = 0;
    void audio.play();
    return;
  }

  const isLast = position >= currentOrder.length - 1;
  if (isLast && repeatRef.current === "off") {
    setIsPlaying(false);
    return;
  }

  setOrderPosition(isLast ? 0 : position + 1);
  shouldAutoplayRef.current = true;
};
```

Обрати внимание: обработчик **не вызывает функции напрямую** — он только меняет состояние.
Новый трек подставится сам, в `useEffect([currentTrackId])`. Это правильный React-стиль:
обработчик **описывает**, что случилось, а не **командует**. И ещё: `void audio.play()` — мы не ждём
промис, но и не игнорируем молча; `void` — явный сигнал читателю и линтеру: «я знаю, что тут Promise».

### Что мы НЕ слушаем и почему

- **`canplaythrough`** — это **оценка** скорости сети; она врёт при просадках, может вообще не сработать
  (файл уже скачан) и **не отменяется**. Не предсказывай — реагируй на факты (`waiting`/`canplay`).
- **`timeupdate`** — слишком редкое (см. раздел 5).
- **`seeked`** — перемотку инициируем только мы сами, новую позицию знаем сразу.
- **`volumechange`** — громкость меняем только мы, значение уже в состоянии React.

## 4. `play()` возвращает Promise — и это не мелочь

**Почему промис, а не «запустилось»?** Потому что запуск звука — **асинхронная операция
с возможностью отказа**: браузер должен решить, разрешать ли звук вообще, есть ли уже данные,
не занято ли устройство вывода.

**Autoplay policy.** Все современные браузеры блокируют звук, начавшийся **без действия пользователя**
(раньше сайты играли музыку при открытии — это было невыносимо):

> Воспроизведение разрешено, если пользователь уже **взаимодействовал со страницей**
> (клик, нажатие клавиши, касание) или ранее разрешил автозвук для этого сайта.

Первый клик по странице «разблокирует» дальнейшее аудио на вкладке. У нас всё в порядке:
пользователь жмёт на строку трека — это и есть жест. Нюансы: **мобильные браузеры строже**
(на iOS/Android автозапуск почти всегда запрещён без касания); **беззвучное** воспроизведение
обычно разрешено, но как только снимаешь `muted` — блок.

**Что происходит при отказе.** `play()` возвращает **отклонённый промис** с `DOMException`
по имени `NotAllowedError`. Не обработаешь — получишь `Unhandled rejection` в консоли и тишину
для пользователя.

```tsx
// АВТОЗАПУСК.
// audio.play() возвращает Promise, который МОЖЕТ быть отклонён, если браузер
// запретил автозапуск. Все наши вызовы play() происходят из обработчиков
// клика, но подстраховаться и показать понятную ошибку всё равно нужно.
if (shouldAutoplayRef.current) {
  shouldAutoplayRef.current = false;
  audio.play().catch((playError: unknown) => {
    setIsLoading(false);
    setError("Браузер заблокировал автозапуск. Нажми ▶");
    console.warn("[player] play() отклонён:", playError);
  });
}
```

Хороший обработчик отказа делает три вещи: **выключает индикатор загрузки** (событие `playing`
не придёт, иначе спиннер будет крутиться вечно), **объясняет человеку, что делать** (не «Ошибка 0x0»,
а «Нажми ▶»), и **пишет техническую деталь в консоль** — для тебя при отладке.

```ts
audio.play();                          // ПЛОХО: ошибка потеряется молча
audio.play().catch(console.log);       // ПЛОХО: ошибка есть, но пользователь не поймёт
```

## 5. `timeupdate` против `requestAnimationFrame`

`timeupdate` срабатывает примерно **4 раза в секунду** — полоса прогресса дёргалась бы крупными
рывками по 0.25 секунды. Для плавной полосы нужно 60 обновлений в секунду.

```tsx
// ПЛАВНОЕ ОБНОВЛЕНИЕ ПОЛОСЫ ПРОГРЕССА ЧЕРЕЗ requestAnimationFrame.
// requestAnimationFrame просит браузер вызвать функцию ПЕРЕД следующей
// перерисовкой экрана, то есть обычно 60 раз в секунду.
//
// Цикл работает ТОЛЬКО пока играет музыка (см. зависимость [isPlaying]).
// На паузе кадров нет вообще.
useEffect(() => {
  if (!isPlaying) return;

  let frameId = 0;

  const updateTime = () => {
    const audio = audioRef.current;
    if (audio) {
      setCurrentTime(audio.currentTime);

      // Сохраняем позицию на сервере, но не чаще раза в 10 секунд.
      const now = Date.now();
      if (now - lastStateSaveRef.current > 10_000) {
        lastStateSaveRef.current = now;
        savePlaybackStateToServer(audio.currentTime);
      }
    }
    frameId = window.requestAnimationFrame(updateTime);   // ← цикл
  };

  frameId = window.requestAnimationFrame(updateTime);

  // Очистка: отменяем запрошенный кадр при паузе или размонтировании.
  return () => window.cancelAnimationFrame(frameId);
}, [isPlaying, savePlaybackStateToServer]);
```

**По шагам:** `requestAnimationFrame` сам себя не повторяет — чтобы получился цикл, нужно
**перезапросить кадр внутри колбэка**. Функция очистки обязательна: без `cancelAnimationFrame`
цикл продолжил бы стучаться в `setCurrentTime` после паузы.

**Почему это правильный инструмент:** синхронизация с экраном (колбэк вызывается ровно перед
перерисовкой — никакого дребезга); автоматическая экономия (на неактивной вкладке браузер **сам**
перестаёт выдавать кадры, а `setInterval(fn, 16)` молотил бы и в фоне); уважение к частоте экрана
(на 144 Гц — 144 вызова, на 60 Гц — 60, код не привязан к «магическому» числу).

### Ключевой приём: изоляция частых обновлений

`currentTime` живёт в **отдельном** контексте:

```tsx
const PlayerActionsContext = createContext<PlayerActions | null>(null);
const PlayerTrackContext = createContext<TrackState | null>(null);
const PlayerTimelineContext = createContext<TimelineState | null>(null);
```

```
// Соблазнительно положить всё состояние в один контекст. Но тогда ЛЮБОЕ
// изменение (например, currentTime, который обновляется 60 раз в секунду)
// перерисовывало бы ВСЕХ потребителей контекста — включая список из 1000
// треков. Это гарантированные тормоза.
```

> **Правило навсегда:** разделяй состояние по частоте изменений. Быстрое (60 Гц) — отдельно
> от медленного (раз в минуту). Иначе каждый кадр тянет за собой перерисовку всего дерева.

## 6. `MediaError` — что именно сломалось

Когда элемент не может воспроизвести файл, он выставляет свойство `error` в объект `MediaError`
и присылает событие `error`. Полезные поля: `code` (число 1..4) и `message` (текст, разный
в разных браузерах — для UI не годится).

| Код | Константа | Что значит | Типичная причина | Что делать |
| --- | --- | --- | --- | --- |
| **1** | `MEDIA_ERR_ABORTED` | Загрузка прервана | `load()` повторно, уход со страницы, смена `src` | Часто безобидно, можно игнорировать |
| **2** | `MEDIA_ERR_NETWORK` | Ошибка сети | Сервер отдал 500, оборвалось соединение | «Проверь сеть», кнопка «повторить» |
| **3** | `MEDIA_ERR_DECODE` | Ошибка декодирования | Файл повреждён, обрезан, битый заголовок | «Файл повреждён», пропустить трек |
| **4** | `MEDIA_ERR_SRC_NOT_SUPPORTED` | Источник не поддерживается | **Самая частая у нас**: неверный `Content-Type`, 404, формат не играется | Проверить MIME в `stream/route.ts` и наличие файла |

```tsx
const handleError = () => {
  setIsLoading(false);
  setIsPlaying(false);

  const code = audio.error?.code;
  const messages: Record<number, string> = {
    1: "Загрузка прервана",
    2: "Ошибка сети при загрузке файла",
    3: "Не удалось декодировать файл (возможно, он повреждён)",
    4: "Формат файла не поддерживается браузером",
  };
  setError(messages[code ?? 0] ?? "Не удалось воспроизвести трек");
};
```

Три приёма: `audio.error?.code` — опциональная цепочка (к моменту обработчика `error` может быть
`null`, без `?.` получили бы `TypeError`); `Record<number, string>` — словарь вместо `switch`;
`?? "..."` — фолбэк, чтобы пользователь никогда не увидел «Ошибка undefined».

**Код 4 — почему он у нас главный подозреваемый.** Тут чаще виноват **сервер**, а не браузер.
Проверяй по порядку:

1. **`Content-Type` не тот.** В `stream/route.ts` есть таблица `AUDIO_MIME_TYPES` (`.mp3` → `audio/mpeg`,
   `.flac` → `audio/flac` и т. д.). Если расширения в таблице нет, отдаётся `application/octet-stream` —
   и `<audio>` откажется играть: *«Если соврать (например, всегда писать `application/octet-stream`),
   тег `<audio>` откажется играть файл»*.
2. **Сервер вернул 404 или 401.** Открой вкладку Network: ответ — не аудио, а JSON с ошибкой.
3. **Формат правда не поддерживается.** FLAC играют все современные браузеры, экзотика (DSD, APE) — почти никто.

Проверить **заранее** можно так: `document.createElement("audio").canPlayType("audio/flac")` →
`"probably"` / `"maybe"` / `""`. Три строки, а не «да/нет», потому что ответ зависит от кодека
**внутри** контейнера: `audio/mp4` может содержать и AAC, и ALAC.

## 7. Как браузер загружает медиа: буферизация и Range

**Наивная модель** («скачай весь файл, потом играй») не работает: для flac на 60 МБ воспроизведение
начнётся через полминуты, а перемотка потребует ждать конца загрузки. **Реальная модель:** браузер
работает как умный читатель — запрашивает **начало файла** с метаданными (у mp3 это ID3-тег,
у flac — заголовок STREAMINFO), читает длительность → событие `loadedmetadata`, затем играет,
**подкачивая данные вперёд** и держа буфер ~10–30 секунд. Именно этот запас показывает `audio.buffered`.

Чтобы «прочитать файл с 300-го мегабайта», нужен HTTP-механизм — **Range Requests** (RFC 7233):

```
GET /api/tracks/5/stream
← 200 OK
  Accept-Ranges: bytes            ← «я умею отдавать кусками»
  Content-Length: 5000000

GET /api/tracks/5/stream
Range: bytes=0-262143             ← «дай первые 256 КБ»
← 206 Partial Content
  Content-Range: bytes 0-262143/5000000
  Accept-Ranges: bytes

Range: bytes=2500000-2750000      ← пользователь тянет ползунок в середину
← 206 Partial Content
  Content-Range: bytes 2500000-2750000/5000000
```

**Ключевой заголовок — `Accept-Ranges: bytes`.** Без него браузер считает, что сервер умеет отдавать
только файл целиком. Тогда перемотка вперёд **не работает** (нечего запросить, кроме начала, —
приходится качать заново), а `duration` может остаться `NaN`, если метаданные лежат в конце файла.

```ts
// Range НЕ запрошен → весь файл (200)
headers: {
  "Content-Length": String(fileSize),
  // Главный заголовок: «я умею отдавать кусками». Без него браузер
  // не станет запрашивать Range и не сможет перематывать.
  "Accept-Ranges": "bytes",
}

// Range запрошен → кусок (206)
const { start, end } = parsedRange;
// Content-Length = «конец минус начало плюс один»: start и end ВКЛЮЧИТЕЛЬНЫ.
// Классическая ошибка новичка — забыть +1 и отдать на байт меньше.
const chunkSize = end - start + 1;

headers: {
  "Content-Length": String(chunkSize),
  // Content-Range объясняет, какой именно кусок пришёл и сколько всего байт.
  "Content-Range": `bytes ${start}-${end}/${fileSize}`,
  "Accept-Ranges": "bytes",
}
```

Разбор заголовка `Range` и логика ответа `416` живут в `parseRangeHeader` того же файла —
**подробный HTTP-разбор в главе про стриминг**, здесь важна только связь:

| Что в браузере | Что нужно на сервере |
| --- | --- |
| Мгновенный старт воспроизведения | Потоки, а не чтение файла целиком в память |
| `duration` известна сразу | Возможность отдать первые килобайты (только начало файла) |
| Перемотка вперёд работает | `Accept-Ranges: bytes` + ответ `206 Partial Content` |
| Перемотка назад без перезагрузки | Умение отдать произвольный диапазон байт |
| Продолжение после буферизации | `206` с корректным `Content-Range` |

**Что смотреть в DevTools.** Network → фильтр `Media`: первый запрос 100–300 КБ (статус 200 или 206),
затем серия `206 Partial Content` со своими `Range`, а при перемотке — новый `206` с большим смещением.
Колонка `Size` будет примерно равна буферу, а не размеру файла. **Первое, что нужно сделать при проблеме
с воспроизведением — открыть Network и посмотреть на реальные ответы сервера.**

Про `preload="metadata"`: чтобы узнать длительность, браузеру нужно прочитать **только начало файла** —
один маленький Range-запрос. Ещё два события для отладки: **`stalled`** — браузер хочет качать,
но данные не приходят (проблема в сети или сервере); **`suspend`** — загрузка приостановлена
**намеренно** (буфер полон). Второе нормально и не ошибка, но их легко перепутать по названию.

## 8. Громкость: диапазон 0..1 и почему не проценты

```ts
audio.volume = 0.5;   // 50%
audio.volume = 1;     // 100%
audio.volume = 0;     // тишина
```

**Диапазон строго `0.0` .. `1.0`.** Почему не проценты? Потому что `volume` — это **коэффициент
умножения амплитуды сигнала**, а не «процент». Проценты — представление **для человека**, которое
мы делаем сами при отображении. Если ошибиться, браузер **не бросит исключение**, а молча зажмёт
значение: `audio.volume = 50` → станет `1.0`, `-0.5` → станет `0`. Поэтому баг «ползунок на 50,
а играет на 100%» ловится глазами, а не в консоли. **Всегда зажимай сам.**

Состояние хранит **коэффициент**:

```tsx
const [volume, setVolumeState] = useState(1);
const [muted, setMuted] = useState(false);

const setVolume = useCallback((value: number) => {
  // Math.min(Math.max(value, 0), 1) — «зажать в диапазон»: сначала
  // «не меньше нуля», потом «не больше единицы».
  const clamped = Math.min(Math.max(value, 0), 1);
  setVolumeState(clamped);
  // Если пользователь крутит громкость — снимаем режим «без звука».
  // Привычка из всех плееров: тянет ползунок вверх — значит, хочет звук.
  if (clamped > 0) setMuted(false);
  writeLocalStorage(STORAGE_VOLUME_KEY, String(clamped));
}, []);

// Применение к элементу — отдельным эффектом.
useEffect(() => {
  const audio = audioRef.current;
  if (!audio) return;
  audio.volume = volume;
  audio.muted = muted;
}, [volume, muted]);
```

**Почему отдельный эффект, а не присваивание прямо в `setVolume`?** Потому что громкость меняется
не только от ползунка: ещё из localStorage при старте, ещё стрелками клавиатуры. Эффект покрывает
**все** пути изменения — это и есть декларативный стиль: «приведи элемент в соответствие с состоянием».

**`muted` или `volume = 0`?** Это **разные вещи**, и правильный плеер использует оба:

| | `muted = true` | `volume = 0` |
| --- | --- | --- |
| Что делает | Глушит вывод, **помня** прежнюю громкость | Реально ставит громкость в ноль |
| Что показывает `audio.volume` | Прежнее значение (0.7) | 0 |
| Восстановление | `muted = false` — звук вернулся на 0.7 | Надо помнить, где было |

Мы используем `muted` — именно чтобы **восстановление было в один клик**:
`const toggleMute = useCallback(() => setMuted((current) => !current), []);`
А иконка учитывает **оба** случая — пользователь, выкрутивший громкость в ноль, ожидает перечёркнутый
динамик, хотя `muted` при этом `false`:

```tsx
{muted || volume === 0 ? "🔇" : volume < 0.5 ? "🔉" : "🔊"}
```

**Проценты — только для показа.** У ползунка `min={0} max={1}` — те же единицы, что у `audio.volume`:

```tsx
<input
  type="range" min={0} max={1} step={0.01}
  value={muted ? 0 : volume}
  onChange={(event) => actions.setVolume(Number(event.target.value))}
  aria-label="Громкость"
  title={`Громкость: ${Math.round(volume * 100)}%`}
/>
```

> **Правило:** храни значение в единицах, в которых его принимает API. Пересчитывай только для показа.

Две ловушки: **`event.target.value` у `input[type=range]` — всегда строка**, даже для чисел
(забудешь `Number(...)` — в состоянии окажется строка, и сравнения сломаются); и **числа
с плавающей точкой**: `0.1 + 0.2` в JS даёт `0.30000000000000004`, поэтому при шаге 0.05 ползунок
начнёт показывать `0.7000000000001`. Приём `Math.round(x * 100) / 100` округляет до сотых:

```tsx
// Шаг громкости 5%. Округление до сотых убирает накопление
// ошибки сложения дробных чисел (0.1 + 0.2 ≠ 0.3 в JS!).
actions.setVolume(Math.round((volume + 0.05) * 100) / 100);
```

## 9. Клавиатурное управление

```tsx
useEffect(() => {
  const handleKeyDown = (event: KeyboardEvent) => {
    // ГЛАВНАЯ ПРОВЕРКА: не мешаем ли мы пользователю печатать. Если фокус
    // в поле поиска и нажат пробел, он ожидает пробел в тексте, а не паузу.
    // tagName содержит имя тега В ВЕРХНЕМ РЕГИСТРЕ ("INPUT", "TEXTAREA").
    const target = event.target as HTMLElement | null;
    const tagName = target?.tagName;
    const isEditing =
      tagName === "INPUT" || tagName === "TEXTAREA" || tagName === "SELECT" || target?.isContentEditable === true;

    if (isEditing) return;

    // Не перехватываем сочетания с Ctrl/Cmd/Alt: там свои горячие клавиши
    // (Ctrl+R — перезагрузка, Cmd+L — адресная строка).
    if (event.ctrlKey || event.metaKey || event.altKey) return;

    switch (event.key) {
      case " ":  event.preventDefault(); actions.toggle(); break;
      case "ArrowRight": event.preventDefault(); actions.seek(currentTime + 5); break;
      case "ArrowLeft":  event.preventDefault(); actions.seek(currentTime - 5); break;
      case "ArrowUp":   event.preventDefault();
        actions.setVolume(Math.round((volume + 0.05) * 100) / 100); break;
      case "ArrowDown": event.preventDefault();
        actions.setVolume(Math.round((volume - 0.05) * 100) / 100); break;
      case "n": case "N": actions.next(); break;
      case "p": case "P": actions.previous(); break;
      default: break;
    }
  };

  window.addEventListener("keydown", handleKeyDown);
  return () => window.removeEventListener("keydown", handleKeyDown);
}, [actions, currentTime, volume]);
```

| Клавиша | Действие |
| --- | --- |
| `Space` | Play / pause |
| `→` / `←` | ±5 секунд |
| `↑` / `↓` | Громкость ±5% |
| `N` / `n` | Следующий трек |
| `P` / `p` | Предыдущий трек |

**Почему нужен `preventDefault` для пробела.** У каждой клавиши есть **действие по умолчанию**,
которое браузер выполняет сам, если никто не вмешался:

| Клавиша | Действие по умолчанию |
| --- | --- |
| `Space` | Прокрутка страницы вниз на экран |
| `↑` / `↓` | Прокрутка страницы |
| `←` / `→` | Прокрутка по горизонтали |
| `/` | Быстрый поиск в Firefox |

`event.preventDefault()` **отменяет действие по умолчанию**; событие при этом продолжает
распространяться по дереву — просто браузер не делает то, что делал бы «сам по себе».
Без `preventDefault` пользователь нажимает пробел, музыка встаёт на паузу — **и страница прыгает вниз**.
Раздражает моментально. Стрелка `→` без него перемотала бы трек **и** сдвинула страницу вправо.

**Проверка `tagName === "INPUT"`.** Представь: в шапке поле поиска, пользователь печатает название
песни, нажимает пробел — и музыка встаёт на паузу. **Недопустимо.** Поэтому мы смотрим на `event.target`
(элемент, получивший событие) и молча выходим, если это редактируемое поле.

**Почему `tagName` в верхнем регистре?** Это особенность DOM: `tagName` **всегда** возвращает имя тега
заглавными (`"INPUT"`, `"DIV"`), даже если в HTML написано `<input>`. Сравнение `tagName === "input"`
всегда ложно — легко полдня искать такой баг. (А `target.localName` вернул бы строчными.)

Почему четыре проверки, а не одна:

- **`INPUT`** — текстовые поля, поиск, **и наш ползунок громкости тоже** (у него `type="range"`).
  Это правильно: стрелки на ползунке громкости должны крутить **его**, а не перематывать трек.
- **`TEXTAREA`** — многострочный ввод.
- **`SELECT`** — выпадающий список: стрелками там выбирают option.
- **`isContentEditable`** — богатые редакторы и CMS не имеют тега `INPUT`, но в них точно так же печатают.

Без проверки `ctrlKey || metaKey || altKey` `Cmd+N` (новое окно в Safari) сначала переключил бы трек,
а потом открыл окно. `metaKey` — это `Cmd` на macOS и `Win` на Windows.

**Зависимости — и почему тут компромисс.** `[actions, currentTime, volume]` означает, что `currentTime`
меняется 60 раз в секунду, значит эффект **пересоздаётся 60 раз в секунду**: снимает старый обработчик,
вешает новый. Звучит страшно, но `addEventListener`/`removeEventListener` на `window` — очень дешёвые
операции, а альтернатива добавляет код ради невидимой экономии. **Но знать альтернативу надо**, потому
что в более тяжёлых случаях она обязательна — тот же приём в `player-context.tsx`:

```
// Такой обработчик «запоминает» значения из момента создания — это
// называется ЗАМЫКАНИЕ (closure). Чтобы не пересоздавать подписки при
// каждом изменении состояния, мы держим актуальные значения в ref'ах
// и читаем их внутри обработчика. Ref всегда даёт свежее значение.
const repeatRef = useRef<RepeatMode>("off");
const shuffleRef = useRef(false);
const orderRef = useRef<number[]>([]);
const queueRef = useRef<TrackDTO[]>([]);
```

```tsx
// ПЛОХО: обработчик «запомнит» currentTime = 0 навсегда,
// потому что эффект выполнится один раз.
useEffect(() => {
  const onKey = (e: KeyboardEvent) => {
    if (e.key === "ArrowRight") actions.seek(currentTime + 5);  // ← всегда 0 + 5!
  };
  window.addEventListener("keydown", onKey);
  return () => window.removeEventListener("keydown", onKey);
}, []);   // пустые зависимости = подписка одна на всю жизнь
```

Два выхода: добавить значение в зависимости (наш выбор в `PlayerBar`) или держать его в `ref`
(наш выбор в `player-context`). Выбор диктуется частотой и ценой пересоздания.

## 10. Media Session API — управление откуда угодно

API позволяет странице сказать системе: «Сейчас играет вот эта песня, вот этого исполнителя,
с такой обложкой. А вот что делать, если пользователь нажмёт "следующий трек"». Без него: играет
музыка, ты нажимаешь мультимедийную клавишу «next» — и **ничего не происходит**, потому что браузер
не знает, что за медиа активно. То же с Bluetooth-наушниками: нажатие уходит в систему, система
спрашивает браузер, браузер — страницу. Не ответила → кнопка мертва.

Где это видно: **экран блокировки телефона**, центр управления iOS / медиапанель Android, macOS Control
Center, мультимедийные клавиши клавиатуры, наушники (AirPods, гарнитуры), мини-панель Chrome справа
от адресной строки.

```tsx
// MEDIA SESSION API — управление с клавиатуры, из наушников и с экрана
// блокировки телефона. Без этого кнопки «следующий/предыдущий» на
// клавиатуре (обычно Fn+стрелки) и на Bluetooth-наушниках работать не будут.
useEffect(() => {
  // Проверяем, что API вообще есть: в старых браузерах его нет.
  if (typeof navigator === "undefined" || !("mediaSession" in navigator)) return;
  if (!currentTrack) return;

  navigator.mediaSession.metadata = new MediaMetadata({
    title: currentTrack.title,
    artist: currentTrack.artist,
    album: currentTrack.album,
    // artwork принимает массив картинок разного размера.
    // sizes — ПОДСКАЗКА браузеру, реальный размер он определит сам.
    artwork: currentTrack.hasCover ? [{ src: buildCoverUrl(currentTrack.id), sizes: "512x512" }] : [],
  });

  navigator.mediaSession.setActionHandler("play", () => { void audioRef.current?.play(); });
  navigator.mediaSession.setActionHandler("pause", () => { audioRef.current?.pause(); });
  navigator.mediaSession.setActionHandler("previoustrack", () => previousRef.current());
  navigator.mediaSession.setActionHandler("nexttrack", () => nextRef.current());
  navigator.mediaSession.setActionHandler("seekto", (details) => {
    const audio = audioRef.current;
    if (details.seekTime != null && audio) {
      audio.currentTime = details.seekTime;
      setCurrentTime(details.seekTime);
    }
  });
}, [currentTrack]);
```

`MediaMetadata` принимает `title`, `artist`, `album` и `artwork` — массив `{ src, sizes, type }`.
Про `artwork` два практичных момента: это **массив**, а не одна картинка (разные системы просят разные
размеры — правильно давать 96/128/192/256/512 пикселей, и система выберет подходящий); а `sizes` —
**подсказка, а не контракт** (браузер всё равно определит реальный размер сам). У нас отдаётся одна
картинка 512×512 и только если обложка есть; пустой массив `[]` — валидное значение.

Обработчики **не вызывают наши функции напрямую**, а проксируют их через ref:
`setActionHandler("nexttrack", () => nextRef.current())`. Из комментария к файлу: *«Обработчики Media
Session ставятся в useEffect, но next/previous объявлены чуть ниже по тексту. Чтобы не ловить путаницу
с порядком объявлений, держим актуальные версии в ref'ах»*. Ref решает сразу две задачи:
**актуальность** (в ref всегда свежая версия функции) и **порядок объявлений**.

| Действие | Когда приходит |
| --- | --- |
| `play` / `pause` / `stop` | Нажали соответствующую кнопку вне страницы |
| `previoustrack` / `nexttrack` | «Предыдущий/следующий трек» |
| `seekbackward` / `seekforward` | «Назад/вперёд на N секунд» (`details.seekOffset`) |
| `seekto` | Прямой переход (`details.seekTime`, `details.fastSeek`) |
| `skipad` | Пропустить рекламу |

**Если обработчик не задан — кнопка просто не появится** в системном интерфейсе. Браузер показывает
только то, что ты умеешь обрабатывать. Хорошая практика — снимать обработчики при размонтировании
(`setActionHandler("nexttrack", null)`); у нас этого нет, потому что провайдер живёт в корневом
`layout` и не размонтируется до закрытия вкладки.

**Поддержка браузерами.** Проверяй по MDN и caniuse перед тем, как обещать поддержку; ориентир:

| Браузер | Поддержка |
| --- | --- |
| **Chrome** (десктоп и Android) | Полная — метаданные и все основные действия |
| **Edge** | Полная (тот же движок) |
| **Firefox** (десктоп) | В основном полная для метаданных и базовых действий |
| **Safari** (macOS/iOS) | **Частичная** — набор действий ограничен, часть работает только через Now Playing |

> **Практический вывод:** никогда не полагайся на Media Session как на **единственный** способ
> управления. Если API нет или действие не поддержано, у пользователя должны остаться наши кнопки.
> Поэтому мы и проверяем `"mediaSession" in navigator` перед использованием.

## 11. Сохранение позиции: `pagehide` + `sendBeacon`

Основной механизм — обычный `fetch` с троттлингом раз в 10 секунд (см. раздел 5). Но есть проблема:
**пользователь закрывает вкладку**, а времени на «нормальный» запрос нет. При закрытии вкладки браузер
запускает выгрузку страницы, и асинхронные операции **могут быть прерваны в любой момент**: запрос
создан, отправлен... а ответ ждать уже некому. Особенно плохо на медленном канале — пока
устанавливается TCP-соединение, вкладки уже нет.

```tsx
// СОХРАНЕНИЕ ПОЗИЦИИ ПРИ УХОДЕ СО СТРАНИЦЫ.
//
// Событие pagehide срабатывает и при закрытии вкладки, и при уходе в bfcache.
// Обычный fetch в этот момент может не успеть — браузер просто закроет
// страницу. Поэтому используем navigator.sendBeacon: он специально сделан
// для «отправь и не жди ответа».
useEffect(() => {
  const handlePageHide = () => {
    const audio = audioRef.current;
    const track = queueRef.current[orderRef.current[orderPositionRef.current] ?? -1];
    if (!audio || !track || typeof navigator.sendBeacon !== "function") return;

    // Blob с типом application/json — чтобы сервер понял формат тела.
    const payload = new Blob([JSON.stringify({ trackId: track.id, position: audio.currentTime })], {
      type: "application/json",
    });
    navigator.sendBeacon("/api/playback-state", payload);
  };

  window.addEventListener("pagehide", handlePageHide);
  return () => window.removeEventListener("pagehide", handlePageHide);
}, []);
```

| | `fetch` | `sendBeacon` |
| --- | --- | --- |
| Возвращает | Promise | `boolean` (поставлено ли в очередь) |
| Ответ сервера | Доступен | **Недоступен вообще** |
| Успеет при закрытии вкладки | Может не успеть | **Гарантированно отправляется** браузером |
| Метод | Любой | **Только POST** |
| Тело | Любое | `Blob`, `ArrayBuffer`, `FormData`, строка, `URLSearchParams` |
| Свои заголовки | Да | **Нет** (кроме `Content-Type` из Blob) |

**Главная фишка:** браузер берёт на себя ответственность за доставку, даже если вкладка закрывается
прямо сейчас. При этом ответ тебе не нужен — это «выстрелил и забыл» по своей природе.
Ограничения, о которых надо знать:

- **Только POST.** Обычное сохранение у нас идёт через `fetch` с `PUT`, аварийное — через beacon
  с `POST`. Сервер должен поддерживать оба — это нормальная практика.
- **`Content-Type` берётся из Blob.** Поэтому JSON оборачивается в `Blob` с типом `application/json`:
  если передать просто строку, тип будет `text/plain`, и серверный парсер JSON может отказаться.
- **Свои заголовки поставить нельзя** — ни токена авторизации, ни кастомного заголовка. Поэтому токен
  у нас кладётся **в query-параметр URL** (см. `buildStreamUrl` и `checkAccessToken`).
- **Гарантирует отправку, а не обработку.** Сервер упал — запрос уйдёт в никуда, ты не узнаешь.
  Для «сохранить секунду воспроизведения» это абсолютно приемлемо. Лимит на размер — обычно 64 КБ;
  у нас payload — пара сотен байт.

**Почему `pagehide`, а не `beforeunload` или `unload`:**

| Событие | Статус |
| --- | --- |
| `unload` | **Устарело.** Ломает bfcache, ненадёжно на мобильных |
| `beforeunload` | Задумано для «спросить, точно ли уходишь». Работает не всегда |
| `pagehide` | **Рекомендуемый способ.** Срабатывает и при уходе, и при уходе в bfcache |

**Что такое bfcache?** Back/forward cache — браузер сохраняет страницу в памяти целиком, чтобы
мгновенно восстановить её при нажатии «назад». Если страница слушает `unload`, браузер **не станет**
её кэшировать, потому что `unload` может сломать состояние. `pagehide` такого эффекта не имеет.
Поэтому в современном вебе **`pagehide` + `sendBeacon`** — стандартная связка.

**Троттлинг основного сохранения** — из цикла `requestAnimationFrame`:

```tsx
// Сохраняем позицию на сервере, но не чаще раза в 10 секунд.
const now = Date.now();
if (now - lastStateSaveRef.current > 10_000) {
  lastStateSaveRef.current = now;
  savePlaybackStateToServer(audio.currentTime);
}
```

Без этого `if` цикл отправлял бы **60 запросов в секунду** — 3600 в минуту ради одной цифры,
которая меняется предсказуемо.

> **Троттлинг** (throttle — «ограничивать расход») — приём «не чаще одного раза в N времени».
> Нужен везде, где есть частое событие и дорогое действие.

Дополнительно позиция сохраняется на паузе — очевидный «момент остановки»:
`audio.pause(); savePlaybackStateToServer(audio.currentTime);`

## 12. Доступность (a11y)

**`aria-label` — «как называется эта кнопка».** Наши кнопки нарисованы **символами**: `◀◀`, `❚❚`, `■`,
`⤨`, `↻`. Скринридер прочитает из них ничего осмысленного — у символов нет произносимых имён.

```tsx
<button type="button" onClick={actions.previous} aria-label="Предыдущий трек">◀◀</button>

<button
  type="button"
  onClick={actions.toggle}
  title="Играть / пауза (пробел)"
  aria-label={isPlaying ? "Пауза" : "Играть"}   // ← имя МЕНЯЕТСЯ
>
  {isPlaying ? "❚❚" : "▶"}
</button>
```

`aria-label` у play/pause **динамический**: со статичным «Играть / пауза» пользователь скринридера
не поймёт, что произойдёт по нажатию.

> **Правило:** имя кнопки описывает **действие, которое произойдёт**, а не текущее состояние.

Для режима повтора имя составное — `↻1` само по себе нечитаемо:
`` aria-label={`Режим повтора: ${repeat === "off" ? "выключен" : repeat === "all" ? "весь список" : "один трек"}`} ``

**`aria-label` vs `title`** — они не дублируют друг друга. `title` — всплывающая подсказка для
**зрячего** пользователя с мышью (показывается через секунду наведения, недоступен при фокусе
с клавиатуры в некоторых браузерах, не работает на тач-устройствах). `aria-label` — доступное имя
для **скринридера**. Пиши оба.

**`aria-pressed` — «это переключатель, и он включён».** Кнопки перемешивания и mute — **переключатели**,
у них есть состояние:

```tsx
<button
  type="button"
  onClick={actions.toggleShuffle}
  // aria-pressed сообщает скринридеру состояние переключателя.
  aria-pressed={shuffle}
  title="Перемешивание"
  aria-label="Перемешивание"
>⤨</button>

<button
  type="button"
  onClick={actions.toggleMute}
  aria-pressed={muted}
  aria-label={muted ? "Включить звук" : "Выключить звук"}
>{muted || volume === 0 ? "🔇" : volume < 0.5 ? "🔉" : "🔊"}</button>
```

С `aria-pressed` скринридер скажет «Перемешивание, переключатель, **нажато**». Без него — просто
«Перемешивание, кнопка», и текущее состояние неизвестно. У кнопки повтора `aria-pressed` поставить
**нельзя**: у неё не булево, а три состояния (`off` / `all` / `one`) — поэтому состояние ушло в `aria-label`.

| Ситуация | Правильно |
| --- | --- |
| Кнопка «выполнить действие» (play, next) | `aria-label` |
| Кнопка-переключатель вкл/выкл | `aria-label` + `aria-pressed` |
| Кнопка с 3+ состояниями | `aria-label` с текущим состоянием |
| Группа взаимоисключающих вариантов | `role="radiogroup"` + `aria-checked` |

**`role="alert"` — «прочитай это немедленно».**

```tsx
{error && (
  <div
    // role="alert" заставляет скринридер прочитать сообщение
    // немедленно, прервав текущее — для ошибок это правильно.
    role="alert"
    className="mt-1 border border-alert px-2 py-1 text-[11px] text-alert"
  >
    ⚠ {error}
  </div>
)}
```

`role="alert"` — это **ARIA live region** с `aria-live="assertive"`: `polite` означает «прочитай,
когда освободишься» (статусы, уведомления), `assertive` — «прерви всё и прочитай **сейчас**».
Почему `assertive`: если трек не заиграл, а пользователь не видит экран, он должен узнать немедленно,
а не после того, как скринридер договорит описание кнопки.

**`aria-valuetext` — самое важное для ползунка.**

```tsx
<input
  type="range"
  min={0}
  // max не может быть нулём: браузер не позволит. Если длительность
  // ещё неизвестна, ставим 1 — ползунок просто будет в начале.
  max={max > 0 ? max : 1}
  // step="any" разрешает дробные значения — важно для секунд с долями.
  step="any"
  value={value}
  onChange={(event) => onChange(Number(event.target.value))}
  aria-label="Позиция воспроизведения"
  aria-valuetext={`${formatDuration(value)} из ${formatDuration(max)}`}
/>
```

**Проблема.** Нативный `input[type=range]` объявит себя так: «Позиция воспроизведения, ползунок,
**42.7381**, минимум 0, максимум 213.915». Слышать `42.7381` бесполезно — человек не думает секундами
с четырьмя знаками после запятой. **Решение:** `aria-valuetext` переопределяет то, что произносится
**вместо** числа → «Позиция воспроизведения, ползунок, **0:42 из 3:33**». При этом `aria-valuenow`
остаётся числом для машинной обработки (берётся из `value` автоматически) — оба нужны, и они
не заменяют друг друга.

> **Правило:** если `input[type=range]` показывает не число, а производную величину (время,
> температуру, цену) — всегда задавай `aria-valuetext`.

**Ещё пара моментов.** Осмысленный `alt` у обложки (`` alt={`Обложка: ${currentTrack.album}`} ``,
а не `alt="cover"`). `disabled` у кнопок без трека: отключённая кнопка не получает фокус и сообщает
скринридеру «недоступно» — лучше, чем кликабельная кнопка, которая молча ничего не делает.
`aria-label="Громкость"` у ползунка — иначе скринридер скажет «ползунок, 0.7» без контекста.
И главное: мы используем настоящие `<button>` и `<input type="range">`, а не `<div onClick>` — это
бесплатно даёт фокус клавиатурой, активацию `Enter`/`Space`, роли ARIA, поддержку скринридеров
и голосового управления. Комментарий в `SeekBar` объясняет ровно это:

```
// Почему не наоборот (сначала полоса, потом невидимый input)? Потому что
// тогда пришлось бы вручную реализовывать перетаскивание, поддержку
// клавиатуры, доступность. Используя настоящий input, мы получаем всё это
// бесплатно от браузера.
```

## 13. Частые ошибки

**1. Не снимать обработчики в cleanup.**

```tsx
// ТАК НЕЛЬЗЯ — обработчик останется навсегда
useEffect(() => { window.addEventListener("keydown", handleKeyDown); }, []);
```

При размонтировании обработчик **останется висеть** на `window`; при повторном монтировании
(навигация, HMR, `<StrictMode>` в dev) их станет **два** — пробел поставит на паузу и сразу снимет;
замыкание держит ссылки на состояние и DOM → **утечка памяти**.

```tsx
useEffect(() => {
  window.addEventListener("keydown", handleKeyDown);
  return () => window.removeEventListener("keydown", handleKeyDown);   // ← обязательно
}, [dependencies]);
```

> `addEventListener` **всегда** в паре с `removeEventListener`. То же для `requestAnimationFrame`
> → `cancelAnimationFrame` и `setInterval` → `clearInterval`. И снимать нужно **ту же самую функцию**:
> `addEventListener("keydown", () => fn(e))` + `removeEventListener` с новой стрелкой не сработает.

**2. Пересоздавать `<audio>` при каждом рендере.**

```tsx
// ТАК НЕЛЬЗЯ
function Player({ track }) { return <audio src={buildStreamUrl(track.id)} autoPlay />; }
```

Поставишь `key={Math.random()}` — **элемент уничтожится и создастся заново**, музыка оборвётся
на полуслове. Передашь новый объект трека в зависимость эффекта — эффект сработает зря. У нас защита
ровно от последнего — **зависимость по `id`, а не по объекту**:

```tsx
// Зависимость — именно id трека, а не весь объект. Перерисовка списка
// создаёт НОВЫЙ объект трека с теми же данными; если бы мы зависели от
// объекта, аудио перезагружалось бы на каждой перерисовке.
const currentTrackId = currentTrack?.id ?? null;
useEffect(() => { /* ... */ }, [currentTrackId]);
```

> В зависимостях эффектов используй **примитивы** (число, строку, boolean), а не объекты и массивы.
> Объект сравнивается по ссылке, и новая ссылка = «изменилось».

Второй аспект — **где живёт `<audio>`**. Он у нас в `PlayerProvider` в корневом layout:
*«Благодаря этому `<audio>` НЕ пересоздаётся при переходах между страницами: музыка продолжает играть,
пока ты листаешь библиотеку, плейлисты и историю»*. Если бы он был на странице библиотеки, при переходе
в плейлисты элемент размонтировался бы и музыка оборвалась. **Размещение элемента — архитектурное решение.**

**3. Положить `currentTime` в общий контекст.** Самая коварная ошибка — она **не ломает ничего сразу**,
просто тормозит: `currentTime` меняется 60 раз в секунду → объект значения контекста создаётся заново
каждый рендер → для React «значение изменилось» → **все** потребители перерисовываются.
Список 500 треков × 60 раз в секунду = **30 000 рендеров в секунду**. Три уровня защиты у нас:
**разделение контекстов** (`currentTime` читает **только** `PlayerBar`, список треков на этот контекст
не подписан); **`useMemo` для значений контекста** (объект пересобирается только при реальном изменении);
**`useCallback` для функций** (`actions` не меняются никогда). **Как заметить проблему:**
React DevTools → Profiler → записать взаимодействие и посмотреть, что перерисовывается и почему.

**4. Забыть про `preload` — и качать всю библиотеку.** Если на странице 200 «превью»-плееров
с `preload="auto"`, браузер попытается начать загрузку **всех двухсот файлов**: сотни мегабайт трафика,
забитый канал, сожжённый мобильный трафик. `metadata` — по умолчанию для списков; `none` — если треков
много и играть будут один-два; `auto` — только если файл **точно** сейчас заиграет. И главное:
**не создавай `<audio>` на каждый трек в списке** — один общий элемент на всё приложение.

**5. Игнорировать возвращённый Promise от `play()`.**

```ts
element.play();                    // ПЛОХО: ошибка потеряется, автозапуск не сработает молча
element.play().catch(console.log); // ПЛОХО: ошибка есть, но пользователь не поймёт

// ХОРОШО: понятное сообщение + выключенный индикатор загрузки
element.play().catch(() => {
  setIsLoading(false);
  setError("Браузер заблокировал автозапуск. Нажми ▶");
});
```

**6. Перематывать до `loadedmetadata`.**
`audio.src = ...; audio.currentTime = 137;` — присваивание сбросится в 0, потому что браузер
не знает, сколько байт соответствует 137-й секунде. Запоминай желаемую позицию и применяй её
в обработчике `loadedmetadata` (см. `pendingSeekRef` в разделе 3).

**7. Хранить громкость в процентах.** `const [volume, setVolume] = useState(70); audio.volume = volume;`
— браузер молча зажмёт в `1.0`, а дальше по коду придётся делить на 100 и однажды забыть.
Правильно: `useState(1)`, проценты считать только для показа.

**8. Забыть про `NaN` в `duration`.** До загрузки метаданных `duration === NaN`, у потоков — `Infinity`.
Отсюда `formatDuration(audio.duration)` покажет `"NaN:NaN"`, а `(currentTime / duration) * 100` даст `NaN`.
Защита: `Number.isFinite` в `loadedmetadata`, проверка `duration > 0` при расчёте процента и первая
строка `formatDuration`: `if (!Number.isFinite(totalSeconds) || totalSeconds < 0) return "0:00";`

**9. `max={0}` у ползунка.** `<input type="range" min={0} max={duration} />` — браузер не даст `max=0`,
ползунок «залипнет». У нас защита: `max={max > 0 ? max : 1}`.

**10. Не обрабатывать `ended`.** Музыка остановится, а `isPlaying` останется `true` навсегда — кнопка
будет показывать «пауза», хотя ничего не играет. Пользователь жмёт play, `toggle()` видит
`audio.paused === true` и вызывает `play()`, а трек уже в конце и мгновенно «заканчивается» снова.
Классический залипший интерфейс.

## 14. Шпаргалка

### Наши события — что слушаем и что делаем

| Событие | Когда срабатывает | Что делаем |
| --- | --- | --- |
| `loadedmetadata` | Прочитан заголовок файла, `duration` известна | `setDuration(...)`, `setIsLoading(false)`, применяем отложенный seek |
| `play` | Вызван `play()` — начали **пытаться** играть | `setIsPlaying(true)`, `setError(null)` |
| `playing` | Звук реально пошёл | `setIsPlaying(true)`, `setIsLoading(false)`, **пишем трек в историю** (один раз) |
| `pause` | Поставлено на паузу (кем угодно) | `setIsPlaying(false)` |
| `waiting` | Нехватка данных, буферизация | `setIsLoading(true)` |
| `canplay` | Данных достаточно, чтобы играть | `setIsLoading(false)` |
| `error` | Ошибка воспроизведения/загрузки | `setIsLoading(false)`, `setIsPlaying(false)`, разбираем `audio.error.code` → текст |
| `ended` | Трек доиграл до конца | Повтор: `one` → заново; `all` → дальше/на первый; `off` → стоп |

### События, которые мы НЕ слушаем — и почему

| Событие | Почему |
| --- | --- |
| `timeupdate` | Слишком редкое (~4 раза/сек) — вместо него цикл `requestAnimationFrame` |
| `canplaythrough` | Это **оценка** скорости сети, может врать. Реагируем на факты (`waiting`/`canplay`) |
| `seeked` | Перемотку инициируем только мы — новую позицию знаем сразу |
| `volumechange` | Громкость меняем только мы, значение уже в состоянии React |
| `seeking` | Начало перемотки неинтересно, UI обновляем оптимистично |
| `loadeddata` | `loadedmetadata` покрывает нашу потребность |
| `progress` | Полосу буферизации не рисуем — `waiting`/`canplay` достаточно |
| `stalled` / `suspend` | Отдельным статусом не показываем, диагностируем через DevTools |
| `ratechange` | Скорость воспроизведения мы не меняем |
| `emptied` | Сброс элемента обрабатываем явно в эффекте смены трека |

| Свойство | Чтение | Запись | Диапазон | Заметка |

## 15. Мини-упражнения

**1. Показать, сколько уже буферизовано.** В `SeekBar` добавь полупрозрачную полосу, показывающую
**скачанную** часть — она должна двигаться впереди проигранной. Подсказка: `audio.buffered` — это
`TimeRanges` с `length`, `start(i)`, `end(i)`; при перемотке кусков может быть несколько. Понадобится
прокинуть `buffered` в `TimelineState` и обновлять в цикле `requestAnimationFrame`.
**Что поймёшь:** почему `buffered` и `played` — разные вещи и как выглядят «дырки» после перемотки.

**2. Регулятор скорости воспроизведения.** Кнопка с тремя скоростями: 1× → 1.25× → 1.5× → 1×.
Ставь `audio.playbackRate = rate` и сохраняй значение в localStorage — по образцу громкости
(`STORAGE_VOLUME_KEY`, `readLocalStorage`). **Внимание:** при смене трека `playbackRate`
**сбрасывается в 1**, придётся выставлять заново в эффекте смены трека. Подумай, почему при 2×
голос звучит «бурундуком» (подсказка: `preservesPitch`).

**3. Уведомление при смене трека через `playing`.** Плашка «▶ {исполнитель} — {название}» на 3 секунды
при начале **реально зазвучавшего** трека. Обязательное условие: вешай показ на `playing`, а не на `play`.
**Проверь разницу:** поставь в DevTools throttling сети на `Slow 3G` и запусти трек — `play` сработает
мгновенно, а `playing` через несколько секунд, когда буфер набрался.

**4. Перемотка по клику на полосе.**

```tsx
const handleClick = (event: React.MouseEvent<HTMLDivElement>) => {
  const rect = event.currentTarget.getBoundingClientRect();
  const ratio = (event.clientX - rect.left) / rect.width;   // 0..1
  actions.seek(ratio * duration);
};
```

Не сломай клавиатурную доступность (клик — **дополнение** к ползунку, а не замена); поставь
`aria-hidden="true"` на декоративные слои; разберись, почему `getBoundingClientRect()` даёт координаты
**относительно окна**, а не страницы.

**5. `seekbackward` / `seekforward` в Media Session.**

```tsx
navigator.mediaSession.setActionHandler("seekforward", (details) => {
  const offset = details.seekOffset ?? 10;   // браузер может предложить свой шаг
  // перемотать вперёд на offset секунд
});
```

**Проверь:** в Chrome открой `chrome://media-internals` — там видно, какие действия зарегистрированы
и какие приходят. Попробуй также выставлять `navigator.mediaSession.playbackState = "playing" | "paused" | "none"`
— это подсказка системе о состоянии, влияет на вид кнопок на экране блокировки. **Бонус:** не регистрируй
`seekto`, если `duration` неизвестна, — иначе пользователь получит кнопку, которая ничего не делает.

## Что запомнить

1. **Звуком управляет DOM-элемент, а не React.** React хранит копию состояния для интерфейса.
2. **Источник правды — сам элемент.** Спрашивай `audio.paused`, а не свой флаг.
3. **`play` ≠ `playing`.** `play` — попытка, `playing` — факт. Побочные эффекты — на `playing`.
4. **`play()` возвращает Promise**, и его отказ надо обрабатывать понятным сообщением.
5. **`timeupdate` слишком редкое** — для плавной полосы нужен `requestAnimationFrame`,
   работающий только при `isPlaying`.
6. **Разделяй состояние по частоте изменений.** `currentTime` — в отдельный контекст, иначе
   60 перерисовок в секунду на всём дереве.
7. **Перемотка вперёд возможна только благодаря Range-запросам.** Нет `Accept-Ranges: bytes`
   на сервере — нет перемотки в браузере.
8. **`volume` — это 0..1, а не проценты.** Проценты только для показа.
9. **`preload="metadata"`** спасает от загрузки всей библиотеки разом.
10. **Media Session** делает работающими кнопки на наушниках и экране блокировки.
11. **`pagehide` + `sendBeacon`** — единственный надёжный способ сохранить данные при уходе.
12. **Нативные `<button>` и `<input type="range">`** дают доступность бесплатно, а `aria-valuetext`
    обязателен для ползунка, показывающего время.
