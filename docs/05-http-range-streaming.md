# 05. HTTP Range и стриминг: как байты музыки едут в браузер

Это глава про самый интересный файл проекта —
`src/app/api/tracks/[id]/stream/route.ts`. Здесь ты познакомишься с механикой,
на которой держится весь интернет: видео, музыка, докачка файлов, торренты,
просмотр PDF по частям.

Если поймёшь эту главу, ты будешь понимать больше про HTTP, чем большинство
фронтенд-разработчиков.

---

## 1. Наивное решение и почему оно не годится

Самое простое, что приходит в голову:

```ts
// ❌ ТАК ДЕЛАТЬ НЕ НАДО
export async function GET(_req: Request, { params }) {
  const { id } = await params;
  const track = await getTrackRowById(Number(id));
  const file = await fs.readFile(track.path);   // читаем ВЕСЬ файл в память
  return new Response(file);
}
```

Что здесь плохо:

1. **Память.** FLAC-альбом может весить 300 МБ. Мы загрузим его целиком
   в оперативную память — и так на каждый запрос. Пять одновременных
   слушателей = 1.5 ГБ памяти.
2. **Время до первого звука.** Пользователь ждёт, пока сервер прочитает
   весь файл с диска, прежде чем услышит первую ноту.
3. **Перемотка не работает.** Чтобы перейти на 3-ю минуту, браузеру придётся
   скачать все байты до неё. А в середину трека вообще не попасть, не
   скачав начало.
4. **Нет докачки.** Соединение оборвалось на 90% — придётся качать заново.

---

## 2. Как это решено в HTTP: Range Requests

В 1996 году в HTTP добавили механизм **частичной загрузки** — Range Requests
(сегодня это [RFC 7233](https://datatracker.ietf.org/doc/html/rfc7233)).
Работает он так:

```
1. Браузер:  GET /api/tracks/1/stream
2. Сервер:   200 OK
             Accept-Ranges: bytes          ← «я умею отдавать кусками»
             Content-Length: 8942026       ← «файл весит 8 942 026 байт»

3. Браузер:  GET /api/tracks/1/stream
             Range: bytes=0-1048575        ← «дай первые 1 МБ»
4. Сервер:   206 Partial Content
             Content-Range: bytes 0-1048575/8942026
             Content-Length: 1048576

   …браузер играет эти 1 МБ, буфер подходит к концу…

5. Браузер:  GET /api/tracks/1/stream
             Range: bytes=1048576-2097151  ← «теперь следующий мегабайт»
6. Сервер:   206 Partial Content
             …

   …пользователь тянет ползунок на середину…
   (браузер выбрасывает буфер и делает новый запрос с другого места)

7. Браузер:  GET /api/tracks/1/stream
             Range: bytes=4471013-          ← «дай всё, начиная с этого байта»
8. Сервер:   206 Partial Content
             Content-Range: bytes 4471013-8942025/8942026
```

Главный герой здесь — заголовок **`Accept-Ranges: bytes`**. Пока сервер его
не пришлёт, браузер даже не попробует запрашивать куски, а значит **перемотка
работать не будет**: плеер будет честно ждать загрузки всего файла.

Это очень распространённая ошибка в самодельных стриминг-серверах: файл
отдаётся, музыка играет, но ползунок не двигается.

---

## 3. Анатомия заголовка `Range`

Заголовок приходит в трёх формах, и все три надо уметь разбирать.

| Заголовок | Значение | Что означает |
| --- | --- | --- |
| `Range: bytes=0-1023` | диапазон | байты с 0-го по 1023-й **включительно** (всего 1024 байта) |
| `Range: bytes=1024-` | открытый конец | с 1024-го байта и до конца файла |
| `Range: bytes=-500` | суффикс | **последние 500 байт** файла (не «с 0 по 500»!) |

Последняя форма — источник классической путаницы. `bytes=-500` означает
«взять хвост», а не «от нуля до пятисот».

### Главная ловушка: границы включительные

И `start`, и `end` в HTTP **включаются** в диапазон. Поэтому длина куска
считается так:

```
размер = end - start + 1
```

Забыть `+ 1` — самая частая ошибка. Браузер получит на один байт меньше,
чем ему обещали в `Content-Length`, и в лучшем случае просто дёрнется
при воспроизведении, в худшем — решит, что файл повреждён.

### Ещё одна ловушка: `bytes=0-0` — это ОДИН байт

Ноль-ноль — это не «пустой диапазон», а «первый байт». Некоторые плееры
используют такой запрос, чтобы просто проверить, поддерживает ли сервер
частичную загрузку.

## 4. Разбор кода: функция `parseRangeHeader`

Находится в `src/app/api/tracks/[id]/stream/route.ts`. Разберём её по частям.

```ts
function parseRangeHeader(
  rangeHeader: string | null,
  fileSize: number,
): { start: number; end: number } | "invalid" | null {
```

Обрати внимание на **возвращаемый тип**: `{start, end} | "invalid" | null`.
Это union из трёх вариантов, и каждый означает своё:

* `{ start, end }` — заголовок был, разобрали успешно;
* `null` — заголовка не было вообще (отдаём файл целиком, статус 200);
* `"invalid"` — заголовок был, но бессмысленный (отдаём 416).

Такая «честная» типизация заставляет вызывающий код обработать **все три**
случая — TypeScript не даст забыть.

```ts
if (!rangeHeader) return null;
if (!rangeHeader.startsWith("bytes=")) return "invalid";
```

Единицы измерения в спецификации бывают разные, но на практике для файлов
используют только байты. Всё остальное — не наш случай.

```ts
const spec = rangeHeader.slice("bytes=".length).trim();
if (spec.includes(",")) return "invalid";
```

Множественные диапазоны (`bytes=0-100,200-300`) в спецификации есть, но
браузеры их для `<audio>` не используют, а реализация ответа
`multipart/byteranges` заметно усложнила бы код. Мы сознательно отказываемся
и отвечаем 416. Это нормальное инженерное решение — при условии, что оно
осознанное и задокументировано.

```ts
const dashIndex = spec.indexOf("-");
const rawStart = spec.slice(0, dashIndex).trim();
const rawEnd = spec.slice(dashIndex + 1).trim();
```

Дальше — три ветки.

### Ветка 1: суффиксный запрос `bytes=-500`

```ts
if (rawStart === "") {
  const suffixLength = Number(rawEnd);
  if (!Number.isInteger(suffixLength) || suffixLength <= 0) return "invalid";

  const start = Math.max(0, fileSize - suffixLength);
  return { start, end: fileSize - 1 };
}
```

`Math.max(0, ...)` защищает от случая «файл меньше, чем просят»: если
запросили последние 500 байт, а в файле всего 100, вернём весь файл
(с 0-го по 99-й). Так велит спецификация.

### Ветка 2: открытый конец `bytes=1024-`

```ts
if (rawEnd === "") {
  return { start, end: fileSize - 1 };
}
```

`end = fileSize - 1`, потому что последний байт файла имеет индекс
«размер минус один» (нумерация с нуля).

### Ветка 3: обычный диапазон

```ts
if (start >= fileSize) return "invalid";
return { start, end: Math.min(parsedEnd, fileSize - 1) };
```

Тут два важных момента:

* если начало за пределами файла — отдать нечего, это 416;
* если конец запрошен больше, чем есть, — **обрезаем**, а не ругаемся.
  Спецификация требует именно такого поведения.

## 5. Потоки: как отдать файл, не читая его целиком

Наивный вариант `fs.readFile` мы уже отвергли. Правильный инструмент —
**поток** (stream).

### Что такое поток

Поток — это способ обрабатывать данные **по частям, по мере поступления**,
вместо того чтобы держать их целиком.

Аналогия: вместо того чтобы вылить в рот сразу ведро воды, ты пьёшь из
трубочки. Ведро (файл) существует, но в тебе (в памяти) в каждый момент
времени — только глоток.

```ts
import { createReadStream } from "node:fs";

const stream = createReadStream(track.path, { start, end });
```

`createReadStream` не читает файл сразу. Он возвращает объект-поток, который
начнёт читать, когда кто-то начнёт «потреблять» данные (или сразу, если
потребитель уже подключён). Внутри он читает файл кусками по умолчанию
по 64 КБ.

В нашем случае память на один запрос: **64 КБ вместо 300 МБ**.

### Два вида потоков

Тут начинается неочевидное.

| | Node.js-потоки | Web Streams |
| --- | --- | --- |
| Откуда | `node:stream` (`Readable`, `Writable`) | стандарт веб-платформы (`ReadableStream`) |
| Где | только на сервере в Node/Bun | в браузере, в `fetch`, в Service Worker |
| Создание | `createReadStream(...)` | `new ReadableStream({ ... })` |

`Response` ожидает **веб-поток** (`ReadableStream`). А `createReadStream`
возвращает **Node.js-поток**. Поэтому нужен переходник:

```ts
import { Readable } from "node:stream";

const nodeStream = createReadStream(track.path, { start, end });
return Readable.toWeb(nodeStream) as unknown as ReadableStream;
```

`Readable.toWeb()` — стандартная функция Node.js для этого преобразования.
Приведение типа `as unknown as ReadableStream` нужно потому, что TypeScript
считает `ReadableStream` из `node:stream/web` и глобальный `ReadableStream`
разными типами, хотя фактически это одно и то же (классическая мелкая
нестыковка типов).

### Альтернатива для Bun

Раз проект работает на Bun, можно написать короче:

```ts
const file = Bun.file(track.path);
return new Response(file.slice(start, end + 1), { status: 206, headers });
```

`Bun.file()` ленивый — он не читает файл, пока данные не понадобятся,
и умеет отдавать срез без копирования в память. Это быстрее.

Почему всё-таки выбран `node:fs`:

1. код останется рабочим, если проект однажды переедет на Node;
2. явный `createReadStream` нагляднее показывает, что такое поток.

Если захочешь ускорить — в файле отмечено, где именно это менять: буквально
две строки в функции `createFileStream`.

## 6. Коды ответа, которые мы используем

| Код | Когда | Тело |
| --- | --- | --- |
| `200 OK` | `Range` не запрошен — отдаём файл целиком | поток файла |
| `206 Partial Content` | `Range` корректен — отдаём кусок | поток куска |
| `304 Not Modified` | браузер прислал `If-None-Match`, совпадающий с нашим ETag | пусто |
| `400 Bad Request` | некорректный `id` в URL | JSON с ошибкой |
| `401 Unauthorized` | неверный или отсутствующий токен доступа | JSON с ошибкой |
| `404 Not Found` | трека нет в базе или файл пропал с диска | JSON с ошибкой |
| `416 Range Not Satisfiable` | диапазон за пределами файла | пусто + `Content-Range: bytes */размер` |

Запомнить легко: **2xx — всё хорошо, 4xx — виноват клиент, 5xx — виноват
сервер**.

## 7. Заголовки ответа: что зачем

```ts
return new Response(stream, {
  status: 206,
  headers: {
    "Content-Type": "audio/mpeg",
    "Content-Length": String(chunkSize),
    "Content-Range": `bytes ${start}-${end}/${fileSize}`,
    "Accept-Ranges": "bytes",
    "Last-Modified": lastModified.toUTCString(),
    ETag: etag,
    "Cache-Control": "public, max-age=86400",
  },
});
```

### `Content-Type`

Говорит браузеру, **что** за данные пришли. Если соврать (например, всегда
писать `application/octet-stream`), тег `<audio>` откажется играть файл.
Определяется по расширению через таблицу `AUDIO_MIME_TYPES`.

### `Content-Length`

Длина **именно этого ответа**, а не файла. Для куска — размер куска.

### `Content-Range`

Только в ответе 206. Формат: `bytes НАЧАЛО-КОНЕЦ/ВСЕГО`. Это ответ на вопрос
«какой именно кусок ты мне дал и сколько всего в файле».

В ответе 416 формат другой: `bytes */8942026` — звёздочка вместо диапазона
означает «никакой кусок я тебе не дам, вот тебе реальный размер».

### `Accept-Ranges: bytes`

Самый важный заголовок для перемотки. Без него браузер не станет
запрашивать куски.

### `ETag` и `Last-Modified`

`ETag` — «отпечаток версии файла». Мы строим его из размера и времени
изменения:

```ts
const etag = `"${fileSize}-${lastModified.getTime()}"`;
```

Браузер запоминает ETag и при следующем запросе присылает его обратно
в заголовке `If-None-Match`: «а у меня уже есть эта версия». Если отпечаток
совпадает — отвечаем `304 Not Modified` **без тела**. Экономия трафика
на повторных запросах.

### `Cache-Control`

```ts
"Cache-Control": "public, max-age=86400",   // аудио: кэшировать сутки
```

А вот у обложек стратегия другая:

```ts
"Cache-Control": "public, max-age=31536000, immutable"   // год + immutable
```

`immutable` означает «этот файл никогда не изменится». Мы можем себе это
позволить, потому что имя файла обложки — это SHA-1 от её содержимого.
Если картинка изменится, изменится и имя, а значит и URL. Это приём
**content-addressed storage**: по нему работают git (объекты по SHA)
и Docker (слои по digest).

## 8. Запросы HEAD

Иногда плеер перед загрузкой посылает запрос методом `HEAD`: «расскажи
про файл, но тело не присылай». Это дешевле, чем качать мегабайты ради того,
чтобы узнать длину.

Мы обрабатываем `HEAD` **той же функцией**, что и `GET`, но с флагом:

```ts
function createFileStream(filePath, start, end, isHeadRequest): BodyInit | null {
  if (isHeadRequest) return null;   // тела нет, но заголовки те же
  // …
}
```

## 9. Токен доступа: простая защита без авторизации

```ts
function checkAccessToken(request: Request): boolean {
  const expected = process.env.STREAM_TOKEN?.trim();
  if (!expected) return true;                       // токен не настроен — пускаем всех

  const url = new URL(request.url);
  const fromQuery = url.searchParams.get("token");
  const fromHeader = request.headers.get("x-stream-token");

  return fromQuery === expected || fromHeader === expected;
}
```

Зачем это нужно: плеер, запущенный дома, слушает сетевой интерфейс и доступен
всем в той же сети. Если у тебя гости или соседи по Wi-Fi — они смогут
скачать твою музыку. Токен это закрывает.

Почему это **не** «настоящая авторизация»: настоящая — это логины, пароли,
сессии, роли. ТЗ прямо просит не усложнять. Токен решает конкретную задачу
и не требует ни базы пользователей, ни библиотек.

Важно понимать ограничения: токен в URL попадает в историю браузера и в логи
сервера. Для чего-то серьёзного так делать нельзя.

## 10. Безопасность: выход за пределы каталога (Path Traversal)

Опасный код выглядел бы так:

```ts
// ❌ УЯЗВИМОСТЬ
const requestedFile = new URL(request.url).searchParams.get("file");
return new Response(createReadStream(path.join(COVERS_DIR, requestedFile)));
```

Злоумышленник запрашивает:

```
/api/covers?file=../../../../etc/passwd
```

`path.join` честно склеит путь, `..` выведут за пределы папки обложек,
и сервер отдаст файл с паролями системы. Это называется **path traversal**
(выход за пределы каталога).

Защита в `src/app/api/tracks/[id]/cover/route.ts`:

```ts
const coversRoot = path.resolve(COVERS_DIR);
const candidate = path.resolve(coversRoot, track.coverFile);

// path.sep важен: без него "/data/covers2" прошёл бы проверку на префикс "/data/covers"
if (!candidate.startsWith(coversRoot + path.sep)) {
  return jsonError("Недопустимый путь к обложке", 400);
}
```

Два уровня защиты:

1. имя файла приходит **из нашей базы**, а не из URL — уже хорошо;
2. даже если бы пришло из URL, проверка префикса отсечёт выход наружу.

## 11. Проверь сам: эксперименты с curl

Лучший способ понять эту главу — потрогать руками. Запусти `bun run dev`
и выполни по очереди.

**Узнать размер и поддержку Range:**

```bash
curl -s -I http://127.0.0.1:3000/api/tracks/1/stream
```

Ищи в ответе `Accept-Ranges: bytes` и `Content-Length`.

**Запросить первые 1024 байта:**

```bash
curl -s -D - -o /dev/null -H "Range: bytes=0-1023" \
  http://127.0.0.1:3000/api/tracks/1/stream
```

Ожидаемо: `206 Partial Content` и `Content-Range: bytes 0-1023/8942026`.

**Поиграть с формами диапазона:**

```bash
# последние 500 байт
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" \
  -H "Range: bytes=-500" http://127.0.0.1:3000/api/tracks/1/stream

# с середины и до конца
curl -s -o /dev/null -w "%{http_code} %{size_download}\n" \
  -H "Range: bytes=1000000-" http://127.0.0.1:3000/api/tracks/1/stream

# диапазон за пределами файла → 416
curl -s -o /dev/null -w "%{http_code}\n" \
  -H "Range: bytes=999999999-" http://127.0.0.1:3000/api/tracks/1/stream
```

**Сравнить размеры:** сохрани первые 1000 байт и первые 2000 байт — второй
файл будет начинаться с тех же байт и будет ровно в два раза длиннее. Так
и работает перемотка: браузер просто берёт другой кусок.

**Проверить кэш:** повтори запрос с заголовком `If-None-Match`, подставив
ETag из предыдущего ответа — получишь `304 Not Modified` без тела.

## 12. Частые ошибки

| Ошибка | Последствие |
| --- | --- |
| не отдавать `Accept-Ranges: bytes` | перемотка не работает вообще |
| `Content-Length = end - start` (забыл `+ 1`) | браузер получает на байт меньше, звук рвётся |
| считать `end` исключительным | теряется последний байт каждого куска |
| читать файл целиком в память | сервер съедает гигабайты на несколько слушателей |
| не проверять, что файл существует | ошибка 500 вместо понятного 404 |
| не обрабатывать `start >= fileSize` | отдаём 200 с пустым телом вместо 416 |
| отдавать `Content-Range` в ответе 200 | клиент запутается |
| всегда отвечать 200 на `Range` | браузер скачает весь файл, перемотка «залипнет» |
| `path.join` без проверки на `..` | уязвимость path traversal |

## Итог

Три вещи, которые стоит унести из этой главы:

1. **HTTP умеет отдавать часть файла** — и это не экзотика, а то, на чём
   держится всё видео и аудио в интернете.
2. **Потоки экономят память** — вместо «прочитай 300 МБ» говорим «читай
   по 64 КБ и отдавай по мере поступления».
3. **Заголовки — это контракт.** `Accept-Ranges`, `Content-Range`,
   `Content-Length` — не украшение ответа, а инструкции для клиента.
   Ошибёшься в них — плеер не заработает, даже если данные «правильные».
