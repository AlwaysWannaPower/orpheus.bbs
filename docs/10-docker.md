# 10. Docker: упаковать плеер и запускать одной командой

Конспект по последнему этапу проекта. Docker ты знаешь поверхностно, поэтому начинаем с
нуля и доходим до двух реальных файлов: `Dockerfile` и `docker-compose.yml`.

**Главная мысль:** Docker нужен не «чтобы модно», а чтобы цель из ТЗ работала одинаково на
любом компьютере:

```bash
git clone <репозиторий> && cd orpheus-bbs
# положил музыку в ./music
docker compose up -d
# открыл http://localhost:3000
```

## 1. Какую боль решает Docker

Отдал проект другу. Он клонирует и делает `bun install && bun run start`. И получает:
`command not found: bun`; потом версия Bun не та (у него 1.1, проекту нужна 1.4.2 — см.
`packageManager` в `package.json`); потом не та версия Node для Next.js 16; а ещё проект
использует модуль `bun:sqlite`, которого в Node.js нет вообще.

Это классическая боль **«у меня работает, а у тебя нет»**. Код одинаковый — разное
**окружение**: рантайм, его версия, системные библиотеки, переменные, права. Docker решает
её радикально: упаковывает **приложение вместе с его окружением** в один переносимый образ.
Внутри уже лежит нужный Linux, нужный Bun нужной версии, все зависимости. Наружу торчит
только твой код и твои настройки.

**Технически в двух словах:** контейнер — не виртуальная машина. Это обычный процесс на
твоём компьютере, которого ядро Linux заставило думать, что он живёт в отдельной системе:
своя файловая система, свои процессы, своя сеть, свои переменные окружения. Поэтому старт за
секунды, а не за минуты, и никаких гигабайт памяти, как у ВМ.

**Чего Docker НЕ делает:** не спасает от логических ошибок в коде и не заменяет тесты. И он
не нужен, пока приложение не работает локально — в ТЗ написано прямо: «только после того, как
приложение нормально работает локально».

## 2. Образ (image) против контейнера (container)

**Образ — это чертёж. Контейнер — то, что запущено по чертежу.** Точная аналогия из
программирования: класс и объект. Из одного класса можно создать сто объектов — из одного
образа запустить сто контейнеров.

| | Образ (image) | Контейнер (container) |
| --- | --- | --- |
| Что это | **Только для чтения:** рантайм, код, зависимости | Запущенный процесс + тонкий записываемый слой сверху |
| Где видно | `docker images` | `docker ps` |
| Можно менять | Нет, только собрать новый | Да, внутрь можно писать |
| Удалил | Пропал, но собирается заново | **Пропало всё, что писалось внутрь контейнера** |

**Здесь спрятан ответ на вопрос «удалю контейнер — данные не пропадут?»** Сам по себе:
**всё, что приложение писало внутрь контейнера, пропадёт.** Поэтому данные (базу, музыку)
выносят наружу в тома — тогда они переживут и удаление контейнера, и пересборку образа
(раздел 7).

## 3. Слои образа и кэш слоёв

Образ — не монолит, а **стопка слоёв**: каждая инструкция Dockerfile (`FROM`, `RUN`, `COPY`,
`ENV`...) создаёт слой — «снимок того, что изменилось на этом шаге».

```
образ music-player
├── слои 7-8 ← CMD, HEALTHCHECK                       (метаданные)
├── слой 6   ← COPY --from=builder /app/drizzle       (миграции, ~2 КБ)
├── слой 5   ← COPY --from=builder /app/.next         (собранный Next.js)
├── слой 4   ← COPY --from=builder /app/node_modules  (зависимости, сотни МБ)
└── слой 2   ← FROM oven/bun:1-alpine                 (Alpine + Bun, ~78 МБ)
```

Слои только для чтения и **переиспользуются между образами**: если у тебя десять проектов на
`oven/bun:1-alpine`, базовый слой лежит на диске один раз.

**Кэш слоёв** — отсюда же: Docker запоминает результат каждого шага и сверяет с «входными
данными» шага. Для `RUN bun install` это `package.json` и `bun.lock`, для `COPY . .` — вообще
все файлы проекта.

```
входные данные не изменились  →  слой из кэша, шаг НЕ выполняется
входные данные изменились     →  слой пересобирается, И ВСЕ СЛОИ ПОСЛЕ НЕГО ТОЖЕ
```

**Поэтому порядок инструкций в Dockerfile — не косметика, а скорость.** Поставишь
`COPY . .` раньше `bun install` — и правка запятой в комментарии будет переустанавливать все
зависимости заново: минуты вместо секунд.

## 4. Зачем Docker именно этому проекту

Плеер на Next.js 16 + Bun + SQLite, без прод-сервера в облаке. Конечная цель по ТЗ —
**переносимость**: музыка лежит отдельно от приложения в `./music`, база и обложки — в
`./data`. Docker даёт три вещи: **одинаковый рантайм** (внутри всегда `oven/bun:1-alpine`, не
важно, что стоит у тебя); **разделение музыки и приложения** (образ не содержит ни одной mp3
— музыка монтируется томом, образ весит сотни мегабайт вместо десятков гигабайт); **запуск
одной командой** вместо инструкции на полторы страницы.

## 5. Разбор `Dockerfile` построчно

`Dockerfile` — рецепт сборки, читается сверху вниз, лежит в корне проекта. Вот его костяк с
разбором каждой инструкции:

```dockerfile
# FROM — ОБЯЗАТЕЛЬНАЯ первая строка: «возьми готовый образ и работай поверх него».
# oven/bun — официальный образ от разработчиков Bun; 1-alpine — мажорная версия Bun
# + вариант на базе Alpine Linux, самый компактный (~78 МБ против ~200 МБ на Debian).
# AS deps — имя этапа, пригодится в COPY --from=deps.
FROM oven/bun:1-alpine AS deps

# WORKDIR — рабочая папка для всех последующих инструкций, аналог постоянного cd.
# Папки нет — Docker создаст. См. врезку ниже, почему для нас это критично.
WORKDIR /app

# COPY — скопировать файлы: COPY <что> <куда>, где точка в конце = WORKDIR.
# Видов два: с хоста (COPY . .) и из предыдущего этапа (COPY --from=...).
COPY package.json bun.lock ./

# RUN — выполнить команду ВО ВРЕМЯ СБОРКИ (один раз), результат впечатать в слой.
# Не путать с CMD: тот выполняется при КАЖДОМ запуске контейнера.
RUN bun install --frozen-lockfile

# ENV — переменные окружения внутри контейнера. Их читает src/lib/config.ts.
ENV NODE_ENV=production
ENV MUSIC_DIR=/music
ENV DB_PATH=/data/music.db
ENV COVERS_DIR=/data/covers
ENV PORT=3000

# EXPOSE — ДОКУМЕНТАЦИЯ, а не проброс: «этот контейнер слушает порт 3000».
# Реальный проброс делает флаг -p 3000:3000 или секция ports в compose.
EXPOSE 3000

# CMD — что запускать при старте контейнера (подробно в 5.1).
CMD ["bun", "run", "start"]
```

**`ENV` читает `src/lib/config.ts`:**

```ts
export const MUSIC_DIR  = absoluteFromEnv(process.env.MUSIC_DIR,  path.join(projectRoot, "music"));
export const DB_PATH    = absoluteFromEnv(process.env.DB_PATH,    path.join(projectRoot, "data", "music.db"));
export const COVERS_DIR = absoluteFromEnv(process.env.COVERS_DIR, path.join(projectRoot, "data", "covers"));
export const PORT       = Number(process.env.PORT ?? 3000);
```

Зачем они тут, если то же самое дублируется в compose? Чтобы контейнер работал и **без**
compose: запустил `docker run -p 3000:3000 music-player` — приложение всё равно найдёт
правильные пути (compose потом просто перекрывает их, см. 6.6). Обрати внимание на
`absoluteFromEnv`: путь `/music` абсолютный, `path.resolve` вернёт его как есть, и вопрос
«какая сейчас рабочая папка» перестаёт быть проблемой.

> **Почему `WORKDIR` — не мелочь.** В `src/lib/db/client.ts` миграции ищутся так:
> `migrate(db, { migrationsFolder: path.resolve(process.cwd(), "drizzle") })`. `process.cwd()`
> — рабочая папка процесса, а это ровно `WORKDIR`, то есть `/app`. Значит, миграции будут
> искаться в `/app/drizzle` — отсюда требование скопировать папку `drizzle/` в финальный
> образ, иначе таблиц в базе не появится.

### 5.1 `CMD`: две формы, и разница принципиальна

```dockerfile
CMD ["bun", "run", "start"]   # exec-форма (массив JSON) — ПРАВИЛЬНО
CMD bun run start             # shell-форма (строка) — так не надо
```

**Shell-форма** запускает команду через `/bin/sh -c "bun run start"`. Главный процесс в
контейнере — `sh`, а Bun — дочерний. При остановке Docker посылает `SIGTERM` процессу номер
один, то есть `sh`, а `sh` сигнал дальше не передаёт: Bun его не получает и не может аккуратно
завершиться (закрыть базу, дописать WAL). **Exec-форма** запускает процесс напрямую, и
`SIGTERM` приходит самому Bun.

Деталь про наш `CMD ["bun", "run", "start"]`: команда `bun run start` читает скрипт `start` из
`package.json`, а он такой — `"start": "bun --bun next start"`. То есть запуск идёт в два шага,
и `--bun` срабатывает внутри скрипта (раздел 5.4).

### 5.2 `HEALTHCHECK`: Docker проверяет, что приложение живо

```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=10s --retries=3 \
  CMD wget -q --spider http://127.0.0.1:3000/api/tracks || exit 1
```

`--interval=30s` — как часто проверять; `--timeout=5s` — сколько ждать ответа;
`--start-period=10s` — «дай приложению проснуться, не ругайся»; `--retries=3` — сколько
провалов подряд до статуса `unhealthy`. Сама проверка: `wget --spider` делает HTTP-запрос и
**не скачивает тело**; роут `/api/tracks` в проекте есть (`src/app/api/tracks/route.ts`);
`|| exit 1` — любой другой исход значит «нездоров». `wget` уже входит в Alpine, ставить не
нужно.

Практический результат: `docker ps` покажет `Up 2 minutes (healthy)`, а если приложение не
отвечает — `Up 1 minute (unhealthy)`. Спасает от ситуации «контейнер вроде `Up`, а сайт не
открывается».

### 5.3 Multi-stage build: зачем три этапа

```dockerfile
FROM oven/bun:1-alpine AS deps     # ЭТАП 1: поставить зависимости
FROM oven/bun:1-alpine AS builder  # ЭТАП 2: собрать приложение
FROM oven/bun:1-alpine AS runner   # ЭТАП 3: то, что реально поедет
```

**Ключевое правило: в финальный образ попадает ТОЛЬКО последний этап.** Всё остальное
выбрасывается — кроме того, что ты явно скопировал через `COPY --from=`.

| Этап | Что делает | Что ему нужно |
| --- | --- | --- |
| `deps` | `bun install --frozen-lockfile` | `package.json`, `bun.lock` |
| `builder` | `bun --bun run build` | весь код + зависимости |
| `runner` | только запуск | `node_modules`, `.next`, `public`, `drizzle`, конфиги |

Для **сборки** нужны исходники, dev-зависимости, компилятор — сотни мегабайт; для **запуска**
из этого нужно процентов десять. В одноэтапной сборке `src/`, `drizzle-kit`, `typescript`,
`eslint`, `tailwindcss` поехали бы в продакшн-образ «на всякий случай»: лишний вес, лишнее
время загрузки, лишняя поверхность для атаки. Копируется в финал только необходимое:

```dockerfile
COPY --from=builder /app/node_modules ./node_modules   # нужны в рантайме
COPY --from=builder /app/.next ./.next                 # Next.js уже собрал код из src/
COPY --from=builder /app/public ./public               # статика
COPY --from=builder /app/package.json ./package.json   # без него `bun run start` не найдёт скрипт
COPY --from=builder /app/next.config.ts ./next.config.ts
COPY --from=builder /app/tsconfig.json ./tsconfig.json
```

**Папки `src/` в финальном образе нет и быть не должно** — Next.js скомпилировал её в `.next`.

> **Почему `drizzle/` копируется отдельно и почему это критично.** Миграции — SQL-файлы,
> которые Next.js не компилирует и не пакует в `.next`; он читает их с диска в момент старта
> (`migrate()` в `client.ts`). Уберёшь строку — контейнер запустится, сайт откроется, а на
> первом запросе к базе получишь `no such table: tracks`. В комментарии Dockerfile это прямо
> названо «ОБЯЗАТЕЛЬНА».

### 5.4 САМОЕ ВАЖНОЕ: почему везде `bun --bun ...`, а не просто `bun run ...`

```json
// package.json
"dev": "bun --bun next dev",  "build": "bun --bun next build",  "start": "bun --bun next start"
```

```dockerfile
# Dockerfile
RUN bun --bun run build
CMD ["bun", "run", "start"]     # → внутри package.json стоит bun --bun next start
```

**Что такое `--bun`.** Когда ты пишешь `bun run next`, Bun берёт исполняемый файл
`node_modules/.bin/next` и запускает его. А у такого файла внутри первая строка (shebang)
примерно такая: `#!/usr/bin/env node` — то есть «запусти меня **Node.js**». По умолчанию
`bun run` уважает shebang и действительно запускает CLI через Node.js: Bun выступает
менеджером пакетов, а само приложение крутится на Node. **Флаг `--bun` это правило ломает:**
«плюнь на shebang, выполняй этот скрипт **моим** рантаймом». После этого весь процесс Next.js
— и серверный, и тот, что выполняет твой серверный код, — работает на Bun.

**Почему для нас это не стилистика, а работоспособность.** База открывается так
(`src/lib/db/client.ts`):

```ts
import { Database } from "bun:sqlite";
import { drizzle, type BunSQLiteDatabase } from "drizzle-orm/bun-sqlite";
import { migrate } from "drizzle-orm/bun-sqlite/migrator";
```

`bun:sqlite` — **встроенный модуль рантайма Bun**. У него нет версии в npm, и в Node.js его не
существует: это не библиотека, а часть самого Bun. Теперь представь, что флага нет:

```
контейнер стартует                       → OK
Next.js поднимается                      → OK
браузер открывает http://localhost:3000  → OK
пользователь жмёт «СКАНИРОВАТЬ»          → 💥  Error: Cannot find module "bun:sqlite"
```

**Сайт открывается, а падает первое же обращение к базе.** «Открыть страницу» и «прочитать
треки из SQLite» — разные вещи, и вторая требует рантайма Bun.

| Команда | Что происходит | Работает? |
| --- | --- | --- |
| `bun run start` | CLI `next` и приложение выполняются Node.js | ❌ нет `bun:sqlite` |
| `bun --bun run start` | всё выполняется рантаймом Bun | ✅ работает |
| `node node_modules/.bin/next start` | Node.js напрямую | ❌ то же самое |

**Одной строкой: `--bun` делает Bun не менеджером пакетов, а рантаймом приложения. Без него
плеер теряет единственный доступ к базе данных.**

### 5.5 Кэш и `--frozen-lockfile`

```dockerfile
COPY package.json bun.lock ./       # сначала ТОЛЬКО описание зависимостей
RUN bun install --frozen-lockfile
# ... и только ПОТОМ, на этапе builder:
COPY . .
```

Правило из раздела 3: **что меняется редко — раньше, что меняется часто — позже.**
`package.json` и `bun.lock` меняются, когда ставишь новый пакет (раз в месяц); `src/**`
меняется каждый раз, когда правишь код.

```
ПЛОХОЙ ПОРЯДОК                          НАШ ПОРЯДОК
COPY . .            ← правка буквы        COPY package.json bun.lock ./  ← не менялись → кэш ВАЛИДЕН
RUN bun install ... ← кэш сброшен,        RUN bun install ...            ← кэш ВАЛИДЕН, 0 секунд
                      ставим заново (мин) COPY . .                       ← пересобирается только отсюда
```

На практике для этого проекта разница — «2 секунды» против «2 минуты» на каждую правку.

**Что делает `--frozen-lockfile`.** `bun.lock` — lock-файл: точные версии всех пакетов с
контрольными суммами. `package.json` говорит `"drizzle-orm": "^0.45.3"` — «подойдёт любая
0.45.x», а lock-файл говорит `0.45.3` — точно. Флаг означает **«не трогай lock-файл вообще»**:
обычный `bun install` может его обновить, а с флагом установка упадёт с ошибкой, если
`package.json` и `bun.lock` разошлись. **Зачем это в Docker:** воспроизводимость — соберёшь
образ сегодня, через год, на другом компьютере, и встанут ровно те же версии. Практическое
следствие: **добавил пакет — обнови `bun.lock` локально и закоммить**, иначе сборка Docker
упадёт (и это правильное поведение, а не баг).

### 5.6 Про пользователя `bun`

В финальном этапе закомментированы `RUN chown -R bun:bun /app /data` и `USER bun`. По
умолчанию процессы в контейнере работают от `root` — плохая практика: найдись в приложении
уязвимость, злоумышленник получит root. В образе `oven/bun` уже есть готовый непривилегированный
пользователь `bun`. Почему закомментировано: как только скажешь `USER bun`, контейнер не сможет
писать в `/data` — папка на хосте принадлежит тебе (uid 1000), а `bun` в контейнере другой uid;
придётся выдавать права и внутри контейнера, и на хосте. Захочешь выставить плеер в интернет —
включай.

### 5.7 Зачем `.dockerignore`

Работает как `.gitignore`, только для Docker: что **не** копировать при `COPY . .`.

| Исключено | Почему |
| --- | --- |
| `node_modules`, `.next` | внутри ставятся и собираются заново, под Alpine; хостовый мусор путает |
| `.git` | история репозитория весит десятки мегабайт и в образе не нужна |
| **`music`** | **там гигабайты mp3 — они монтируются томом, внутрь образа им нельзя** |
| **`data`** | база и обложки тоже монтируются томом |
| `.env`, `.env.local` | **секреты не должны попадать в образ: образ можно скачать и распаковать** |
| `*.log`, `.DS_Store`, `.bun-install`, `.bun-tmp` | мусор и локальный кэш Bun |
| `docs`, `README.md`, `AGENTS.md`, `CLAUDE.md`, `Техническое задание.md` | в runtime-образе не нужны, только увеличивают его |

**Три причины существования файла:** **скорость** (`COPY . .` копирует всё, что не исключено, а
20 ГБ музыки — это сборка на вечность); **кэш** (лишние файлы меняются постоянно и сбрасывают
слои); **безопасность** (секреты не должны попадать в образ). Проверить, что музыка не попала
внутрь: `docker run --rm -it music-player ls -la /music` покажет пустую папку — её создал
`RUN mkdir -p /music`, а музыка приходит только томом.

## 6. Разбор `docker-compose.yml` построчно

`Dockerfile` описывает, **как собрать образ**. Но чтобы запустить контейнер, нужно ещё решить:
какой порт открыть, какие папки смонтировать, какие переменные задать, что делать при
перезагрузке. Можно каждый раз писать длинную команду:

```bash
docker run -d --name music-player -p 3000:3000 -v ./music:/music:ro -v ./data:/data \
  -e MUSIC_DIR=/music -e DB_PATH=/data/music.db --restart unless-stopped music-player
```

А можно один раз записать в файл. **Compose — это описание запуска в виде файла**, и
конфигурация лежит в репозитории рядом с кодом, а не в чьей-то голове и не в истории команд.

```yaml
services:                    # сервисы = контейнеры проекта. У нас он один
  orpheus-bbs:               # имя сервиса; оно же сетевое имя: http://orpheus-bbs:3000
    build:                   # откуда взять образ
      context: .             # контекст сборки — папка, доступная инструкциям COPY
      dockerfile: Dockerfile # какой файл читать
    container_name: orpheus-bbs    # без этого Docker придумает имя вида a3f9c1b2
    ports:
      - "3000:3000"          # СНАРУЖИ:ВНУТРИ
    volumes:
      - ./music:/music:ro    # ПАПКА_НА_ХОСТЕ:ПАПКА_В_КОНТЕЙНЕРЕ[:режим]
      - ./data:/data
    environment:             # перекрывает ENV из Dockerfile
      NODE_ENV: production
      MUSIC_DIR: /music
      DB_PATH: /data/music.db
      COVERS_DIR: /data/covers
      # STREAM_TOKEN: смени-меня            ← необязательный токен, раздел 13
      #                                       (ОБЯЗАТЕЛЬНО только эта строка,
      #                                        NEXT_PUBLIC_* здесь не работает)
    restart: unless-stopped  # поднимать после перезагрузки ПК, но не возвращать после stop
    logging:                 # ротация логов, чтобы не занять весь диск
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"
```

Разберём ключевые секции подробнее.

**`services`.** Внутри перечисляются сервисы. Отступы в YAML — синтаксис, а не украшение: два
пробела означают вложенность, табы запрещены. Секции `version:` в файле нет, и это правильно —
в Compose V2 она устарела и только выдаёт предупреждение.

**`build`.** `context: .` = корень проекта; именно его фильтрует `.dockerignore`.
Альтернатива — `image: user/name:tag`, если образ уже лежит в реестре (Docker Hub, GHCR):
тогда `docker compose up` его просто скачает.

**`ports` — формат «СНАРУЖИ:ВНУТРИ».** Самая частая точка непонимания:

```text
     3000 : 3000
       ↑      ↑
       │      └─ порт ВНУТРИ контейнера (то, что в EXPOSE 3000)
       └──────── порт НА ТВОЁМ КОМПЬЮТЕРЕ (на хосте)
```

Читается: «слушай на порту 3000 моего компьютера и передавай всё, что туда пришло, на порт
3000 в контейнере». Варианты: `"8080:3000"` — сайт на `localhost:8080`, приложение внутри
всё так же на 3000; `"3000"` — Docker выберет случайный порт (узнать:
`docker compose port music-player 3000`); `"127.0.0.1:3000:3000"` — доступно только с этого
компьютера, не из локальной сети. **Меняя левое число, ты не меняешь ничего внутри
приложения.** Правое трогать не надо никогда: оно прибито к `EXPOSE 3000`, `ENV PORT=3000` и к
тому, что слушает Next.js. Кавычки обязательны: без них `3000:3000` YAML разберёт как **время
в формате `MM:SS`** (3000 минут : 3000 секунд), а не как строку.

**`volumes`.** Слева — папка на твоём компьютере рядом с `docker-compose.yml`, справа —
абсолютный путь внутри контейнера, куда смотрит переменная из `environment`. `./data:/data` без
`:ro`, потому что сюда приложение **пишет**: базу `music.db`, её служебные файлы
`music.db-wal` / `music.db-shm` (режим WAL из `client.ts`) и обложки в `covers/`. Разбор
томов — раздел 7.

**`environment`.** То же, что `ENV` в Dockerfile, но **эти значения сильнее** — они перекрывают
заданные в образе. Дублирование нужно, чтобы все настройки конкретного запуска лежали в одном
читаемом файле: Dockerfile описывает образ «вообще», а compose — «как он запущен у тебя».

**`restart`.**

| Значение | Поведение |
| --- | --- |
| `no` | по умолчанию: упал — и лежит |
| `on-failure` | перезапускать только при падении с ошибкой |
| `always` | перезапускать всегда, даже после перезагрузки и **даже если ты остановил его вручную** |
| **`unless-stopped`** | после падения и после перезагрузки компьютера — да, но **не возвращать, если ты остановил контейнер сам** |

Это то, что нужно домашнему сервису: выключил компьютер — включил, плеер поднялся сам.
Надоело — `docker compose stop`, и он не возвращается.

**Ограничение логов.** Приложение пишет в stdout (`log()` из `config.ts`), Docker складывает это
в файлы. С настройкой выше максимум **3 файла по 10 МБ** — всего 30 МБ: дорастает до 10 МБ,
переименовывается, начинается новый, самый старый удаляется (классическая ротация). Без
ограничений эти файлы растут бесконечно, и однажды `/var/lib/docker` занимает весь диск.
Побочный эффект — старые логи исчезают; для домашнего плеера нормально.

## 7. Тома (volumes) подробно

Это ответ на вопрос **«удалю контейнер — данные не пропадут?»**.

**Проблема.** У контейнера есть **записываемый слой** поверх образа — база, обложки, логи. И
неприятное свойство: **удалил контейнер — записываемый слой испарился вместе с ним.** Это не
баг, а осознанное решение: контейнеры задуманы как расходный материал. Обновил версию — старый
выбросил, новый запустил из нового образа; если бы данные жили внутри, каждое обновление
стирало бы библиотеку.

**Решение.** **Том — это дырка в броне контейнера.** Папка, которая физически лежит на твоём
компьютере, но видна внутри контейнера: удаляешь контейнер — папка остаётся, создаёшь новый —
он видит те же данные.

```
       ХОСТ                                    КОНТЕЙНЕР
┌──────────────────────┐                ┌──────────────────────┐
│ ./music → 31 МБ mp3  │◄──────────────►│ /music  (ro)         │
│ ./data               │                │ /data                │
│   music.db, -wal     │◄──────────────►│   music.db, -wal     │
│   covers/            │                │   covers/            │
└──────────────────────┘                └──────────────────────┘
   ЖИВЁТ ВСЕГДА (удалил контейнер — осталось)
```

**Два вида томов — разница важная.**

| | **Bind mount** | **Именованный том (named volume)** |
| --- | --- | --- |
| Синтаксис | `./music:/music` | `music-data:/music` |
| Где данные | **в понятной папке рядом с проектом** | внутри Docker: `/var/lib/docker/volumes/music-data/_data` |
| Кто создаёт | ты сам | Docker сам, при первом запуске |
| Видно в файловом менеджере | да | нет (только `docker volume inspect`) |
| Менять файлы снаружи | да, просто копируешь mp3 в `./music` | почти нет, нужны костыли |
| Бэкап | `cp -r ./data ~/backup` | `docker run --rm -v data:/d -v $PWD:/b alpine tar cf /b/d.tar /d` |
| Обычно для | **данных, которые ты сам наполняешь и хочешь видеть** | баз данных, кэшей — «служебных» данных |

**Проект использует bind mount, и для плеера это правильный выбор:** музыку ты кладёшь руками
из файлового менеджера, поэтому папка обязана быть обычной папкой на диске. Разница «на глаз»:
bind mount — это вот они, файлы, прямо здесь (`ls ./data` показывает `covers  music.db
music.db-shm  music.db-wal`); именованный том снаружи не видно вообще — `docker volume ls`
покажет только имя `music-player_data`, а файлы лежат в
`/var/lib/docker/volumes/music-player_data/_data`.

Как выглядел бы наш compose на именованных томах: `music-data:/music:ro` и `player-data:/data`
плюс секция `volumes:` с их объявлением. Для `/data` это было бы даже удобно, а для `/music` —
нет: ты не смог бы просто перетащить альбом в папку.

> **Деталь, которая многих путает: `docker compose down -v`.** Флаг `-v` удаляет тома, но
> **bind mount — не том Docker**, а просто папка на твоём диске, поэтому `down -v` наши
> `./music` и `./data` не тронет вообще. С именованными томами `-v` стёр бы их вместе с базой.

**Короткий ответ: да, не пропадут — если данные лежат в томе или bind mount, а не внутри
контейнера.**

| Действие | Музыка в `./music` | База в `./data` |
| --- | --- | --- |
| `docker compose stop` / `down` / `restart` | ✅ цела | ✅ цела |
| `docker rm music-player` | ✅ цела | ✅ цела |
| `docker compose down -v` | ✅ цела (bind mount!) | ✅ цела (bind mount!) |
| `docker compose build --no-cache` | ✅ цела | ✅ цела |
| `rm -rf ./data` | ✅ цела | ❌ база удалена → пересканировать |
| `rm -rf ./music` | ❌ музыка удалена | ✅ база есть, но ссылки битые |

**Единственный способ потерять базу — удалить её руками.** Ни `down`, ни обновление образа, ни
`docker system prune` (без `--volumes`) её не тронут.

## 8. Почему музыка монтируется как `:ro`

`:ro` = read-only: контейнер может **читать** файлы в `/music`, но не может ни изменить, ни
создать, ни удалить там что-либо. Четыре причины:

1. **Приложение и правда не должно писать в музыку.** Плеер читает mp3, вытаскивает теги,
   отдаёт аудиопоток; всё, что он записывает, идёт в `/data`. Право на запись ему не нужно.
2. **Принцип наименьших привилегий.** Если в разборе метаданных (`music-metadata` читает
   потенциально битые файлы) найдётся уязвимость — она физически не сможет испортить коллекцию:
   ядро откажет в записи.
3. **Защита от бага.** Ошибка в пути, случайный `unlink`, неверный рекурсивный обход — любая
   упрётся в `EROFS: read-only file system` и станет безобидной.
4. **Явное намерение в конфиге.** Читаешь `./music:/music:ro` — сразу понимаешь, что папка для
   плеера только источник.

`./data` — наоборот, без `:ro`, потому что туда пишут. Поставишь `:ro` на `/data` —
приложение упадёт при первой же записи (раздел 11.3).

## 9. Практические команды

Выполняются из корня проекта, где лежит `docker-compose.yml`.

```bash
docker compose up -d              # собрать образ (если нужно) и запустить в фоне
docker compose down               # остановить и УДАЛИТЬ контейнер (образ и данные остаются)
docker compose stop               # просто остановить
docker compose start              # запустить остановленный обратно
docker compose restart            # перезапустить (stop + start), образ НЕ пересобирается
docker compose logs -f            # следить за логами (выход — Ctrl+C, контейнер живёт)
docker compose logs --tail=50     # только последние 50 строк
docker compose logs -f -t         # с метками времени — видно, когда что случилось
docker compose build              # пересобрать образ (с кэшем слоёв)
docker compose up -d --build      # пересобрать и сразу перезапустить
docker compose build --no-cache   # пересобрать ПОЛНОСТЬЮ, игнорируя кэш
docker compose exec music-player sh   # интерактивный shell ВНУТРИ работающего контейнера
docker ps                         # запущенные контейнеры: имя, образ, статус, порты
docker ps -a                      # ВСЕ, включая остановленные и падающие (Exited / Restarting)
docker images                     # локальные образы с размерами
docker system prune               # убрать неиспользуемые контейнеры, образы, кэш сборки, сети
docker system df                  # сколько места всё это занимает
docker system prune -a            # + удалить ВСЕ неиспользуемые образы, не только висячие
docker system prune -a --volumes  # САМОЕ ОПАСНОЕ: + все именованные тома (наш bind mount уцелеет)
```

Пояснения к неочевидному:

* **`up -d`.** `-d` = detached, «отвяжись» — команда вернёт терминал, контейнер работает в фоне.
  **Без `-d` терминал занят, и Ctrl+C остановит контейнер.** Если образа нет — Compose сначала
  его соберёт; если изменил `Dockerfile` или `package.json` — тоже пересоберёт; если изменил
  только код в `src/` — **не** пересоберёт, нужно явно `docker compose up -d --build`.
* **`down`.** Контейнер именно удаляется — это нормально: при следующем `up` он создастся заново
  из образа, а данные подхватятся из томов.
* **`restart`.** `stop` + `start` того же контейнера: образ берётся тот же, новый **не**
  собирается. Полезно, когда зависло приложение.
* **`logs -f`.** `-f` = follow, «следи»: новые строки дописываются в реальном времени, как
  `tail -f`. В логах ты увидишь вывод `log()` из `config.ts` — например
  `[player] SQLite открыта: /data/music.db`. **Это лучший способ узнать, что контейнер на самом
  деле запустился и нашёл базу.**
* **`build --no-cache`.** Занимает минуты вместо секунд, но решает загадочные случаи «я
  поправил, а эффекта нет».
* **`exec music-player sh`.** `exec` — выполнить команду в уже запущенном контейнере,
  `music-player` — имя сервиса, `sh` — что выполнить. **Именно `sh`, а не `bash`:** в Alpine
  Linux (а у нас `oven/bun:1-alpine`) bash по умолчанию нет, только BusyBox `sh`; команда с
  `bash` выдаст `executable file not found`. Флаг `-it` часто пишут, но Compose подставляет его
  сам, когда понимает, что запускается shell.
* **`docker ps`.** Ключевая колонка — `STATUS`: `Up 5 minutes (healthy)` означает, что
  healthcheck проходит. Если контейнер перезапускается по кругу, `docker ps -a` покажет
  `Restarting (1) 5 seconds ago` — тогда идём в логи (раздел 11.4).

Что полезно проверить внутри контейнера:

```bash
$ docker compose exec music-player sh
/app $ pwd                       # /app — здесь WORKDIR
/app $ ls /music                 # тут должны быть твои mp3
/app $ ls -la /data              # music.db, music.db-wal, covers
/app $ ls /app/drizzle           # миграции, без них не будет таблиц
/app $ bun --version             # проверяем, что рантайм — Bun
/app $ touch /music/test.txt
touch: /music/test.txt: Read-only file system   # ← :ro работает
/app $ exit
```

Наш образ при этом весит сотни мегабайт, но музыки внутри нет — только код и рантайм.

## 10. Перенос на другой компьютер

Конечная цель проекта по ТЗ. Пошагово.

**Шаг 1. Установить Docker** — только его. **Bun, Node.js и Next.js ставить НЕ нужно**, всё
внутри образа; в этом весь смысл. Проверка: `docker --version`, `docker compose version`.

**Шаг 2. Клонировать репозиторий:** `git clone <адрес-репозитория> && cd orpheus-bbs`

**Шаг 3. Положить музыку в `./music`** — именно рядом с `docker-compose.yml`, потому что том
смонтирован как `./music:/music:ro`. Если папки нет, Docker создаст пустую (и это будет загадка
«почему библиотека пустая»):

```bash
mkdir -p music && cp -r ~/Music/любимые-альбомы/* ./music/
```

**Шаг 4. Поднять и следить за первым запуском:**

```bash
docker compose up -d
docker compose logs -f     # ждём строку: [player] SQLite открыта: /data/music.db
```

Первый запуск: Docker скачает `oven/bun:1-alpine`, поставит зависимости, соберёт Next.js — это
минуты. Дальше секунды.

**Шаг 5. Открыть браузер** — `http://localhost:3000`. Если контейнер здоров, `docker ps` покажет
`(healthy)`.

**Шаг 6. Нажать «СКАНИРОВАТЬ».** Отдельный шаг, и его легко забыть: **приложение не сканирует
папку само при старте** — оно ждёт кнопку. Сканирование обойдёт `/music`, прочитает теги через
`music-metadata`, вытащит обложки в `/data/covers` и наполнит таблицу `tracks`. Пустой список
треков после открытия — нормально.

| Что | Как переносится |
| --- | --- |
| Код и инфраструктура | `git clone` |
| Музыка | копируешь в `./music` (или монтируешь внешний диск) |
| Библиотека (база) | **не переносится** — проще пересканировать |
| Обложки | создаются заново при скане |
| **Плейлисты и история** | лежат в базе (`music.db`) → переносятся копированием `./data` |

Если хочешь сохранить не только музыку, но и плейлисты с историей, скопируй папку `./data`
целиком. Пути внутри базы абсолютные (`/music/...`), а внутри контейнера они одинаковые на любой
машине — поэтому всё найдётся. Это ещё один плюс того, что пути в контейнере фиксированы через
`WORKDIR /app` и `ENV MUSIC_DIR=/music`.

## 11. Что делать, если пошло не так

Порядок диагностики всегда один:

```bash
docker compose ps                     # 1. Он вообще запущен? Какой статус?
docker compose logs                   # 2. Что он говорит?
docker compose exec music-player sh   # 3. Что внутри?
```

**11.1 Порт 3000 занят.** Симптом: контейнер не поднимается, в логах
`driver failed programming external connectivity: Bind for 0.0.0.0:3000 failed: port is already
allocated`. Причина: порт на хосте уже занят — например, ты забыл запущенный `bun run dev`, или
это другой контейнер. Найти виновника: `lsof -i :3000` (macOS/Linux), `ss -ltnp | grep 3000`
(Linux), `docker ps`. Решение — поменять левое число в `ports`:

```yaml
    ports:
      - "8080:3000"    # было "3000:3000"
```

Затем `docker compose up -d`. **Правое число не меняй:** оно связано с `ENV PORT=3000` и
`EXPOSE 3000` внутри образа. Сайт откроется на `http://localhost:8080`, а приложение продолжит
слушать 3000 внутри.

**11.2 Папка `music` пуста / библиотека пустая.** Симптом: сайт работает, жмёшь «СКАНИРОВАТЬ»
— находит 0 треков. Причины: **забыл положить музыку** (проверь `ls -la ./music`); **папки не
было, и Docker создал её пустой** (том `./music:/music:ro` требует, чтобы папка на хосте
существовала); **музыка лежит не там** — классика: положил в `~/Music`, а не в `./music` рядом с
`docker-compose.yml` (помни: `./music` — **относительно compose-файла**, а не относительно
домашнего каталога); **смонтировал не ту папку** или переопределил `MUSIC_DIR` в `environment`.
Проверка, что видит контейнер: `docker compose exec music-player sh`, затем `ls -la /music` и
`echo $MUSIC_DIR` (должно быть `/music`). Пусто в `/music`, но файлы в `./music` есть — значит,
смонтировано не туда: смотри путь в `volumes` слева от двоеточия.

**Нюанс про расширения:** сканер берёт только то, что в `AUDIO_EXTENSIONS` из `config.ts` —
`.mp3`, `.flac`, `.m4a`, `.aac`, `.ogg`, `.opus`, `.wav`. Файл `.wma` или `.ape` он просто
пропустит, и это не баг.

**11.3 База не создалась — права на `./data`.** Симптом: в логах
`[config] не удалось создать папку /data: EACCES: permission denied`,
`Error: unable to open database file` или `SQLiteError: attempt to write a readonly database`.
Причины: **папка `./data` на хосте принадлежит `root`** (типично, если Docker однажды создал её
сам от root; проверь `ls -ld ./data`, лечится `sudo chown -R $(id -u):$(id -g) ./data`);
**случайно поставил `:ro` на `/data`** (в compose должно быть `- ./data:/data` без режима —
приложению нужно писать сюда базу и обложки); **`./data` на хосте — файл, а не папка** (том
смонтируется странно); **ты включил `USER bun`** в Dockerfile, но не выдал права (раздел 5.6).
Проверка после исправления:

```bash
docker compose down && docker compose up -d
docker compose logs -f     # ждём: [player] SQLite открыта: /data/music.db
ls -la ./data              # появились music.db, music.db-wal, music.db-shm
```

**11.4 Контейнер перезапускается по кругу.** `docker ps` показывает
`Restarting (1) 3 seconds ago` снова и снова, сайт не открывается. Причина: приложение падает
при старте, а `restart: unless-stopped` честно поднимает его опять — бесконечный цикл. **Что
делать — всегда одно и то же: `docker compose logs --tail=100`.**

| Что в логах | Причина | Решение |
| --- | --- | --- |
| `Cannot find module "bun:sqlite"` | потерялся `--bun`, приложение на Node.js | проверить `package.json` и `CMD` (5.4) |
| `no such table: tracks` | в образ не попала папка `drizzle/` | проверить `COPY --from=builder /app/drizzle ./drizzle` |
| `EACCES` / `readonly database` | права на `/data` | раздел 11.3 |
| `EADDRINUSE` | порт занят **внутри** контейнера | обычно из-за `PORT`; правую часть в `ports` не менять |
| `Cannot find module 'next'` | `node_modules` не скопировался в финальный этап | `COPY --from=builder /app/node_modules` |

Полезный приём — отключить автоперезапуск и посмотреть на падение спокойно:

```bash
docker compose run --rm music-player sh   # контейнер с shell вместо CMD
/app $ bun run start                      # запустить руками и увидеть полную ошибку
```

Ещё подсказка по статусу выхода: `Exited (1)` — ошибка приложения, `Exited (137)` — процесс
убит (например, не хватило памяти).

**11.5 «Открывается, но не играет звук».** Виноват не Docker, а стрим-роут
`src/app/api/tracks/[id]/stream/route.ts`: он использует HTTP Range Requests. Гипотеза 1
(главная): стрим не отдаёт `206`. Проверить руками:

```bash
curl -i -H "Range: bytes=0-1023" http://localhost:3000/api/tracks/1/stream
```

В ответе должно быть:

```
HTTP/1.1 206 Partial Content          ← ОБЯЗАТЕЛЬНО 206
Content-Type: audio/mpeg
Content-Length: 1024
Content-Range: bytes 0-1023/8942026   ← обязательно
Accept-Ranges: bytes                  ← без него браузер не станет перематывать
```

Видишь `200 OK` вместо `206` — перемотка работать не будет. Видишь `404` — смотри текст ошибки,
роут честно говорит, чего не хватает.

**Гипотеза 2: файл пропал с диска.** Роут отдельно это проверяет (`stat(track.path)`) и
отвечает: «Файл не найден на диске. Возможно, он был перемещён или удалён — запусти сканирование
заново». База — это индекс, и о переименовании файла в `./music` она не знает; лечится
пересканированием.

**Гипотеза 3: `401` из-за токена** — раскомментировал `STREAM_TOKEN`, значит запрос без
`?token=...` получит «Доступ запрещён: неверный токен»; проверь с токеном:

```bash
curl -i -H "Range: bytes=0-1023" "http://localhost:3000/api/tracks/1/stream?token=смени-меня"
```

**Гипотеза 4: контейнер не видит `/music`** — тогда `stat` провалится и вернётся 404 с сообщением
про файл на диске; идём в раздел 11.2. **Гипотеза 5: MIME-тип** — расширение должно быть в
`AUDIO_MIME_TYPES`; неизвестное отдаётся как `application/octet-stream`, и `<audio>` может
отказаться играть. Смотри `Content-Type` в ответе curl.

## 12. `./data` нельзя удалять бездумно

```
data/
├── music.db       ← библиотека: tracks, playlists, history, playback_state
├── music.db-wal   ← журнал WAL (PRAGMA journal_mode = WAL из client.ts)
├── music.db-shm   ← разделяемая память WAL
└── covers/        ← обложки, вытащенные из тегов при сканировании
```

| Если удалить `./data` целиком | Последствие |
| --- | --- |
| Музыкальные файлы в `./music` | ✅ **целы** — они в другом томе, смонтированы `:ro` |
| Список треков | ❌ пропал → восстанавливается сканированием |
| Обложки | ❌ пропали → пересоздаются при сканировании из тегов |
| **Плейлисты** | ❌ **пропали безвозвратно** |
| **История прослушиваний** | ❌ **пропала безвозвратно** |
| **Позиции «продолжить слушать»** | ❌ **пропали безвозвратно** |

**Вот в чём суть: база — это не только индекс файлов.** Первые строки восстанавливаются одной
кнопкой, а последние три — нет. Плейлист с вручную подобранным порядком и история за полгода
живут **только** в `music.db`; восстановить их из mp3 невозможно — там просто нет такой
информации. Что делать при проблемах с базой вместо удаления:

```bash
docker compose stop                        # чтобы WAL дописался в основной файл
cp -r ./data ~/backup-data-$(date +%F)     # файлы маленькие — можно просто скопировать
docker compose start
```

Штатный «сброс» на случай, если база побилась, есть в `package.json`:

```json
"db:reset": "rm -f data/music.db && echo 'База удалена. Перезапусти скан библиотеки.'"
```

Он удаляет только `music.db`; база создастся заново при первом обращении (в `client.ts`
подключение открыто с `{ create: true }`), миграции применятся автоматически, останется нажать
«СКАНИРОВАТЬ». Но плейлисты при этом тоже уйдут. **Правило: `./data` — это твои данные, а не
кэш.** Бэкапить перед экспериментами, не удалять от отчаяния.

## 13. Ограничения домашнего запуска и токен `STREAM_TOKEN`

**Приложение слушает все интерфейсы.** Next.js по умолчанию слушает `0.0.0.0` — **все сетевые
интерфейсы**, не только `localhost`. В связке с пробросом `0.0.0.0:3000->3000/tcp` (видно в
`docker ps`) это значит: **плеер доступен любому устройству в твоей локальной сети.** Узнать
свой адрес (`ip -4 addr show | grep inet` на Linux, `ipconfig getifaddr en0` на macOS) и открыть
с телефона `http://192.168.1.42:3000`. Удобно — можно слушать с телефона. Но **любой сосед по
Wi-Fi может скачать твою музыку** и увидеть библиотеку с плейлистами.

**Способ 1, самый строгий — не публиковать порт наружу:**

```yaml
    ports:
      - "127.0.0.1:3000:3000"    # порт открыт только на loopback, из сети не виден
```

Минус: с телефона не послушать.

**Способ 2 — токен на аудиопоток.** Реализован в `src/app/api/tracks/[id]/stream/route.ts`:

```ts
function checkAccessToken(request: Request): boolean {
  const expected = process.env.STREAM_TOKEN?.trim();
  if (!expected) return true;                       // токен не задан — пускаем всех
  const url = new URL(request.url);
  const fromQuery = url.searchParams.get("token");
  const fromHeader = request.headers.get("x-stream-token");
  return fromQuery === expected || fromHeader === expected;
}
```

То есть токен принимается либо параметром `?token=...` в адресе, либо заголовком
`X-Stream-Token`. Раскомментируй в `docker-compose.yml` строки `STREAM_TOKEN: смени-меня` и
`NEXT_PUBLIC_STREAM_TOKEN: смени-меня`, затем `docker compose up -d`.

| Переменная | Где видна | Зачем |
| --- | --- | --- |
| `STREAM_TOKEN` | только на сервере | сервер сверяет с ним пришедшее значение |
| `NEXT_PUBLIC_STREAM_TOKEN` | **и на сервере, и в браузере** | префикс `NEXT_PUBLIC_` велит Next.js вклеить значение в клиентский бандл, чтобы `<audio src>` подставило токен в URL |

Без второй переменной браузер не будет знать токен и аудио не заиграет — поэтому в комментарии
compose честно написано: **значение должно совпадать в двух строках**.

**Чего токен НЕ делает:** он **не** защищает список треков, плейлисты и историю — только
аудиопоток, интерфейс остаётся открытым. И он **не** заменяет авторизацию: в комментариях к
роуту сказано прямо, что настоящая авторизация — это логин, пароль, сессии и роли, а ТЗ просит
не усложнять. Плюс токен в URL попадает в **историю браузера и в логи сервера** — для домашнего
плеера приемлемый компромисс, для чего-то серьёзного нет.

**Ещё стоит помнить:** Docker compose **не заменяет бэкап** (диск умирает, и `./music` с
`./data` умрут вместе с ним; музыку обычно можно перекачать, базу с плейлистами — нет);
обновление проекта — `git pull && docker compose up -d --build`; остановка на ночь —
`docker compose stop` (данные в безопасности); автозапуск после перезагрузки уже настроен через
`restart: unless-stopped`.

## 12.1. ⚠ Том `./data` ОБЩИЙ для всех способов запуска

Важная деталь, которую легко упустить: **локальный запуск и Docker
используют ОДНУ И ТУ ЖЕ базу** — ту, что лежит в `./data/music.db`.

```
bun run dev            →  DB_PATH=./data/music.db
docker compose up -d   →  ./data  монтируется в  /data
                       →  DB_PATH=/data/music.db
```

Это сделано специально (данные должны переживать удаление контейнера),
но у такого решения есть последствие: **в базе нельзя хранить ничего,
что зависит от способа запуска**.

Именно на этом проект один раз сломался: в колонке пути хранился
АБСОЛЮТНЫЙ путь. Локально это `/home/august/.../music/песня.mp3`,
в контейнере — `/music/песня.mp3`. После запуска через Docker база
содержала пути, которых нет на хосте, и **вся музыка перестала играть**
(404 на `/api/tracks/N/stream`).

Решение: в базе хранится путь ОТНОСИТЕЛЬНО папки с музыкой
(`"ATL - Ящик.mp3"`), а абсолютный собирается в момент обращения
добавлением `MUSIC_DIR`. Подробный разбор — в docs/06, раздел 6.1.

> **Вывод:** если один и тот же том используется и локально, и в контейнере,
> проверяй, что все хранимые в нём значения не зависят от окружения.
> Пути, адреса, имена хостов — первые кандидаты на такую ошибку.

## 13.1. ⚠ ВАЖНО: почему `NEXT_PUBLIC_STREAM_TOKEN` здесь НЕ работает

В первых версиях этого проекта в `docker-compose.yml` было две строки:

```yaml
STREAM_TOKEN: смени-меня
NEXT_PUBLIC_STREAM_TOKEN: смени-меня   # ← так делать НЕЛЬЗЯ
```

Вторая строка **не работала**, и это стоит разобрать: ошибка типичная
и очень неочевидная.

**Причина.** Переменные с префиксом `NEXT_PUBLIC_` подставляются в код
**в момент СБОРКИ**, а не в момент запуска. В Docker это разные моменты:

```
docker compose build   → во время сборки переменных ещё НЕТ
docker compose up      → переменные появляются, но код уже собран
```

Во время сборки токена не существует, поэтому в бандл уезжает пустая
строка — и браузер не может добавить токен к адресу потока. Аудио
не играет, причём с ошибкой 401, которая не имеет видимой причины.

**Проверить самому** (в проекте, где такая ошибка есть):

```bash
# если значение не было задано при сборке, в файле останется обращение
# к переменной, а не сама строка
grep -rl 'NEXT_PUBLIC_STREAM_TOKEN' .next/static
```

**Как исправлено в ORPHEUS.BBS.** Токен читает **сервер** в момент
запроса (`src/app/layout.tsx`), и передаёт значение в плеер обычным
пропсом:

```tsx
const streamToken = process.env.STREAM_TOKEN?.trim() ?? "";
// …
<PlayerProvider streamToken={streamToken}>
```

Никаких `build.args`, никакой пересборки при смене токена: один и тот же
образ можно запускать с разными токенами. Подробный разбор — в
`src/lib/stream-url.ts`.

> **Правило на будущее.** `NEXT_PUBLIC_*` годится только для значений,
> известных **во время сборки** (например, название сайта или адрес API).
> Всё, что должно настраиваться **при запуске** — токены, пароли, адреса
> базы — передавай с сервера пропсом или через cookie.

## 14. Мини-упражнения

**1. Поменять порт.** Запустить плеер на `http://localhost:8080`, не трогая ничего внутри
приложения: замени в `docker-compose.yml` `- "3000:3000"` на `- "8080:3000"`; сделай
`docker compose up -d` и открой `http://localhost:8080`; проверь, что `http://localhost:3000`
больше **не** работает; посмотри `docker ps` — увидишь `0.0.0.0:8080->3000/tcp`.
**Вопрос:** почему `EXPOSE 3000` в Dockerfile остался правильным и менять его не надо?

**2. Собрать без кэша и замерить.**

```bash
time docker compose build              # 1-й раз: с кэшем (почти мгновенно, если уже собирал)
time docker compose build --no-cache   # 2-й раз: полностью с нуля
```

Сравни время. Потом сделай правку **только в комментарии** внутри `src/` и снова
`time docker compose build` — обрати внимание, что шаг `RUN bun install --frozen-lockfile`
выполнился **мгновенно** (взялся из кэша). Это ровно та оптимизация из раздела 5.5.
Дополнительно: включи обещанный `BUN_VERSION`, добавив перед `FROM` строку `ARG BUN_VERSION=1`
и заменив тег на `oven/bun:${BUN_VERSION}-alpine`, а затем собери с
`docker compose build --build-arg BUN_VERSION=1`.

**3. Добавить второй сервис** и убедиться, что сервисы видят друг друга по имени. Добавь в
`docker-compose.yml` (рядом с `music-player`, на том же уровне вложенности):

```yaml
  # Второй сервис: nginx просто отдаёт список файлов музыки.
  # Нужен только для учёбы — посмотреть, как контейнеры общаются между собой.
  music-browser:
    image: nginx:alpine
    container_name: music-browser
    volumes:
      - ./music:/usr/share/nginx/html:ro   # тот же bind mount, что и у плеера
    ports:
      - "8081:80"                          # слева 8081, чтобы не конфликтовать с плеером
    restart: unless-stopped
```

Подними (`docker compose up -d`), проверь `docker compose ps` (два сервиса) и
`http://localhost:8081` — увидишь список mp3-файлов. Затем изнутри плеера проверь сетевое имя:
`docker compose exec music-player sh`, потом
`wget -q -O - http://music-player:3000/api/tracks | head -c 200`.
**Вопрос:** почему `http://music-player:3000` работает, хотя `music-player` — не имя хоста и не
IP-адрес? Кто превращает имя в адрес? Обрати внимание: **оба контейнера используют один и тот же
volume `./music` одновременно** — это нормально.

**4. Сломать и починить доступ к базе.** Сделай `docker compose down`; поставь `:ro` на данные
(`- ./data:/data:ro`); подними (`docker compose up -d`) и посмотри `docker compose logs -f` —
найди ошибку, скорее всего `attempt to write a readonly database` или `EACCES`; зайди внутрь
(`docker compose exec music-player sh`) и проверь, что `touch /data/test.txt` падает с
`Read-only file system`; верни как было (`- ./data:/data`) и перезапусти.
**Вопрос:** почему для `/music` `:ro` — хорошо, а для `/data` — плохо? Одним предложением.

**5. Проверить стриминг вручную.**

```bash
curl -s http://localhost:3000/api/tracks | head -c 400          # 1. список треков, найди id

# 2. Первые 1024 байта: нужен статус 206 и заголовок Content-Range
curl -i -H "Range: bytes=0-1023" http://localhost:3000/api/tracks/1/stream | head -20

# 3. Только статус-код
curl -o /dev/null -s -w "статус: %{http_code}\n" \
  -H "Range: bytes=0-1023" http://localhost:3000/api/tracks/1/stream

curl -I http://localhost:3000/api/tracks/1/stream                # 4. HEAD: заголовки без тела
```

Шаг 3 должен напечатать **`статус: 206`**. Напечатает `200` — Range не обрабатывается, и
перемотка в плеере работать не будет. Шаг 4: тела быть не должно, но заголовки
`Accept-Ranges: bytes`, `Content-Length` и `ETag` — должны.

## 15. Шпаргалка: команда → что делает

| Команда | Что делает |
| --- | --- |
| `docker compose up -d` | Собрать (если нужно) и запустить в фоне |
| `docker compose up` | То же, но в переднем плане: логи в терминале, Ctrl+C = стоп |
| `docker compose up -d --build` | Пересобрать образ и перезапустить |
| `docker compose down` | Остановить и **удалить** контейнер (данные в томах остаются) |
| `docker compose down -v` | То же + удалить **именованные** тома (наших bind mount не касается) |
| `docker compose stop` / `start` | Просто остановить / запустить остановленный |
| `docker compose restart` | Перезапустить (stop + start), образ не пересобирается |
| `docker compose logs -f` | Смотреть логи в реальном времени |
| `docker compose logs --tail=50` / `-t` | Последние 50 строк / с метками времени |
| `docker compose build` | Пересобрать образ (с кэшем) |
| `docker compose build --no-cache` | Пересобрать полностью, игнорируя кэш |
| `docker compose ps` | Статус сервисов проекта (включая `healthy`/`unhealthy`) |
| `docker compose exec music-player sh` | Зайти в shell **внутри** работающего контейнера (bash в Alpine нет) |
| `docker compose run --rm music-player sh` | Разовый контейнер с shell вместо `CMD`, потом удалить |
| `docker compose port music-player 3000` | Узнать, на какой порт хоста проброшен 3000 |
| `docker compose config` | Итоговый конфиг после подстановок — удобно для отладки YAML |
| `docker ps` / `docker ps -a` | Запущенные / все контейнеры (включая падающие) |
| `docker images` | Локальные образы с размерами |
| `docker logs music-player` | Логи по имени контейнера (без compose) |
| `docker volume ls` | Именованные тома (у нас их нет — мы на bind mount) |
| `docker system df` | Сколько места занимают образы, контейнеры, кэш |
| `docker system prune` | Удалить неиспользуемые контейнеры, образы, кэш сборки |
| `docker system prune -a --volumes` | **Опасно:** + все неиспользуемые образы и именованные тома |

### Мини-словарь

| Слово | Что это |
| --- | --- |
| **Образ (image)** / **контейнер (container)** | Чертёж / запущенный по нему процесс с записываемым слоем |
| **Слой (layer)** | Результат одной инструкции Dockerfile; кэшируется и переиспользуется |
| **Том (volume)** | Папка, живущая вне контейнера; переживает удаление контейнера |
| **Bind mount** / **именованный том** | Том на конкретную папку хоста (`./music`) / том, которым управляет Docker |
| **Контекст сборки** | Папка, доступная инструкциям `COPY` (у нас `.`) |
| **Multi-stage build** | Несколько `FROM` в одном Dockerfile; в финал идёт только последний |
| **`--frozen-lockfile`** / **`--bun`** | Ставить строго по lock-файлу / выполнять рантаймом Bun (иначе нет `bun:sqlite`) |
| **HEALTHCHECK** / **`:ro`** | Проверка живости приложения / папка только для чтения |

**Финальная проверка цели из ТЗ на чистой машине:**

```bash
git clone <репозиторий> && cd orpheus-bbs
cp -r ~/Music/* ./music/
docker compose up -d
# → http://localhost:3000 → кнопка «СКАНИРОВАТЬ»
# → музыка играет, контейнер можно удалить и создать заново
```
