# 09. Структура проекта: что где лежит и почему именно там

Эта глава — карта местности. После неё ты сможешь открыть любую папку проекта и
понимать, зачем она существует, и — что важнее — куда класть новый код, чтобы
через месяц не искать его по всему репозиторию.

Главная мысль, которую стоит запомнить сразу:

> **В проекте нет «просто папок». Каждая папка отвечает на вопрос «что это за код?»
> — маршрут, компонент, доступ к данным, работа с файлами или настройка.**

---

## 1. Папка верхнего уровня

Сначала — что вообще лежит рядом с кодом. Большая часть этих файлов не содержит
логики приложения: они описывают, **как** это приложение собрать и запустить.

```text

│

│

│   ├── 0000_clammy_norrin_radd.sql   первая (и пока единственная) миграция:
│   │                                 CREATE TABLE для всех пяти таблиц

├── data/                     ← ДАННЫЕ, а не код. В git НЕ коммитится

│   └── *.svg                 стандартные заглушки из create-next-app

│

├── bun.lock                  точные версии всех пакетов; коммитится в git

├── README.md                 краткое описание и команды запуска
```

Заметь закономерность: **всё, что «про запуск», лежит в корне; всё, что «про
приложение», лежит в `src/`**. Корень — это паспорт проекта, а не его тело.

Ещё одна привычка, которую стоит перенять: `data/` и `music/` не в git, но
существуют как папки. Код в любой момент может их удалить и восстановить —
база пересобирается сканером, музыка у тебя и так на диске.

## 3. Правила раскладки: почему так, а не иначе

### 3.1 Почему `app/` и что значит «маршрут = папка»

Next.js использует **файловый роутинг** (App Router). Отдельного файла `routes.js`
со списком адресов нет: **адрес страницы — это путь к папке**, а имя файла внутри
говорит, *что* это за файл.

| Путь в браузере | Файл на диске |
| --- | --- |
| `/` | `src/app/page.tsx` |
| `/playlists` | `src/app/playlists/page.tsx` |
| `/playlists/7` | `src/app/playlists/[id]/page.tsx` |
| `/history` | `src/app/history/page.tsx` |
| `/api/tracks` | `src/app/api/tracks/route.ts` |

Квадратные скобки (`[id]`) — **динамический сегмент**: сюда подставляется любое
значение, и страница получает его в пропсе `params`. Так один файл обслуживает все
плейлисты сразу. Главное удобство: чтобы добавить страницу, **не нужно ничего
регистрировать** — создал папку с `page.tsx`, и адрес появился.

### 3.2 `page.tsx`, `layout.tsx`, `route.ts` — три роли одного места

| Файл | Что это | Отдаёт HTML | Особенность |
| --- | --- | --- | --- |
| `page.tsx` | Страница маршрута | да | Может быть `async`, читать базу |
| `layout.tsx` | «Рамка» вокруг страниц уровня | да | **не пересоздаётся** при переходах |
| `route.ts` | HTTP-обработчик (Route Handler) | нет, отдаёт `Response` | Здесь живут `GET`/`POST`/`PATCH`/`DELETE` |

**Почему `page.tsx` и `route.ts` не могут лежать в одной папке.** Оба претендуют
на один и тот же адрес: страница рендерит HTML, обработчик отвечает данными.
Next.js не может решить, что вернуть по этому URL, и падает на этапе сборки.
Поэтому API живёт в отдельном дереве `src/app/api/` и со страницами не пересекается.

**Важное следствие про layout.** Провайдер плеера `PlayerProvider` стоит именно в
корневом `layout.tsx`, а не в `page.tsx`. Layout не пересоздаётся при переходах —
значит, `<audio>` создаётся один раз за сессию, и музыка **не обрывается**, когда
ты уходишь из библиотеки в плейлисты. Самый наглядный пример, зачем нужен layout.

### 3.3 Почему папка с `_` или `()` не становится маршрутом

App Router игнорирует часть папок — и это не случайность, а возможности:

| Шаблон | Имя приёма | Смысл |
| --- | --- | --- |
| `_name`, `__name` | приватная папка | файлы внутри не участвуют в роутинге: удобно для служебного кода рядом со страницами |
| `(name)` | группа маршрутов | скобки **не попадают в URL**: `(marketing)/about/page.tsx` даёт адрес `/about` |
| `[id]` | динамический сегмент | значение приходит в `params` |

Отсюда — реальный урок, который мы получили на практике. При отладке возникла идея
сделать страницу-пробник прямо в дереве маршрутов, папкой с двойным подчёркиванием
— что-то вроде `src/app/__probe/page.tsx`. Файл на месте, код корректный, **а
страница по URL не открывается**: Next.js считает любую папку, начинающуюся с `_`,
приватной и в маршруты её не включает. Пришлось переименовать папку.

Мораль: если страница «не находится», хотя файл на месте — первым делом посмотри
на **имя папки**. Приватность по `_` — не баг, а защита.

### 3.4 Почему бизнес-логика в `src/lib`, а не в компонентах

Компонент отвечает на вопрос **«как это выглядит и что происходит по клику»**, а не
«как устроен SQL-запрос». Причины практические:

* **Переиспользование.** `listPlaylists()` вызывают серверный `Sidebar`, страница
  `/playlists` и Route Handler `/api/playlists`. В компоненте запрос пришлось бы
  копировать три раза.
* **Проверяемость.** `format.ts` — чистые функции без базы и DOM: проверить можно
  в консоли одной строкой.
* **Доступность с обеих сторон.** `listTracks()` вызывается и из серверного
  компонента, и из Route Handler. Сам компонент так не умеет: он либо серверный,
  либо клиентский.
* **Логику нельзя случайно утащить в браузер.** Клиентский компонент уезжает
  пользователю целиком: если внутри `TrackList` лежал бы SQL, он бы уехал с ним.

### 3.5 Разделение внутри `src/lib`

`lib` — не свалка «всего вспомогательного», а четыре разных мира:

| Модуль | Отвечает за | Почему лежит отдельно |
| --- | --- | --- |
| `lib/db/*` | доступ к данным | База — это индекс, сканер — тот, кто его наполняет. Смешаешь их — получишь код, который не запустить без диска |
| `lib/scanner/*` | работу с файлами на диске | Чистая работа с `node:fs` и `music-metadata`, без React и HTTP. Запускается из одного места — `POST /api/scan` |
| `lib/format.ts` | чистые функции форматирования | Ни базы, ни сети, ни `window`: одинаковый вход → одинаковый выход. Поэтому `formatDuration` вызывается и из серверной страницы плейлиста, и из клиентского `TrackList` |
| `lib/config.ts` | настройки | Единственное место, где читаются переменные окружения: иначе переименование `MUSIC_DIR` превратилось бы в охоту за привидениями |

Есть и «клей» между мирами: `lib/db/mappers.ts` превращает строку из базы
(`TrackRow`) в объект для интерфейса (`TrackDTO`). Компоненты перестают зависеть
от формы таблиц: изменил колонку — поправил один маппер, а не десять компонентов.

### 3.6 Почему компоненты разбиты на шесть папок

Не по типу («всё, что с кнопками») и не по размеру, а **по области приложения**:

| Папка | Область | Пример |
| --- | --- | --- |
| `layout/` | каркас, общий для всех страниц | шапка, сайдбар, навигация |
| `player/` | воспроизведение звука | `player-context.tsx`, `PlayerBar.tsx` |
| `library/` | библиотека треков | `TrackList`, `SearchBar`, `ScanButton` |
| `playlists/` | плейлисты | `PlaylistCard`, `PlaylistCreateForm` |
| `history/` | история | `HistoryList`, `TopTracks`, `RecentlyPlayed` |
| `ui/` | мелочи без предметной логики | `CoverArt` |

Что это даёт: папка `library/` целиком соответствует главной странице — ищешь код
экрана, открываешь одну папку. Новые фичи не размазываются: фича «плейлисты»
трогает `playlists/`, `playlist-queries.ts` и `api/playlists/`. А `ui/` —
единственная папка, которую можно переиспользовать в другом проекте: в `CoverArt`
нет ни слова про музыку, только «картинка с заглушкой».

### 3.7 Именование файлов

| Что | Стиль | Пример | Почему |
| --- | --- | --- | --- |
| Модули в `lib/` | `kebab-case` | `track-queries.ts` | Файл — не «сущность», а набор функций; имя читается как фраза. В мире Node.js для модулей принят kebab-case |
| Компоненты | `PascalCase` | `TrackList.tsx` | Имя файла **совпадает с именем компонента** — ищешь `<TrackList>` → файл `TrackList.tsx`, без перевода |
| Файлы маршрутов | фиксированные имена | `page.tsx`, `layout.tsx`, `route.ts` | Имена зарезервированы Next.js: по ним фреймворк понимает роль файла |
| Динамические сегменты | `[id]` | `playlists/[id]/page.tsx` | Синтаксис Next.js |
| Папки компонентов | `kebab-case` | `components/library/` | Папка — не компонент, поэтому не PascalCase |

Один компонент — один файл. Единственное исключение в проекте — `TrackRow` внутри
`TrackList.tsx`: приватная строка таблицы, нужная только списку. Такие исключения
допустимы, но их оговаривают в комментарии, чтобы читатель не искал `TrackRow.tsx`
по всему проекту.

### 3.8 Алиас `@/` вместо `../../../`

В `tsconfig.json` есть блок `"paths": { "@/*": ["./src/*"] }` — это **алиас
путей**: `@/` означает корень `src/`. Поэтому в проекте везде

```ts
import { listTracks } from "@/lib/db/track-queries";
import { TrackList } from "@/components/library/TrackList";
```

и нигде — `../../lib/db/track-queries`. Почему это лучше относительных путей:

* **Путь не зависит от глубины файла.** Перенёс `TrackList.tsx` в другую папку —
  импорты не изменились ни на символ.
* **Видно принадлежность.** `@/lib/...` — «это логика», `@/components/...` —
  «это интерфейс». С `../../../` приходится считать уровни.
* **Работает поиск.** Поиск по `@/lib/db/track-queries` находит все места
  использования; `../../../lib/db/...` в разных файлах выглядит по-разному.

Техническая деталь: `paths` понимает TypeScript, но сборщик тоже должен их
поддерживать. Next.js читает этот же блок из `tsconfig.json` сам.

### 3.9 Где серверный код, а где клиентский

Правило проекта простое и работает без исключений:

> **По умолчанию компонент серверный. Директива `"use client"` в первой строке
> файла — единственный признак клиентского компонента.**

| Признак | Серверный компонент | Клиентский компонент |
| --- | --- | --- |
| Первая строка файла | ничего (или импорты) | `"use client";` |
| Может быть `async` + `await` | да | нет |
| Может читать базу (`@/lib/db`) | да | нет (только через `fetch`) |
| Может использовать `useState`, `useEffect` | нет | да |
| Может обрабатывать `onClick` | нет | да |
| Знает про `window`, `localStorage` | нет | да |
| Уезжает в браузер | **нет, вообще не уезжает** | да, целиком |

Практические следствия, которые видно прямо в дереве:

* `app/layout.tsx`, `components/layout/AppHeader.tsx`, `Sidebar.tsx` —
  **серверные**: `AppHeader` и `Sidebar` объявлены как `async function` и читают
  базу напрямую.
* `components/player/player-context.tsx`, `PlayerBar.tsx`, `TrackList.tsx` и почти
  весь `library/`, `playlists/`, `history/` — **клиентские**: им нужны хуки и
  обработчики кликов.
* `components/ui/CoverArt.tsx` — клиентский, хотя кажется «просто картинкой»: он
  держит `useState`, чтобы показать заглушку при ошибке загрузки.
* `src/app/error.tsx` **обязан** быть клиентским: обработка ошибок в React работает
  через хуки, а хуки бывают только в браузере.

Два правила, которые спасают от типичных ошибок: **(1)** данные для первой
отрисовки берём на сервере (`Server Component` → `lib/db`), а `fetch` к своему же
API — только когда данные нужны после клика; **(2)** `params` и `searchParams` в
Next.js 15+ — это **Promise**: `const { id } = await params;` (примеры —
`src/app/playlists/[id]/page.tsx` и все `route.ts` с `[id]`).

## 4. Сквозной маршрут данных: от mp3 до звука в колонках

Это самое полезное упражнение для понимания проекта. Проследим один трек через
весь код — от файла на диске до нажатия кнопки «play».

```text
  [1] ДИСК  music/ATL - Ящик.mp3        ← источник правды, база лишь индексирует
        │   POST /api/scan (кнопка «СКАНИРОВАТЬ»)
        ▼
  [2] lib/scanner/walk.ts               обход папок, фильтр по AUDIO_EXTENSIONS
        ▼
  [3] lib/scanner/metadata.ts           music-metadata читает ID3-теги;
        │                               обложка → data/covers/<sha1>.png
        ▼
  [4] lib/scanner/index.ts              scanMusicLibrary(): собрать шаги вместе
        ▼
  [5] lib/db/track-queries.ts           upsertTrack():
        │                               INSERT ... ON CONFLICT(path) DO UPDATE
        ▼
  [6] SQLite: data/music.db, таблица tracks
        │   обычная загрузка страницы «/»
        ▼
  [7] app/page.tsx (СЕРВЕРНЫЙ)          listTracks() + getPlaybackState()
        │                               через Promise.all — фильтры уже в SQL
        ▼
  [8] HTML + RSC-поток → БРАУЗЕР        layout.tsx → PlayerProvider → AppHeader
        │                               → Sidebar → page.tsx → TrackList
        ▼
  [9] КЛИК по строке TrackList.tsx      onClick → usePlayerActions().playTrack()
        ▼
  [10] components/player/player-context.tsx   buildStreamUrl(id) → src у <audio>
        ▼
  [11] GET /api/tracks/12/stream        route.ts: getTrackRowById → stat → поток
        │                               ответ 206 Partial Content + Content-Range
        ▼
  [12] событие <audio> "playing"        POST /api/history → recordPlay()
                                        PUT /api/playback-state → «продолжить»
```

Разбор по шагам, с указанием файлов:

| Шаг | Файл | Что происходит |
| --- | --- | --- |
| 1 | `music/ATL - Ящик.mp3` | Файл на диске — источник правды. Скан запускает `components/library/ScanButton.tsx` через `POST /api/scan` |
| 2 | `src/lib/scanner/walk.ts` | Рекурсивно обходит папки и отсеивает всё, чего нет в `AUDIO_EXTENSIONS` (список — в `src/lib/config.ts`) |
| 3 | `src/lib/scanner/metadata.ts` | `music-metadata` достаёт исполнителя, альбом, длительность; обложка сохраняется в `data/covers/`, в базу идёт только имя файла |
| 4 | `src/lib/scanner/index.ts` | `scanMusicLibrary()`: тонкий слой, который соединяет шаги и считает статистику |
| 5 | `src/lib/db/track-queries.ts` | `upsertTrack()`: `INSERT ... ON CONFLICT(path) DO UPDATE`, поэтому повторный скан обновляет строку, а не плодит дубликаты |
| 6 | `data/music.db` | SQLite, таблица `tracks` (описание — `src/lib/db/schema.ts`) |
| 7 | `src/app/page.tsx` | Серверный компонент параллельно `await`-ит `listTracks(...)` и `getPlaybackState()`. Данные уже отфильтрованы и отсортированы **в SQL** |
| 8 | `src/app/layout.tsx` | Рендер: `layout.tsx` оборачивает страницу в `PlayerProvider`, добавляет шапку и сайдбар; в браузер едет готовый HTML |
| 9 | `src/components/library/TrackList.tsx` | Клик по строке: `TrackRow` зовёт `playTrack(track)` из контекста плеера |
| 10 | `src/components/player/player-context.tsx` | Собирает URL через `src/lib/stream-url.ts` и подставляет его в `<audio>` |
| 11 | `src/app/api/tracks/[id]/stream/route.ts` | Ищет трек, проверяет файл на диске, разбирает `Range` и отдаёт **кусок** файла (`206 Partial Content`) — поэтому перемотка мгновенная |
| 12 | `src/app/api/history/route.ts` | Обратный путь: на событие `<audio>` «playing» уходит `POST /api/history` → `history-queries.ts` → `recordPlay()`. Раз в несколько секунд — `PUT /api/playback-state` для «продолжить слушать» |

Заметь симметрию: **чтение идёт напрямую** (`page.tsx` → `lib/db`, без HTTP),
**а запись — через API** (`fetch` → `route.ts` → `lib/db`). Это не
непоследовательность, а разделение ролей: сервер может обратиться к базе
напрямую, а браузер — нет, ему нужен HTTP-эндпоинт.

## 5. Карта API

Все обработчики лежат в `src/app/api/`. Имена экспортов (`GET`, `POST`, `PATCH`,
`DELETE`, `PUT`, `HEAD`) — это и есть маршрутизация: имя функции = HTTP-метод.

| Метод + путь | Файл | Что делает |
| --- | --- | --- |
| `POST /api/scan` | `api/scan/route.ts` | Запускает сканирование `MUSIC_DIR`, возвращает отчёт (`ScanResultDTO`) |
| `GET /api/tracks` | `api/tracks/route.ts` | Список треков с фильтрами `search`, `artist`, `album`, `favoritesOnly`, `sort`, `limit`, `offset` |
| `PATCH /api/tracks/[id]` | `api/tracks/[id]/route.ts` | Частичное изменение трека: сейчас — переключение `isFavorite` |
| `GET /api/tracks/[id]/cover` | `api/tracks/[id]/cover/route.ts` | Отдаёт PNG/JPEG обложки из `COVERS_DIR` (с защитой от path traversal) |
| `GET /api/tracks/[id]/stream` | `api/tracks/[id]/stream/route.ts` | Отдаёт аудио с поддержкой `Range` → `200` или `206 Partial Content` |
| `HEAD /api/tracks/[id]/stream` | `api/tracks/[id]/stream/route.ts` | Те же заголовки, но без тела: «расскажи про файл, не присылая его» |
| `GET /api/playlists` | `api/playlists/route.ts` | Список всех плейлистов со счётчиком треков |
| `POST /api/playlists` | `api/playlists/route.ts` | Создаёт плейлист (`{ name, description? }`), отвечает `201 Created` |
| `GET /api/playlists/[id]` | `api/playlists/[id]/route.ts` | Плейлист + его треки |
| `PATCH /api/playlists/[id]` | `api/playlists/[id]/route.ts` | Переименование / изменение описания |
| `DELETE /api/playlists/[id]` | `api/playlists/[id]/route.ts` | Удаляет плейлист (связи уходят каскадом), отвечает `204` |
| `POST /api/playlists/[id]/tracks` | `api/playlists/[id]/tracks/route.ts` | Добавляет трек; `409`, если он уже в плейлисте |
| `DELETE /api/playlists/[id]/tracks?trackId=17` | `api/playlists/[id]/tracks/route.ts` | Убирает трек из плейлиста |
| `PUT /api/playlists/[id]/tracks` | `api/playlists/[id]/tracks/route.ts` | Задаёт новый порядок: присылается полный массив `trackIds` |
| `GET /api/history?limit=50` | `api/history/route.ts` | Последние прослушивания (максимум 500 записей) |
| `POST /api/history` | `api/history/route.ts` | Записывает событие `{ trackId }` → `204 No Content` |
| `DELETE /api/history` | `api/history/route.ts` | Очищает историю → `204 No Content` |
| `GET /api/playback-state` | `api/playback-state/route.ts` | Что играло в прошлый раз и на какой секунде |
| `PUT /api/playback-state` | `api/playback-state/route.ts` | Сохраняет `{ trackId, position }` |

Три вещи, общие для всех обработчиков, — и это не совпадение:

* **`export const dynamic = "force-dynamic";`** есть в каждом файле. Никакого
  кэширования: данные меняются, а устаревший JSON — источник странных багов.
* **Логика не живёт в `route.ts`.** Обработчик разбирает вход, валидирует и
  зовёт функцию из `lib/`. Сам он остаётся тонким.
* **Валидация входа — обязательна.** Всё, что пришло снаружи, проверяется: `id`
  целое и положительное, тело — нужной формы. Правило: никогда не доверяй
  запросу, даже если его отправил твой же интерфейс (то же самое можно сделать
  через `curl`).

## 7. Куда добавлять новый код

Практический раздел. Шесть типовых задач — и точный ответ, какие файлы трогать.

### 7.1 «Хочу новую страницу»

Например, страницу «Исполнители» по адресу `/artists`.

1. Создай `src/app/artists/page.tsx` с `export default async function ArtistsPage()`.
2. Прочитай данные через функцию из `lib/db` (если её нет — см. 7.3).
3. Добавь `export const dynamic = "force-dynamic";`, если данные меняются.
4. Нужен пункт в навигации — допиши его в массив `NAV_ITEMS` в
   `src/components/layout/MainNav.tsx`.

Ничего регистрировать не нужно: папка = маршрут. **Но проверь имя папки** — если
начнёшь с `_`, страница не появится (см. раздел 3.3).

### 7.2 «Хочу новый API-метод»

Например, `GET /api/artists`.

1. Создай `src/app/api/artists/route.ts` и экспортируй функцию с именем метода:

   ```ts
   export async function GET(request: Request): Promise<Response> { ... }
   ```

2. Разбери вход (`new URL(request.url)`, `parseNumberParam` из `@/lib/api-helpers`)
   и позови функцию из `lib/db` — **логика в обработчике не пишется**.
3. Верни ответ через `json(...)` и `noStoreHeaders` из `@/lib/api-helpers`, ошибки —
   через `jsonError(...)`, общий перехват — `handleApiError(error)`.
4. Добавь `export const dynamic = "force-dynamic";` — как в остальных файлах.

**Осторожно:** не клади `route.ts` в папку, где уже есть `page.tsx` — Next.js
такого не разрешает.

### 7.3 «Хочу новый запрос к базе»

1. Выбери файл: треки — `src/lib/db/track-queries.ts`, плейлисты —
   `playlist-queries.ts`, история — `history-queries.ts`.
2. Пиши на Drizzle, а не склейкой строк: значения передаются параметрами
   (`eq(...)`, `inArray(...)`), иначе получишь SQL-инъекцию. Рядом в комментарии —
   эквивалентный SQL (`-- SQL: SELECT ...`).
3. Возвращаешь треки — прогони строки через маппер
   (`toTrackDTO`/`toTrackDTOList` из `mappers.ts`), чтобы наружу шёл `TrackDTO`,
   а не строка таблицы.
4. Помни про N+1: вместо запроса в цикле — один запрос с `inArray(...)`.
5. Ни компонент, ни `route.ts` не должны содержать SQL: они зовут твою функцию.

### 7.4 «Хочу новую таблицу в базе»

1. Опиши таблицу в `src/lib/db/schema.ts` — **это единственное место, где живёт
   схема.**
2. Сгенерируй миграцию:

   ```bash
   bunx drizzle-kit generate
   ```

   Появится новый SQL-файл в `drizzle/` (например, `0001_....sql`). **Его
   коммитят в git** — миграции и есть история изменений базы.
3. Применять отдельно не нужно: `src/lib/db/client.ts` вызывает `migrate()` при
   первом обращении к базе, то есть при старте приложения. Достаточно
   перезапустить dev-сервер. Посмотреть данные глазами — `bunx drizzle-kit studio`.
4. Руками `ALTER TABLE` из консоли не делаем: следующий `migrate()` разъедется
   со схемой.
5. Если база «сломалась» настолько, что проще начать заново — `bun run db:reset`
   (удаляет `data/music.db`), затем запусти приложение и нажми «СКАНИРОВАТЬ»:
   база соберётся заново из файлов. В этом и смысл правила «музыка — источник
   правды, база — индекс».

### 7.5 «Хочу новый компонент»

Сначала ответь: **нужны ли ему хуки или обработчики событий?**

* **Нет** → серверный компонент (никакой директивы): читает базу напрямую,
  в браузер не уезжает вовсе.
* **Да** → клиентский: первая строка файла `"use client";`.

Дальше выбери папку по области приложения:

| Что за компонент | Папка |
| --- | --- |
| Часть каркаса (шапка, сайдбар, панель) | `components/layout/` |
| Про воспроизведение | `components/player/` |
| Про список треков, поиск, фильтры | `components/library/` |
| Про плейлисты | `components/playlists/` |
| Про историю и статистику | `components/history/` |
| Универсальная мелочь без предметной логики | `components/ui/` |

Имя файла — `PascalCase`, совпадает с именем компонента. Данные передавай
пропсами с сервера. После изменения данных на клиенте вызывай `router.refresh()`,
а **не** `window.location.reload()` — перезагрузка убьёт воспроизведение музыки.

### 7.6 «Хочу изменить оформление»

Оформление живёт в двух местах:

1. **`src/app/globals.css`** — дизайн-система: токены в блоке `@theme`
   (`--color-accent`, `--color-accent`, `--color-surface`…) и готовые классы
   `term-panel`, `term-btn`, `term-btn-danger`, `term-title`, `term-input`,
   `track-row`, `term-range`, `cursor-blink`, `glow`, `ascii-rule`. Правишь цвет
   один раз здесь — он меняется во всём приложении.
2. **Классы в JSX** — утилиты Tailwind (`flex`, `gap-3`, `text-[11px]`).

Правила: цвета берём **только через токены** (`text-ink / text-accent`, а не `text-[#00ff41]`),
а перед новым классом проверь, нет ли уже подходящего `term-*`. Шрифт
подключается в `src/app/layout.tsx` через `next/font` (IBM Plex Mono с
кириллицей). Анимации обязаны отключаться при `prefers-reduced-motion: reduce` —
это уже учтено, не ломай.

## 8. Чего в проекте СОЗНАТЕЛЬНО нет и почему

Это, пожалуй, самая важная глава для понимания. Отсутствие перечисленных
технологий — **не недоработка и не «пока не успели»**. Это осознанное
инженерное решение, зафиксированное в ТЗ и повторённое в правилах проекта:

> Redis, PostgreSQL, отдельный backend, микросервисы, Kubernetes, Supabase,
> облачные сервисы, сложная авторизация, ИИ-фичи — не добавляем.

| Чего нет | Что было бы «как в продакшене» | Почему не здесь |
| --- | --- | --- |
| **PostgreSQL** | Отдельный сервер БД, пользователь, права, сеть | SQLite — это файл. Нет сервера, нет настройки, нет «подними базу перед запуском». Для личной библиотеки из сотен треков SQLite не просто достаточен — он **лучше**: база лежит рядом и удаляется одной командой |
| **Redis** | Кэш, сессии, очереди задач | Кэшировать нечего: запросы к локальному SQLite занимают микросекунды. Добавить Redis — значит добавить сервис, сеть и точку отказа ради нулевой выгоды |
| **Отдельный backend** | Плюс Express/Nest/FastAPI рядом с фронтендом | Next.js уже умеет бэкенд: Route Handlers и Server Components — это тот же сервер, один процесс, один язык, один деплой |
| **Микросервисы** | Отдельные сервисы для каталога, плейлистов, аудио | У проекта один пользователь и один процесс. Микросервисы решают задачу координации больших команд — здесь координировать некого, а сложность выросла бы многократно |
| **Kubernetes** | Оркестрация контейнеров, автоскейл, ingress | Один контейнер на одном компьютере. `docker compose up -d` — и всё работает. Kubernetes был бы в десятки раз сложнее самого приложения |
| **Supabase / облако** | Внешний хостинг, managed-база, CDN | Музыка лежит у тебя на диске и никуда не уезжает. Локальность — не компромисс, а требование: это персональный плеер, а не сервис |
| **Сложная авторизация** | Логин, пароль, сессии, роли, OAuth | Пользователь ровно один — хозяин. Единственное, что действительно нужно, — не отдавать музыку соседям по Wi-Fi; это решает необязательный токен в `STREAM_TOKEN` (проверяется в `api/tracks/[id]/stream/route.ts`) |
| **ИИ-фичи** | Рекомендации, автотеги, «похожие треки» | ТЗ прямо просит не усложнять. Проект «для отдушины» после основной учёбы, а не второй крупный продукт |

Главный принцип здесь такой:

> **Меньше технологий — это тоже архитектурное решение, и часто самое сложное.**
> Добавить сервис легко, а вот объяснить, зачем он нужен, — трудно.

Практические следствия, которые стоит ценить: проект **стартует мгновенно**
(`bun run dev`, и всё — ничего не надо поднимать), **целиком уезжает в одном
образе** с данными в двух томах (`./music` и `./data`), **помещается в голове** —
его можно прочитать за вечер. Каждая новая зависимость — исключение, требующее
обоснования: стандартная библиотека и уже выбранные инструменты закрывают почти всё.

При этом проект **не игрушечный**: здесь настоящий потоковый HTTP с `Range`,
настоящие миграции, схема с внешними ключами и `ON DELETE CASCADE`, Docker с
многоэтапной сборкой. Просто без технологий, которые этой задаче не нужны.

## 9. Как читать проект новичку: порядок из десяти файлов

Не открывай файлы подряд по алфавиту — это самый быстрый путь к каше в голове.
Иди **от внешнего к внутреннему**: сначала адреса и каркас, потом данные, потом
логика, потом файлы. Каждый следующий шаг опирается на предыдущий.

| # | Файл | Зачем читать именно здесь |
| --- | --- | --- |
| 1 | `package.json` | Точка входа в проект: что за стек, какие команды есть (`dev`, `build`, `typecheck`, `db:reset`), какие зависимости. После него понятно, с чем вообще имеешь дело |
| 2 | `src/app/layout.tsx` | Каркас: где живёт `PlayerProvider` и почему именно здесь. Показывает, что общего у всех страниц |
| 3 | `src/app/page.tsx` | Первая настоящая страница: как серверный компонент читает базу и передаёт данные компонентам. Здесь видно всю схему «URL → SQL → HTML» |
| 4 | `src/lib/types.ts` | Словарь проекта. Что такое `TrackDTO`, `PlaylistDTO`, `TrackSortKey`. Дальше все файлы читаются втрое легче, потому что термины уже знакомы |
| 5 | `src/lib/db/schema.ts` | Модель данных: пять таблиц, связи, индексы. Поняв схему, ты понимаешь половину проекта — остальное это способы её показать и изменить |
| 6 | `src/app/api/tracks/[id]/stream/route.ts` | Самый «мясной» файл: поток, `Range`, `206 Partial Content`, защита от path traversal, MIME-типы. Здесь проходит граница между «просто сайт» и «музыкальный плеер» |
| 7 | `src/components/player/player-context.tsx` | Ядро клиентской части: очередь, `<audio>`, три контекста, сохранение позиции. Самый большой файл, но после шагов 4–6 он читается логично |
| 8 | `src/components/library/TrackList.tsx` | Как список отрисовывает данные с сервера и реагирует на клики. Связь «пропсы с сервера → интерактивность на клиенте» становится наглядной |
| 9 | `src/lib/db/track-queries.ts` | Где на самом деле живут запросы: фильтры, сортировка, upsert, индексация по пути. Сравни с шагом 3: страница лишь вызывает эти функции |
| 10 | `Dockerfile` + `docker-compose.yml` | Финал: как всё это упаковывается в образы и запускается одной командой, где монтируются музыка и база |

Что делать после: открой `src/lib/scanner/` (как файлы попадают в базу) и
`src/lib/format.ts` (как данные превращаются в человеческий текст). Это две
небольшие папки, которые замыкают картину.

И держи под рукой три подсказки на все случаи:

* **Не понимаешь, откуда взялся адрес** — иди по папкам `src/app/`.
* **Не понимаешь, откуда взялись данные** — ищи функцию в `src/lib/db/`.
* **Не понимаешь, почему что-то на экране** — ищи компонент в `src/components/`
  по имени, которое видишь в JSX.

## Итого

* `src/app/` — адреса и HTTP. Папка = URL, `page.tsx` = страница, `route.ts` = API.
* `src/components/` — показ и взаимодействие, сгруппированные по областям.
* `src/lib/` — логика: `db` (данные), `scanner` (файлы), `format` (чистые функции),
  `config` (настройки). Ни одной строчки JSX.
* `drizzle/` — история изменений схемы; `data/` и `music/` — данные, не код.
* Серверный компонент → база напрямую. Браузер → только через `src/app/api/`.
* Добавить код почти всегда означает одно из четырёх: папка в `app/`,
  функция в `lib/db/`, запись в `schema.ts` + миграция, компонент в `components/`.
